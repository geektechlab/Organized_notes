When we are unable to allocate memory due to zones
dipping below their minimum watermark, memory re-
serves are exhausted, and direct reclaim has failed we
must take drastic action to avoid the system becom-
ing unusable. At this stage the Out of Memory (OOM)
Killer steps in, finds the biggest memory hog and kills
the process and all associated threads. In this chapter
we explore how this is implemented and the criteria
the OOM killer uses to determine which process to
eliminate.
One of the central tenets of the Linux memory management subsystem
is the disconnect between virtual memory mappings and the physical mem-
ory which backs them.
Ordinarily, a mapping performed by malloc() or mmap() will result in ab-
solutely no physical memory being allocated. Instead, the struct mm_struct
object describing a process’s address space object will have a new
struct vm_area_struct (Virtual Memory Area or “VMA”) object assigned to
it, describing the mapped range (see chapters 3 and 4 for an in-depth discus-
sion). The actual allocation of memory is therefore only performed when a pro-
cess attempts to access it, at which point a CPU hardware fault arises which
is trapped by the kernel and processed as a “page fault” (see Chapter 6).
On page fault, the faulting address is checked to determine whether it is
address is within a valid VMA range. If so, memory is allocated as necessary,
if not a segfault signal is sent to the process.
As a result, it becomes entirely possible for a process to access a valid
mapping that causes the kernel to attempt to allocate physical memory, only
to find it is unable to do so.
In this situation the kernel must do something in order to maintain system
stability, as the mapping of the memory is a long-distant memory and there
is no mechanism by which to indicate to the process which mapped it that
the allocation could not be performed.
N O T E It’s also important to note that, even if the mapping process could somehow be in-
formed, it would most likely result in that process simply terminating, as it is rarely
the case that an arbitrary allocation can simply be allowed to fail. Given that the
process(es) which are causing the memory pressure might well be distinct from the one
happening to fault, this wouldn’t even necessarily help relieve the underlying mem-
ory pressure anyway.
That something is the Out of Memory (OOM) killer, which resolves the
situation by determining which process is using the most memory (subject
to manual user adjustment via the /proc/oom_score_adj interface see Section
13.2) and kills it, thus (hopefully) freeing sufficient memory to complete the
failing allocation.
The selection of a process to kill (the “victim”) and freeing it (“reaping”
it) are two separate events, occurring at different times. The victim is se-
lected as soon as the OOM killer event occurs, and then a kernel thread as-
signed to reaping victim threads is woken to perform the actual freeing of
memory.
A failed allocation will be retried as long as forward progress is made
in freeing up memory, and the selection of an OOM victim constitutes
progress, thus the actual result of the killing will tell after it has been ini-
tiated. See Section 13.4 below for a detailed examination of how this oc-
curs and Chapter 11 for a detailed examination of how forward progress is
utilised as a concept on reclaim.
A manual invocation of the OOM killer can also be performed via the
sysrq-f operation, see Section 13.1.2 for details.
13.1 Causes of Out of Memory Conditions
13.1.1 Memory Allocation
As described in Chapter 2, in order to ensure that the system never reaches
a point where memory is so critically low that the kernel might not be able
to function, we must maintain minimum reserves and establish watermarks
below which we start to attempt to free up memory. These watermarks are maintained per-zone, per-NUMA node (if NUMA
is enabled) and determine the point at which reclaim occurs. Reclaim is the
means by which the kernel frees up memory without killing any processes
(see chapter 11 for a detailed exploration of reclaim).
While this is covered in chapter 2, but briefly—a zone is simply a named
physical memory range. For instance, the first 16 MiB of x86-64 machines
is designated ZONE_DMA, as this is the only range of physical memory very old
DMA devices could access. Each NUMA node further subdivides the physi-
cal memory range, associating CPUs with the memory they are electronically
local to. Nodes can span multiple zones.
N O T E NUMA is an abbreviation for Non-Uniform Memory Access, and describes the mech-
anism by which the kernel handles architectures which have memory which is not
equally fast to access from all CPUs. Beyond the fundamentals around nodes and
zones, this is out of scope for the book.
For file-backed memory, reclaim can be as simple as dropping memory
from the page cache (see chapter 9), for anonymous i.e. non-file backed
memory this involves swapping memory out to disk. Kernel memory allo-
cated using the slab allocator might also reduce cache sizes via shrinkers (the
slab allocator is out of scope for the book).
When physical memory is allocated, it ultimately originates from a spe-
cific zone (see chapter 2 for the details as to how this is designated). When
doing so, the zone watermarks are checked. There are three core water-
marks – WMARK_MIN, WMARK_LOW and WMARK_HIGH (there’s also WMARK_PROMO, but this is
used by NUMA for very specific purposes which are out of scope here).
When the low watermark is reached, indirect reclaim is started in the
form of the kswapd kernel thread (there is one process per NUMA node).
This performs reclaim in the background until at least one zone which could
serve the allocation reaches the high watermark, at which point it sleeps
(again, see chapter 11 for more on reclaim).
If the memory pressure is extreme, this might not be enough – in this
instance, a zone might reach the minimum water mark at which point direct
reclaim can occur – this is reclaim that the process must wait until before
proceeding.
Finally, if the direct reclaim cannot free up sufficient memory, we are
left in a difficult position where we are simply unable to service a page fault,
which renders the process unable to continue executing.
The simplest solution to this would be to kill the faulting process causing
the allocation, however this would be unfair – the disconnect between map-
ping and backing of memory in linux means that a faulting process may have
absolutely no relation to one which is using excessive memory.
N O T E It’s actually possible to cause the kernel to kill the allocating process via the
vm.oom_kill_allocating_task tunable. See Section 13.3 for details. Instead, we invoke the Out Of Memory killer to elect the most appropri-
ate victim to kill whose memory we can immediately free. This maintains
system stability even in the face of extreme memory pressure.
It’s worth reflecting on how we might end up in this situation in the first
place – how can a process allocate more memory than the system has avail-
able? The answer is overcommit – by default, the kernel does not constrain
memory mapping such that it must fit in available physical memory, rather it
simply disallows any one mapping which exceeds available physical and swap
memory (see Chapter 4 for more details on this).
13.1.2 sysrq-f
The sysrq interface is a means by which users can perform actions using a
special key combination (typically alt + the sysrq/print screen key + a letter
to indicate the task to perform).
This may not even be enabled by your kernel (you can determine this by
examining the kernel.sysrq tunable which masks out various available sysrq
operations). Even if unavailable from the command line, it’s possible to trig-
ger sysrq events by writing to the /proc/sysrq-trigger procfs interface.
An OOM killer-relevant operation exposed by this interface is sysrq-f,
which causes the out of memory killer to be unconditionally invoked and to
kill the process using the most resources as if an allocation had failed.
This will not result in a kernel panic no matter the outcome of the OOM
killer invocation, it will simply perform the kernel’s process selection logic
and terminate the selected process.
See Section 13.4 for a detailed analysis as to how this actually imple-
mented within the kernel.
13.2 OOM Killer Score Adjustment
It is possible to adjust the likelihood of a process being selected for termina-
tion via the OOM killer score adjustment interface as exposed per-process
via procfs in /proc/$pid/oom_score_adj (there is also an /proc/$pid/oom_adj inter-
face, however this is deprecated and simply used to calculate a value to set
oom_score_adj to so we disregard it).
The score is standardised to a range of -1000 to 1000, and defaults to 0. At
0, the process is as likely as any other (unadjusted) process to be selected by
the OOM killer. At -1000 the process will never be killed by the OOM killer,
and at 1000 the process will almost certainly be selected (unless an alterna-
tive process which also has a very high adjustment score assigned uses more
memory).
When the OOM killer considers a process for termination, it does so by
determining how much resident memory it is utilising and compares it to all
the other processes in the system, selecting the one that is using the most
resident memory.

🔥 OOM Killer Internals (Explained Simply)
1. Why OOM Killer Exists
When Linux runs out of memory, normal reclaim fails (dropping cache, swapping, shrinking slabs).

At that point, the kernel must kill a process to free memory, otherwise the system deadlocks.

The OOM killer chooses which process to kill and frees its memory.

2. Scoring: How Processes are Chosen
Each process has a score (oom_score) that reflects how much memory it uses compared to the system’s total memory.

This score can be adjusted with /proc/$pid/oom_score_adj:

Range: -1000 → 1000

-1000 → immune (never killed)

0 → default, neutral chance

1000 → almost guaranteed to be killed

Internally:

The adjustment is in 0.1% of total RAM+swap.

Example: oom_score_adj=-400 → process treated as if it used 40% less memory.

Example: oom_score_adj=20 → treated as if it used 2% more memory.

This way, critical daemons (e.g., systemd) can be protected, while non-essential hogs are more likely killed.

3. Score Normalization
Linux converts oom_score_adj into a normalized 0–2000 range (internally).

Why?

Because historically, userland tools expected scores in that range.

Formula:

Offset + scale (by 2/3) to fit in range.

Maximum value = 2000.

4. When OOM is Triggered
OOM happens after multiple fallback attempts fail:

Allocate from PCP lists (fast path).

If fail → allocate from zones but don’t drop below low watermark.

If fail → enter slow path reclaim (__alloc_pages_slowpath).

If fail → direct reclaim.

If still fail → last attempt with very high watermark, no direct reclaim.

If still fail → invoke OOM Killer (__alloc_pages_may_oom → out_of_memory()).

So OOM killer is last resort after all reclaim has failed.

5. The Kernel Structures
Main struct: struct oom_control
Contains:

zonelist: memory zones considered.

nodemask: NUMA restrictions if policy applies.

memcg: memory cgroup (if OOM is within cgroup).

gfp_mask: allocation flags that triggered OOM.

order: allocation order (e.g., higher-order pages).

Internal:

totalpages: total system pages.

chosen: process picked as victim.

chosen_points: badness score of chosen process.

constraint: info about policy/cgroup constraints.

This struct carries all context about why OOM occurred and how to select the victim.

6. Manual OOM Trigger (sysrq-f)
User can manually invoke OOM killer:

Press Alt+SysRq+F (if enabled).

Or: echo f > /proc/sysrq-trigger.

In this case:

oom_control.order = -1 marks it as manual.

The kernel avoids panic-on-OOM and behaves differently.

If no task can be killed → prints info but doesn’t panic.

7. OOM Killer Core Flow
From the diagram (Fig 13-1):

__alloc_pages_may_oom() → calls out_of_memory().

Inside out_of_memory():

Check if OOM killer disabled.

If current process already dying, just reap it.

If sysctl_oom_kill_allocating_task=1, kill the allocating task directly.

Otherwise, run badness heuristic (oom_badness()) to select worst process.

Mark it (mark_oom_victim()).

Queue oom_reaper kernel thread to free memory.

If no process is found:

If sysrq invoked → just return.

If real OOM with no killable process → panic (deadlocked system).

8. Alternative Behaviours
Two important sysctls:

vm.panic_on_oom

If set → kernel panics instead of killing.

Used in environments where killing is unacceptable.

vm.oom_kill_allocating_task

If set → kill the allocating process (the one that triggered OOM).

Default = off, since faulting process may not be real hog.

9. Code Flow Example
Allocation fails → enters __alloc_pages_may_oom().

Tries fallback: get_page_from_freelist().

If still fails → builds oom_control object.

Calls out_of_memory(&oc).

Selects victim → oom_kill_process().

Sends SIGKILL → memory reaped.

✅ Final Summary
Linux OOM killer is a last resort mechanism.

Triggered when reclaim & reserves fail.

Victim chosen by memory usage + oom_score_adj.

oom_score_adj lets admins protect or bias processes.

Controlled via oom_control struct inside kernel.

Can be manually triggered (sysrq-f).

Alternative behaviours: panic (vm.panic_on_oom) or kill allocating task (vm.oom_kill_allocating_task).

If no process can be killed → system panics (deadlocked).

🔥 OOM Victim Selection Internals (Explained)
1. oom_badness() — The Scoring Function
Purpose: Assign a “badness score” to a task. Higher = more likely to be killed.

Inputs:

task_struct *p → the process being considered.

totalpages → total RAM + swap available.

Steps:

Skip if task is unkillable (init, kernel threads, or explicitly protected).

Lock task’s mm_struct (address space). If task has no mm (already exiting), skip.

Skip if:

It’s already been reaped, or

It’s in vfork, or

oom_score_adj = -1000 (immune).

Compute baseline score = process’s memory usage:

RSS (resident set size)

swap usage

page tables (in pages)

Normalize score to fraction of total memory.

Add oom_score_adj (scaled by totalpages/1000).

👉 Result: A process with huge resident memory and high oom_score_adj = very high badness.

2. oom_unkillable_task()
Checks if a task is immune:

Global init process (PID 1).

Kernel threads (PF_KTHREAD).

If yes → never killed.

3. find_lock_task_mm()
Ensures we can safely reference the task’s mm_struct (address space).

Process may be partly exiting, but a sub-thread may still hold mm.

If found, lock it → safe to proceed. If none → return NULL (skip).

4. task_will_free_mem()
Before killing, check if the task will exit soon anyway:

Already has SIGKILL pending.

In process of exiting (PF_EXITING).

All threads in group marked for exit.

If yes → just mark as victim and let it free memory naturally.

5. process_shares_mm()
Iterates through all threads in a thread group.

Checks if they share the same mm_struct (address space).

Needed because if one thread exits, all must exit for memory to be freed.

6. task_will_free_mem() wrapper
Wraps the above checks with extra edge cases:

Skip tasks already drained by the OOM reaper.

Skip tasks marked MMF_OOM_SKIP (not useful to kill).

If only one user left of mm_struct (mm_users <= 1), assume memory will be freed soon.

Ensures all threads sharing mm are also dying, otherwise memory won’t be freed.

👉 Ensures OOM doesn’t waste time killing processes that won’t release memory.

7. oom_evaluate_task()
Evaluates each candidate task:

Skip if unkillable.

Skip if already victim.

If this task is the origin of OOM (i.e. triggered allocation failure), give it LONG_MAX score (kill immediately).

Otherwise → call oom_badness() for real score.

Compare against current best (stored in oc->chosen_points).

If better, replace chosen victim.

8. select_bad_process()
Core loop:

Iterates over all processes.

Calls oom_evaluate_task() for each.

Keeps track of highest badness score.

Final result stored in struct oom_control:

chosen → the victim process.

chosen_points → its score.

9. out_of_memory()
Orchestrates everything:

Check if OOM disabled.

Check if current task will free memory (skip kill).

If vm.oom_kill_allocating_task=1 and current is valid → kill allocating task.

Otherwise → run select_bad_process().

If no process found:

If sysrq-f → return.

Else → panic (system deadlocked).

Kill chosen process via oom_kill_process().

Queue reaper thread to free its memory.

✅ Summary (Crisp)
Scoring (oom_badness) = based on RSS, swap, page tables, + adjusted with oom_score_adj.

Unkillable processes: init, kernel threads, oom_score_adj=-1000.

Special handling:

Already dying tasks just marked victim.

Allocating task killed first if oom_kill_allocating_task=1.

sysrq-f manually triggers global OOM.

Victim selection = process with highest badness score after skipping protected/unhelpful ones.

Final kill = send SIGKILL, queue OOM reaper, free memory.

Schedules the victim for reaping.

1. Why OOM Happens
Virtual vs Physical memory mismatch

malloc()/mmap() only reserve virtual space.

Physical pages allocated lazily (on access).

If no memory available at page fault → OOM.

Zones & Watermarks

Memory split into zones (DMA, NORMAL, etc.).

Watermarks:

WMARK_HIGH = healthy

WMARK_LOW = background reclaim (kswapd)

WMARK_MIN = allocations must reclaim directly

If even direct reclaim fails → OOM.

Overcommit

Linux allows allocating more virtual memory than available physical (/proc/sys/vm/overcommit_memory).

When commitments can’t be fulfilled → OOM.

2. OOM Killer Trigger
Triggered when kernel can’t satisfy allocations and reclaim fails.

Already exiting tasks skipped.

7. oom_reap_task()

Set MMF_UNSTABLE → marks mm unstable (future accesses SIGBUS).

File-backed pages skipped (already reclaimable).
