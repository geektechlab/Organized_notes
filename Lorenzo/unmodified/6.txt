1. Virtual vs Physical
Virtual memory (VA): What user programs see (e.g., malloc(4096) gives a virtual address).

Physical memory (PA): Actual RAM that backs those addresses.

The MMU (Memory Management Unit) + page tables translate VA → PA.

When you malloc(), the kernel does not immediately allocate RAM. Instead:

It reserves a range of VAs (a VMA, Virtual Memory Area).

Actual RAM is only allocated when you first touch the memory.

This is why malloc(1 GB) and never using it doesn’t eat RAM.

2. What Triggers a Page Fault?
A page fault happens when:

The MMU walks the page table and finds no valid mapping for the VA.

Or, the access type (read/write/execute) doesn’t match permissions.

At this point:

Hardware raises a trap (#PF on x86, Data Abort on ARM).

CPU jumps into the kernel’s page fault handler (do_page_fault() in Linux).

3. The Kernel’s Job at Page Fault
The kernel inspects:

Which VMA contains this address?

Is the access valid? (e.g., writing to a read-only mmap would cause SIGSEGV).

If valid:

For anonymous memory (like malloc): kernel allocates a new physical page, zeroes it, updates the PTE (page table entry).

For file-backed memory (mmap of a file): kernel looks in the page cache:

If the page is already cached → just map it.

If not → read from disk into page cache, then map it.

This is demand paging: RAM is committed only when actually needed.

4. “Faulted In” Pages
When a page is allocated or loaded into RAM due to a page fault, it is said to be faulted in.

Can be:

Read fault → first read of that page.

Write fault → first write, often triggers Copy-on-Write (COW).

5. Pre-faulting with MAP_POPULATE
Normally, pages are faulted in lazily.
But if you call:

mmap(..., MAP_POPULATE, ...);
The kernel will pre-fault them → it touches each page in advance (like simulating a write fault) so future access won’t cause page faults.

6. Complexity (Swap, Migration, NUMA)
This is where real kernel trickiness comes in:

Swap: If a page was evicted, page fault triggers swap-in from disk.

Page migration: NUMA balancing may move a page between nodes, and fault handling redirects access.

Huge pages / THP: Fault granularity changes.

7. Architecture-specific Details
Hardware exceptions differ (x86 #PF, ARM Data Abort).

But once the kernel gets control, it funnels into common Linux fault handling paths (handle_mm_fault() etc.).

✅ Key Takeaway for You

Mapping != Allocation. A VMA defines the allowed range, but no RAM is committed until access.

Page fault is the MMU screaming “no mapping/permissions” → kernel decides whether to fix it (allocate/map) or kill the process.

Anonymous vs File-backed → allocate zero page vs load from page cache/disk.

Advanced features (swap, NUMA, COW) are all just specialized page fault handling cases.

If not spurious → we’re really in trouble.

Handles invalid kernel memory accesses.

Calls kernelmode_fixup_or_oops().

5. kernelmode_fixup_or_oops()
Two cases:

Fixup possible:

If in exception context (e.g., get_user()/copy_from_user()), kernel has a fixup handler via fixup_exception().

These are “safe probes” into user memory. If the faulted, kernel resumes gracefully.

Otherwise: it’s a real kernel bug → call page_fault_oops().

Final stop: kernel says “Oops, something went bad”.

Steps:

Special cases:

Stack overflow → guard page check.

In kernel threads (no user process to kill), an Oops can panic the kernel.

Spurious vs Real Faults

Spurious = stale TLB after permissions upgrade.

Never spurious if P=0 (not present).

Only affects W→RO or X→NX upgrades.

Huge Pages

spurious_kernel_fault() must detect large entries (pmd_large, pud_large) and check permissions at that level.

Safe Probing of User Memory

get_user() and copy_from_user() rely on fixup exceptions.

Guard Pages

Kernel stacks have guard pages to detect overflows via page fault.

Oops Handling

Not the same as panic:

Oops → try to kill offending task.

Panic → whole kernel halts.

🧩 Why Do Kernel Faults Happen?
You’re right in principle:

The kernel’s address space is always mapped (at least the linear/direct mapping part),

Kernel memory is never swapped out,

Kernel virtual addresses are generally static and permanent compared to user mappings.

So why can the kernel still take page faults?

👉 Because not every kernel access is to the linear map. There are several situations where kernel code still triggers faults:

1. Accessing User Memory in Kernel
Kernel often copies data between user and kernel (syscalls: read, write, copy_from_user, etc).

These dereferences go through user VMAs (not kernel linear map).

If the user page isn’t present → page fault.

That’s why kernel must use get_user() / copy_from_user() with fixup tables.

Without fixup → unrecoverable kernel page fault (Oops).

2. Lazy TLB Invalidation (Spurious Faults)
Kernel updates PTEs (e.g., RO → RW) but doesn’t flush TLB immediately (to avoid costly shootdowns).

If CPU uses stale TLB entry, it faults — but the page table entry is already valid.

Kernel detects this via spurious_kernel_fault().

3. Guard Pages
Kernel stacks have guard pages at their bottom.

If kernel stack overflows, next access hits an unmapped guard page → fault → stack overflow detected.

4. Special Mappings
Not all kernel addresses are linear map:

vmalloc/ioremap regions are mapped lazily.

Accessing them may fault until the page table is set up.

5. Speculation & Prefetch
CPU may speculatively prefetch invalid addresses → page fault (ignored if instruction never retires).

Example: AMD erratum #91 (prefetch RIP corruption).

6. Hardware Poison / ECC Errors
If a kernel-mapped page is marked hardware-poisoned (memory error), accessing it causes a machine-check-driven fault.

👉 So kernel faults ≠ “swap-like” faults. They’re either:

Accessing user mappings from kernel.

Guard/protection mechanisms.

Lazy TLB / speculation.

Hardware errors.
