Short summary (one-paragraph)
The kernel implements reverse mapping (rmap) so that from a physical folio (or struct page/struct folio) it can find every vm_area_struct (VMA) that maps it. A folio’s mapping pointer points either to a struct address_space (file-backed/pagecache folios) or to an struct anon_vma (anonymous memory). For anonymous pages the kernel uses anon_vma_chain objects to record which VMAs refer to an anon_vma; the chains let the kernel walk from a folio’s anon_vma to all VMAs that map it (needed for try_to_unmap(), COW/fork handling, reclaim). For file-backed folios the address_space / pagecache data structures are used to enumerate mappings. See kernel docs and rmap.c for the implementation.

Why the intermediary (anon_vma + anon_vma_chain) is needed
A folio can be mapped into many VMAs (forked processes, shared mappings). Mapping every folio to an explicit list of VMAs would cause duplication and expensive updates on fork/split/merge.

Instead, the kernel keeps per-VMA anon_vma_chain entries and a smaller anon_vma object per related group. This gives a many-to-many representation that’s cheap to maintain when VMAs are split/merged/forked. (Rik van Riel’s anon_vma_chain work from ~2010 was critical to scalability.)

🔑 What Reverse Mapping Is
Forward mapping: virtual address → physical folio (via page tables).

Reverse mapping (rmap): given a folio, find all vm_area_structs (VMAs) that map it.

Needed for reclaim, page migration, COW, NUMA balancing, KSM, etc. → we must unmap/update PTEs in every process that maps the folio.

🧱 Core Data Structures
1. struct folio
Physical memory unit.

Key field: folio->mapping

If file-backed → points to struct address_space.

If anonymous → points to struct anon_vma.

2. struct anon_vma
Represents a set of anonymous folios.

Purpose: VMAs are ephemeral (split/merge/fork), so we don’t attach folios directly to VMAs. Instead, folios attach to anon_vma, and anon_vma links to VMAs.

Contains:

rb_root: interval tree of mappings.

num_children: child count (for reuse).

num_active_vmas: how many VMAs currently map it.

parent: for fork hierarchy.

3. struct anon_vma_chain (AVC)
Glue object: connects a specific VMA ↔ anon_vma.

There is exactly one AVC for each VMA–anon_vma pair.

Stored:

In VMA.anon_vma_chain list (so VMA can find its anon_vmas).

In anon_vma.rb_root interval tree (so anon_vma can find all VMAs covering offsets).

4. struct vm_area_struct (VMA)
Describes a contiguous memory range in a process.

Fields relevant to rmap:

struct list_head anon_vma_chain; → linked AVCs.

struct anon_vma *anon_vma; → root reference.

vm_file / shared.rb if file-backed.

Ephemeral: created/destroyed on mmap/split/merge/fork.

5. struct address_space
For file-backed mappings (page cache).

Key field: i_mmap: an interval tree of VMAs mapping this file (red-black tree).

Each folio indexes into this using its index (page offset within file).

⚙️ How Reverse Mapping Works
Anonymous memory:
Folio has mapping → anon_vma.

Walk anon_vma.rb_root interval tree.

Each node = anon_vma_chain.

From anon_vma_chain, get VMA.

Compute correct virtual address in VMA using folio->index (virtual page offset).

Operate (unmap, migrate, check COW status, etc.).

File-backed memory:
Folio has mapping → address_space.

Walk address_space->i_mmap red-black interval tree.

Each node = VMA.

Offset checked via folio->index (page offset in file).

Operate on PTEs as needed.

🌀 Why We Need This Indirection
If each folio carried a list of VMAs → duplication + high cost on fork/split/merge.

Fork: one folio suddenly maps into 2+ processes.

Split: one VMA becomes two; folios may need to map differently.

Merge: VMAs fuse; folio mappings must merge too.

Solution: lightweight anon_vma + anon_vma_chain model. Many-to-many, scalable.

📚 Examples From Diagrams
Initial VMA (Fig 7-1)
VMA → AVC → anon_vma.

One num_active_vmas = 1, one num_children = 1.

Fork (Fig 7-2)
Parent anon_vma cloned for child.

Parent’s anon_vma still references both VMAs (for shared COW).

Child gets its own anon_vma for private copies.

Separate interval trees maintained for parent & child.

Split (Fig 7-3)
VMA split into two.

New AVC created for each sub-VMA.

Both still point to the same anon_vma (so folios are tracked correctly).

num_active_vmas = 2.

Merge Back (Fig 7-4, 7-5)
Kernel tries to restore single-VMA state if mergeable.

Rule: VMA can only have one anon_vma.

If two VMAs had different anon_vmas → merging forbidden (checked via is_mergeable_anon_vma()).

📂 File Reverse Mapping (Fig 7-6)
File-backed VMA’s reverse mapping = simpler.

Folio → mapping → address_space.

address_space → i_mmap red-black tree → VMA list.

No need for anon_vma_chain, because file mapping doesn’t fork into multiple unrelated copies (COW semantics don’t apply the same way).

🚨 Edge Cases
MAP_PRIVATE file mappings:

On COW, they appear in both the file’s i_mmap tree and anon_vma’s tree.

These are “hybrids” → look like file-backed at first, but after write they act like anonymous.

Truncate/shrink file:

i_mmap used to find VMAs covering truncated range → clear their PTEs.

VMAs can split/merge:

Interval tree helps efficiently update all AVCs without retagging every folio.

🔒 Locking
Folio lock held during try_to_unmap / migration.

anon_vma root rwsem protects anon_vma hierarchy.

mmap_lock protects VMA tree of a process.

rmap_walk() handles concurrency (can retry on race).

🧑‍💻 Interview-Ready Insights (FAANG/Arm UK Core)
Why rmap exists: Without it, kernel couldn’t reclaim/migrate pages safely because it wouldn’t know which PTEs to zap.

Design trade-off: direct folio→VMA list = expensive; indirection via anon_vma_chain = scalable.

Data structures used:

anon_vma trees (for anonymous).

address_space i_mmap red-black tree (for file).

Interval trees (efficient range lookup).

Fork & COW complexity: parent/child must share enough state for COW, but also diverge on write → why separate anon_vma hierarchies exist.

Edge case: MAP_PRIVATE file mappings belong to both trees until COW, then behave like anonymous.

Locking discipline: must hold folio lock when traversing rmap, plus anon_vma root rwsem when modifying trees.

Scalability: anon_vma reuse, interval trees, and AVC indirection minimize cost when VMAs are split/merged frequently.

Connects 1 VMA ↔ 1 anon_vma.

Inserted both into:

VMA’s anon_vma_chain list (same_vma).

anon_vma’s interval tree (rb).

⚙️ Functions & Flow
1. anon_vma_prepare(vma)
int anon_vma_prepare(struct vm_area_struct *vma) {
    if (likely(vma->anon_vma))
        return 0;
    return __anon_vma_prepare(vma);
}
Ensures the VMA has an anon_vma attached before using it for anonymous folios.

Common case: already present → fast return.

Otherwise, calls __anon_vma_prepare() to allocate/link.

2. __anon_vma_prepare(vma)
Steps:

Allocate a new anon_vma_chain (AVC).

Try to reuse an adjacent VMA’s anon_vma (find_mergeable_anon_vma()).

Saves overhead, avoids proliferation of anon_vma objects.

If none reusable → allocate a fresh anon_vma (anon_vma_alloc()).

anon_vma_alloc() sets:

refcount = 1,

num_children = 0,

num_active_vmas = 0,

root = self,

rb_root = RB_ROOT_CACHED.

Lock anon_vma for write.

Attach VMA to anon_vma:

vma->anon_vma = anon_vma.

Link AVC into both lists (VMA’s list and anon_vma’s rb_root tree).

Increment anon_vma->num_active_vmas.

Release locks.

3. find_mergeable_anon_vma(vma)
Looks at prev and next VMAs (neighbors in vm_area_struct list).

Calls reusable_anon_vma(old, a, b) to test if adjacent VMA’s anon_vma can be shared.

4. reusable_anon_vma(old, a, b)
if (anon_vma_compatible(a, b)) {
    anon_vma = READ_ONCE(old->anon_vma);
    if (anon_vma && list_is_singular(&old->anon_vma_chain))
        return anon_vma;
}
return NULL;
Checks:

Compatibility: anon_vma_compatible() → VMAs are adjacent, same policies (protection, flags).

list_is_singular(): the old VMA must be the only user of its anon_vma, else it’s considered “complex” (already forked/split).

If both true → reuse that anon_vma.

Else → must allocate a new one.

📦 Allocation & Free
AVC allocation:
anon_vma_chain_alloc() → slab-allocates an AVC.
anon_vma_chain_free() → slab-free.

anon_vma allocation:
anon_vma_alloc() → slab-allocates an anon_vma, initializes fields.
anon_vma_ctor() → constructor, sets rwsem, refcount=0, rb_root=RB_ROOT_CACHED.

🔄 Lifecycle Summary
New VMA created (mmap) → no anon_vma attached yet.

First fault into it → anon_vma_prepare() runs: attaches anon_vma, allocates AVC.

Split VMA (mprotect/unmap) → new VMA created, may reuse anon_vma, AVCs linked.

Fork → parent and child VMAs get their own anon_vma objects, with parent/child linkage.

Merge VMAs → allowed only if they share the same anon_vma (checked by is_mergeable_anon_vma()).

Cleanup → if no VMAs remain, anon_vma is freed.

🧑‍💻 Why This Design Matters (FAANG/Arm UK Ready Points)
Scalability:

Folios don’t store VMA lists directly (too costly on fork/split).

Instead, indirection via anon_vma + interval tree.

Efficiency:

Interval tree keyed by folio->index = O(log n) lookup for “which VMA maps this folio”.

rb_subtree_last makes range queries fast.

Correctness:

Fork → parent and child both see COW folios.

Splits/merges handled via flexible AVC linking.

Reuse optimization:

Neighbor VMAs often share the same anon_vma (esp. after mprotect splits).

find_mergeable_anon_vma() avoids allocating new anon_vma unnecessarily.

Locking discipline:

mmap_lock for VMA tree.

anon_vma->rwsem for tree of AVCs.

page_table_lock for page tables.

1. anon_vma_compatible(a, b)
Checks if two VMAs can share the same anon_vma.

Conditions:

Adjacent ranges: a->vm_end == b->vm_start.

Same NUMA memory policy (mpol_equal()).

Same vm_file (either both anonymous or same file with MAP_PRIVATE).

Same flags, except for access flags (VM_READ, VM_WRITE, VM_EXEC) and VM_SOFTDIRTY.

Matching offsets: b->vm_pgoff = a->vm_pgoff + (b->vm_start - a->vm_start)>>PAGE_SHIFT.

👉 If all true, VMAs are mergeable for reverse mapping.

2. Extra Merge Constraint (commit do9ef1578f2)
Adjacent VMA must not already have multiple anon_vma_chain entries.

Why? Because if it’s from a forked child, merging would tangle the hierarchy.

This guarantees: if two VMAs share the same anon_vma, they will share exactly one AVC.

3. anon_vma_chain_link(vma, avc, anon_vma)
Attaches a VMA to an anon_vma via an AVC.

Steps:

avc->vma = vma.

avc->anon_vma = anon_vma.

Add AVC to VMA’s anon_vma_chain list.

Insert AVC into anon_vma’s red-black interval tree.

👉 After this, folio→anon_vma→AVC→VMA reverse lookup works.

4. anon_vma_clone(dst, src)
Copies all anon_vma links from a source VMA into a destination VMA.

Used during:

VMA split

VMA merge

Fork (anon_vma_fork)

mremap, copy_vma, etc.

Optimisation: reuses an existing anon_vma if:

It has no other VMAs,

Only one child,

And num_active_vmas == 0.

👉 Prevents endless chains of anon_vmas when forking repeatedly.

5. anon_vma_fork(vma, pvma)
Called when a process forks.

Steps:

If parent has no anon_vma → nothing to do.

Clear child’s vma->anon_vma.

Clone parent’s anon_vmas into child (anon_vma_clone).

If existing anon_vma reused → done.

Else:

Allocate new anon_vma (anon_vma_alloc).

Point it to parent’s root and parent.

Add reference to root.

Link via new AVC (anon_vma_chain_link).

Increment parent->num_children.

👉 This ensures COW pages can be found in both parent and child during reclaim/unmap.

6. anon_vma_interval_tree_pre_update_vma(vma) / post_update_vma(vma)
Used when VMA’s boundaries (vm_start, vm_end, vm_pgoff) change (e.g. mprotect, mremap).

Pre-update: remove AVCs from interval tree.

Update VMA fields.

Post-update: reinsert AVCs with new ranges.

👉 Maintains correctness of interval tree lookups.

7. anon_vma_merge(vma, next)
Used when two adjacent VMAs can be merged.

Preconditions checked by is_mergeable_anon_vma().

Action: simply unlink absorbed VMA’s AVCs (unlink_anon_vmas(next)), because they both point to the same anon_vma.

8. is_mergeable_anon_vma(anon_vma1, anon_vma2, vma)
Checks if two VMAs’ anon_vmas can be merged.

If either anon_vma is NULL, or VMA has only one anon_vma_chain → merge allowed.

Else, both anon_vma pointers must be equal.

👉 Prevents merging across forked hierarchies.

9. page_add_new_anon_rmap(page, vma, address)
Called when a new anonymous page is faulted in.

Since the page is fresh:

It’s assumed mapped only once, so no need for refcount test.

Compare to &init_mm — if the CPU is currently running with the kernel’s init_mm (the special kernel address space), we do not enter lazy mode and return immediately.

this_cpu_write(...is_lazy, true) — otherwise set the per-CPU is_lazy flag to true, marking that this CPU is now in lazy TLB mode (i.e. the kernel thread intends to “borrow” the user mm without doing a full context switch / TLB reload).

Why the init_mm check?
init_mm denotes the kernel’s master address space (used when a CPU is not running a user mm).

If the CPU already uses init_mm, there’s no point marking is_lazy — lazy mode only makes sense when the CPU has a user mm loaded that a kernel thread intends to borrow.

Also avoids confusing the tracking logic: lazy mode semantics assume a user mm is loaded.

What lazy TLB mode actually means
Kernel threads can run while the TLB still contains translations for a user address space instead of doing an expensive switch_mm() which would reload CR3 and flush TLBs.

is_lazy = true signals other TLB/shootdown logic: this CPU may be holding references to a user mm without having done a proper context switch.

It’s an optimization to avoid repeated context-switch/TLB overhead when the kernel thread will shortly return to the same user context.

Important side effects & safety
Possible corrupted kernel-mode TLB entries: because the kernel is running without reloading the kernel page tables, stale user-page translations might be present and sometimes used in kernel mode — this can look like spurious faults. The kernel expects this and handles them (e.g. spurious_kernel_fault() and other architecture-specific handlers).

Why that’s tolerable: kernel code knows how to handle these rare transient faults; the optimization trades occasional handled faults for frequent avoided TLB reloads.

Per-CPU flag: the flag is per-CPU, so correctness depends on per-CPU state being read/written atomically for that CPU (no global lock needed for the flag itself).

How we leave lazy mode
The book says: leaving lazy TLB mode is done in switch_mm_irqs_off() (the normal code path used when we must guarantee the CPU no longer references the old user mm).

switch_mm_irqs_off() will:

Ensure preemption/IRQs are off,

Perform the necessary switch_mm()-type work (CR3 reload, TLB control), and

Clear is_lazy so future TLB logic knows the CPU is up-to-date.

In other words: enter_lazy_tlb is a short-lived hint; the regular scheduler/ctx-switch machinery eventually clears it safely.

When/where to use it
Used by kernel code paths that want to run briefly in kernel mode while keeping the currently loaded user mm intact (e.g. certain syscalls, short work that doesn’t need full mm switch).

Not used when the kernel must guarantee no stale user mappings exist (e.g. before freeing page tables, certain unmaps, or when doing sensitive TLB shootdowns).
