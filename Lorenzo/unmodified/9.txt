📌 Linux Page Cache & VFS — Simplified but Detailed
1. Why Page Cache Exists
Disk access is much slower than memory:

SSD: ~4× slower

HDD: ~80× slower

To hide this latency, Linux keeps a cache of file contents in RAM → the page cache.

Almost all file accesses go through the page cache (unless explicitly bypassed with direct I/O or DAX).

2. How Page Cache Works
Reads:

Kernel first looks in the page cache.

If page exists → return immediately.

If not → do I/O to fetch from disk → place in cache → process sleeps until ready.

Writes:

MMU can map cached pages as read-only.

When a process writes → page fault occurs → kernel marks page dirty.

Dirty pages are eventually written back to disk (writeback).

Once synced, page is marked clean again.

⚡ Dirty tracking = mechanism to detect and track modified pages.
⚡ Writeback = syncing dirty pages to permanent storage (can be explicit via fsync()/msync()/munmap() or automatic via kernel background threads).

3. Exceptions
tmpfs / hugetlbfs → entirely RAM-backed → page cache is the actual data store.

A disk-backed filesystem could skip dirty tracking, but it would be impractical.

4. Where Page Cache Fits in Kernel
To understand where page cache lives, we need to understand the Virtual File System (VFS) abstraction.

Key Kernel Structures
struct inode

Describes metadata of a file/directory.

Each file has a unique inode number (i_ino).

struct file

Represents an open file descriptor.

Points to inode via f_inode.

Tracks file offset (f_pos), mode (f_mode), etc.

Multiple struct file objects can reference the same inode.

struct address_space

Critical for page cache.

Represents the cache for a given file.

Linked from:

inode->i_mapping

file->f_mapping

Pages (folio->mapping)

struct super_block

Represents a mounted filesystem.

Holds global FS info + list of inodes (s_inodes).

5. Customisation Points (Ops Tables)
Each structure has a table of function pointers so that each filesystem can plug in its own logic:

inode->i_op → struct inode_operations (inode-specific ops).

file->f_op → struct file_operations (file descriptor-level ops).

address_space->a_ops → struct address_space_operations (page cache ops: readpage, writepage, etc.).

super_block->s_op → struct super_operations (filesystem-level ops).

vm_area_struct->vm_ops → struct vm_operations_struct (for memory-mapped files, set during mmap).

6. Summary (Key Flow)
Process opens a file → kernel creates struct file → points to inode (f_inode) + mapping (f_mapping).

File content caching → handled by struct address_space.

Read path: check page cache → if miss, do I/O → populate cache.

Write path: MMU enforces CoW-like protection → page fault on write → mark page dirty → later flushed to disk.

Filesystem glue: different FSs implement custom ops via VFS function tables.

Superblock ties all inodes of a mounted FS together.

✅ So in essence:
The page cache is not just a performance hack, it’s the core buffer layer Linux uses for all file I/O, abstracted via VFS structures (inode, file, address_space, super_block).

📌 Xarray in Linux (Simple but Detailed)
1. What is an Xarray?
Xarray = eXtensible Array → replacement for radix trees.

It maps indices (unsigned long) → to either pointers (e.g. struct page) or values (integers).

Used heavily in page cache (struct address_space->i_pages).

Why Xarray?
Cache-friendly: traversing adjacent indices is fast (better than linked lists/trees).

Expands/contracts efficiently.

Supports:

Lockless reads (via RCU).

Auto-locking on writes.

Mapping ranges of indices.

Marks for fast categorization.

Internal error encoding.

2. Core Structures
struct xarray
struct xarray {
    spinlock_t xa_lock;  // protects writes
    gfp_t xa_flags;      // allocation flags
    void __rcu *xa_head; // root entry: NULL, single entry, or node pointer
};
xa_lock: for writes; reads often use RCU.

xa_head:

NULL → empty.

Single entry → stored directly.

Non-NULL node → pointer to struct xa_node.

struct xa_node
struct xa_node {
    unsigned char shift;     // how many bits this node covers
    unsigned char offset;    // index offset in parent
    unsigned char count;     // non-NULL entries
    unsigned char nr_values; // number of value entries
    struct xa_node __rcu *parent;
    struct xarray *array;
    void __rcu *slots[XA_CHUNK_SIZE]; // 64 slots (x86-64)
    unsigned long tags[XA_MAX_MARKS][XA_MARK_LONGS];
    unsigned long marks[XA_MAX_MARKS][XA_MARK_LONGS];
};
Node = array chunk of 64 slots (on x86-64).

Each slot → value or pointer to another xa_node.

Tree expands dynamically as more indices are used.

shift encodes how many index bits belong to this level.

3. Entry Types
The lowest 2 bits of an entry decide its type:

00 → Pointer entry (to another node).

10 → Internal entry (special markers, errors).

x1 → Value entry / tagged pointer.

Internal entries:
Used for:

Sibling entry (0–62).

Retry entry (256).

Zero entry (257 = represents NULL).

Errors (negative values up to -4095).

4. Helper Functions (from your screenshots)
Value-related
xa_is_value(entry)   // check if entry is a value
xa_to_value(entry)   // extract integer value
xa_mk_value(v)       // create entry from integer
Values = encoded in pointer by shifting and tagging bit 1.

Internal-related
xa_is_internal(entry)  // check if entry is internal
xa_to_internal(entry)  // extract internal value
xa_mk_internal(v)      // create internal entry
Internal entries use tag 2.

Error-related
xa_is_err(entry)  // check if entry encodes an error
xa_err(entry)     // extract errno
Errors are stored as negative values encoded into internal entries.

Node-related
xa_is_node(entry)       // is entry pointing to xa_node?
xa_to_node(entry)       // convert to struct xa_node*
xa_mk_node(node)        // encode xa_node* as entry
Node pointers are tagged as internal.

5. Example Expansion
Start: xa_head = NULL → empty.

Insert one element → stored directly in xa_head.

Insert more → promote xa_head into a struct xa_node with slots.

Each node handles 64 entries; tree grows upward if indices exceed range.

Page cache stores struct page* per index (index = file offset / PAGE_SIZE).

address_space->i_pages = struct xarray.

So:

Key = page index in file.

Value = pointer to struct page.

Efficient lookups, insertions, and writeback tracking rely on xarray.

🔑 Core Idea
When a process accesses a memory-mapped file (mmap()), the kernel may need to fetch data from disk into RAM. This is handled via the page cache and the filemap_fault() path. It ensures:

The faulting virtual address maps to the correct folio (page/block of memory).

Data is loaded (if not already in cache).

Proper locks and races are handled.

Errors (e.g., invalid offsets, truncations, OOM) are gracefully managed.

📍 Step-by-Step Flow
1. Fault Entry (filemap_fault)
Triggered when accessing a file-backed VMA.

Takes the mmap_lock initially (read/write semaphore).

Uses struct vm_fault (details of the fault: address, VMA, offset, flags).

First checks:

Valid offset? (not past end-of-file).

If invalid → send SIGBUS to process.

2. Cache Lookup
Calls filemap_get_folio(mapping, index):

If folio exists in cache → minor fault.

If not → major fault (requires disk I/O).

If found folio:

Check if uptodate (PG_uptodate flag set):

If yes → proceed.

If no → need to explicitly read it (filemap_read_folio()).

3. Read-Ahead
Minor fault case: trigger asynchronous readahead (do_async_mmap_readahead) so future reads are faster.

Major fault case: do synchronous readahead (do_sync_mmap_readahead) — block until at least this folio is fetched.

Caveat: If user set MADV_RANDOM → disables readahead.

4. Locking & Race Handling
After readahead, we lock the folio via lock_folio_maybe_drop_mmap():

Ensures no concurrent writeback/truncation.

Might drop mmap_lock if needed → then retry.

Acquire invalidate_lock (mapping->invalidate_lock) before inserting/allocating folios to avoid races with truncation or invalidation.

5. Folio Creation (if missing)
Calls __filemap_get_folio() with FGP_CREAT:

If folio not in cache, allocate a new one.

Add it to page cache.

Pin with reference count.

If allocation fails → return VM_FAULT_OOM.

6. Post-Processing & Validations
Once folio is locked:

Check truncation (folio->mapping must still match).

Check index validity (not beyond file size).

If invalid → SIGBUS.

Verify uptodate:

If not → go fetch from disk (filemap_read_folio).

If still not possible → retry or fail.

If all good → mark success (VM_FAULT_LOCKED).

⚖️ Error/Edge Cases
SIGBUS vs SIGSEGV:

SIGSEGV: Invalid address (no mapping, no perms).

SIGBUS: Valid but bad file offset (past EOF, truncated, corrupted, or not backed).

VM_FAULT_RETRY: If lock dropped, retry fault path.

VM_FAULT_OOM: Out of memory during folio creation.

VM_FAULT_LOCKED: Success, folio is locked.

📊 Major vs Minor Fault
Major fault: Folio not present at all (needs I/O).

Minor fault: Folio already present but needs mapping/validation.

Counters:

pgfault → all faults.

pgmajfault → major subset.

User-visible via /proc/vmstat, /proc/[pid]/stat, getrusage(), etc.

📌 Flow Summary (Simplified)
Process touches mapped file page → filemap_fault.

Validate offset → else SIGBUS.

Try get folio from cache:

Found + uptodate → done.

Found but not uptodate → fetch from disk.

Not found → allocate folio + read from disk.

Apply readahead optimizations.

Lock folio, check truncation, validity, uptodate.

Return success or error (SIGBUS, OOM, RETRY).

🔹 Suppose process does sequential reads from start:

First page fault → initial readahead (small window, e.g., 4 pages).

Next fault → ondemand_readahead() sees sequential pattern → window doubles: 8 → 16 → 32 (until ra_pages limit).

Async readahead ensures that by the time process touches next page, it’s already cached (avoiding major faults).

If pattern breaks (random seek) → readahead stops.

If readahead misses exceed threshold (MMAP_LOTSAMISS) → disable for that file.

PG_readahead flag marks folio that should trigger next async readahead.

mmap_miss counter tracks failures; capped at 100 × 10.

ra->async_size = quarter of readahead window, used to stagger async fetches.

Alignment logic: order ensures allocation matches hardware IO size.

EOF handling: never readahead past file’s end page.

Deadlock prevention: _GFP_NOFS avoids reclaiming FS pages during allocation.

Starts small,

Expands aggressively if sequential,

Falls back gracefully if random,

Uses markers (PG_readahead, mmap_miss) and history (count_history_pages) to decide future reads,
