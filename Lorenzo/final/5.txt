1) The simplified ELF / process-memory layout (what the diagram shows)
From low → high virtual addresses (typical user process layout):

.text — the executable code. Usually mapped read-only and file-backed (so pages can be shared between processes).

.rodata — read-only data (literal constants).

.data — initialized writable static data.

.bss — zero-initialized static data (uninitialized globals).

Heap — dynamic memory region. Its upper edge is the program break. The heap grows upwards (addresses increase).

(large unmapped gap often left)

Stack — user stack, normally placed near the top of user address space and grows downwards (to lower addresses).

The diagram usually draws an arrow labeled Program break marking the top of the heap.

Key notes:

The program break is a single pointer that separates the process’s data/bss/heap area from the rest of user space. brk() sets it to an absolute address; sbrk() moves it by an offset.

Not everything in a process is a contiguous single region — every mapping (text, data, heap, each mmap) is represented by a VMA (vm_area_struct).

Stack growth is handled lazily by the kernel on page-faults (automatic expansion, if allowed). Heap growth by brk() is explicit (syscall).

2) Two principal ways user apps get dynamic memory
brk() / sbrk() (program break) — single contiguous heap region controlled by the program break. Historically malloc() grew this region to satisfy small allocations.

mmap() (anonymous fileless mappings or file-backed) — creates independent VMA(s). Common for large allocations or file mappings, and used heavily by dynamic loader (shared libraries), mmaped files, and modern malloc for big chunks.

Typical allocator policy (glibc and many allocators):

Small/normal allocations: use the heap (brk).

Large allocations: use mmap(…, MAP_ANONYMOUS, …). This keeps large chunks out of the contiguous heap region to limit fragmentation and make it easy to release them back to the kernel with munmap().

3) Which area does mmap “come from”? (short answer)
No — mmap() is independent of the brk/heap region.
mmap creates a new VMA (or VMAs) at whatever free virtual address the kernel chooses (unless you pass MAP_FIXED). The kernel will avoid overlapping the heap; code in brk() checks for conflicts. So mmap allocations are separate VMAs, not “part of the heap”, though they coexist in the same process address space and the kernel prevents collisions.

4) Does the diagram show kernel + user space, or just user space?
The diagram in your screenshot is a user-space process layout (ELF image + heap + stack).

The kernel has its own code/data and its own mappings; on most architectures the kernel is mapped (in kernel virtual addresses) and is not part of the user .text/.data/.bss/heap/stack picture. Each process has its own user address space (mm_struct + VMAs). The kernel code/data are not duplicated per process (physically shared), but kernel virtual mappings are present in the page tables and are normally in a different address range (and not user accessible).

Important distinction: user mode segments (the ELF segments, heap, stack, mmaped libs) are per-process virtual mappings. The kernel lives elsewhere; its pages are mapped in kernel space (or a separate top-half of the address space), not shown in that user-space diagram.

6) Explaining the helper pieces briefly
mm_struct and vm_area_struct

mm_struct represents a process’s memory manager (its address space). It keeps a list / RB tree of VMAs (mmaped regions), mmap_lock, start_code, end_data, start_brk, brk, etc.

Each region (text, data, a heap VMA, individual mmaped chunk, stack) is a vm_area_struct with vm_start, vm_end, vm_flags. The kernel manages these as an ordered structure (rb-tree + linked list).

mmap_lock

Protects the VMA list and operations that create/destroy/modify VMAs. Writers (write_lock) are used for structural changes; readers (read_lock) for readers. __do_munmap sometimes downgrades a write lock to a read lock internally (e.g., to serialize with operations in a safe manner) — the brk() code handles that possibility.

find_vma(mm, addr)

Finds the first VMA with vm_end > addr (the VMA after addr). Used to detect conflicts.

vm_start_gap(next)

Kernel helper to compute a safe start boundary for a VMA, often leaving a guard page to protect from accidental encroachment (for example to catch stack overflow). The brk() check newbrk + PAGE_SIZE > vm_start_gap(next) ensures an expansion does not collide with the next VMA (even with a one-page guard).

__do_munmap() and do_brk_flags()

__do_munmap() — unmaps pages, may adjust VMA(s), notify userfaultfd, and can change lock state internally.

do_brk_flags() — install new VMA(s) or extend existing heap VMA to cover the requested pages when growing the heap.

The kernel must create/destroy VMAs atomically with proper locking and update page tables.

userfaultfd_unmap_complete()

If userfaultfd was used to monitor page faults in that region, this notifies/unregisters the unmap events so the userfaultfd userspace handler can react.

mm_populate()

If memory is MLocked (process requested pages be resident), the kernel will populate the new mapping immediately to avoid page faults.

7) Concurrency, safety and why brk() is page-aligned
Kernel mappings live at page granularity, so modifying the mapping is done on page boundaries. mm->brk is allowed to be any address within the page, but the mapping changes (new pages or unmapped pages) are done on page boundaries (PAGE_ALIGN).

Small changes inside a page are handled by just updating mm->brk without touching page tables (the if (oldbrk == newbrk) { mm->brk = brk; goto success; } case).

mmap_lock ensures only one thread mutates the address space structure concurrently. __do_munmap may downgrade the lock for internal reasons, so brk() must handle that.

8) Interplay between malloc, brk, and mmap
malloc() implementations historically extend the heap with sbrk() / brk() for small allocations. For large allocations they use mmap() and munmap() so those large blocks can be returned to the kernel quickly.

mmap() allocations are separate VMAs and therefore will not change mm->brk. The brk() code explicitly checks for collisions with existing mmap() areas to avoid overlapping them.

9) Additional related concepts to be aware of
ASLR (Address Space Layout Randomization) — modern systems randomize base addresses of executables/shared libs and stack placement to make attacks harder; PIE executables are relocated via mappings. This affects where .text and other segments appear.

Sharing / copy-on-write — .text (code) pages are commonly shared between processes (same file), .data/.bss are private per process (but may share physical pages until written — COW after fork).

Stack vs heap expansion — stack expansion is triggered by a page fault below the current stack top and uses different mechanics (VMA with VM_GROWSDOWN), while heap expansion is explicit via brk() or implicit via mmap.

Guard pages — kernel often leaves a guard page between heap & next mapping (or between stack and other mappings) to detect overruns.

rlimit differences — RLIMIT_DATA limits how big the data segment (heap) can get; RLIMIT_AS limits total virtual memory; both can influence growth. The brk() code checks the data limit (check_data_rlimit).

10) Summary / TL;DR answers to your two explicit questions
Does mmap come from the heap region?

No. mmap() creates separate VMAs and does not “come from” the brk/heap region. The kernel ensures the heap and mmap regions don’t collide; brk() explicitly checks for nearby mappings and refuses to grow if it would overlap. Allocators use both mechanisms for different purposes (small vs large allocation).

Does the simplified layout cover kernel and userspace both, or do both have separate copies of those sections?

The diagram is user-space process layout (ELF image + heap + stack).

The kernel has its own code/data (kernel .text, .data, etc.) separate from user space. Kernel code is not shown in that diagram. User processes have per-process user segments (each process has its own .data, .bss, heap, stack), while .text pages for an executable or shared libraries can be shared between processes by mapping the same file pages into different processes’ address spaces. In short: user-space segments are per-process virtual mappings; the kernel is separate and mapped into kernel address space (shared physically but different virtual mapping).

11) Practical implications you’ll care about (if you’re working in kernel / drivers / allocator / KGSL)
If you change or inspect brk/heap behavior, remember mmap VMAs are independent — look at find_vma, do_brk_flags, and __do_munmap.

When shrinking the heap, the kernel unmaps pages (and must handle userfaultfd and locking downgrades). That early mm->brk = brk; assignment in the code is intentional (other code may observe it).

When growing, kernel must check rlimits and VMA collisions (to avoid stepping into mmaped memory or stack).

Page alignment and guard pages are important — allocator decisions are heavily influenced by page boundaries and kernel VMA policy.

For debugging: check mm->mmap / mm->mmap_cache / /proc/<pid>/maps to see how the kernel placed VMAs; pmap/vmmap tooling also helps.

examining the userland interface itself in Listing 5.0.2.
void *mmap(void *addr, size_t length, int prot, int flags,
int fd, off_t offset);
The function maps memory into the virtual address space as defined by
these parameters, returning either the page-aligned virtual address of the
mapped region or MAP_FAILED (i.e. (void *)-1), setting errno to the error that
arose.
Examining each of the parameters:
• addr – This is either NULL if the returned address is of no importance
(which is the typical means of invoking this function), or the virtual ad-
dress the mapping should start from.
If the MAP_FIXED flag is set then mapping at this address is a hard require-
ment (and the function will return an error if it cannot map here). Oth-
erwise it is a hint which the kernel will make a best effort to fulfil, but
may not be able to.
All memory mapped by the kernel will be page-aligned, so if a hint ad-
dress is specified which is not, the kernel will page-align it. If MAP_FIXED is
specified and the address is not page-aligned, an error will occur.
• length – The size of the memory to be mapped, in bytes. The actual size
of the mapping will be page-aligned, so this value will be rounded up to
the nearest base page.
• prot – This determines how the memory is intended to be accessed and
maps onto VMA flags. PROT_NONE (set as a single value not a flag) indi-
cates that the memory cannot be accessed at all*, PROT_READ, PROT_WRITE
and PROT_EXEC can be combined to indicate whether the memory can be
read from, written to or executed.
Each of PROT_READ, PROT_WRITE and PROT_EXEC are converted to VM_READ,
VM_WRITE and VM_EXEC respectively via calc_vm_prot_bits().
• flags – These determine the characteristics of the allocation, which we
will examine below.
• fd – If the mapping is anonymous, then this should be set to -1. Oth-
erwise it specifies the file descriptor of the file to be mapped. This file
descriptor can be safely closed after the mapping has been performed.
• offset – This is only meaningful if a file is being mapped and determines
the offset within the file, in bytes, from which to start the mapping. It
must be page-aligned, or an -EINVAL error will be returned. The offset
can be outside of the size of the file at the time it is mapped, as the file
size might change in future rendering the mapping valid. However if the
file is accessed at a time when the offset is invalid a page fault will arise.
Examining each of the possible flags that can be passed in the flags field:
• MAP_PRIVATE – Mutually exclusive with MAP_SHARED. Indicates that a Copy
On Write (COW) mapping should be obtained. This can be used with
both anonymous and file-backed mappings.
Typically this is combined with MAP_ANONYMOUS to indicate that an un-
shared, anonymous mapping is required. However, it can also be spec-
ified for file-backed mappings, in which case it gains very specific seman-
tics – becoming a Copy-on-Write read-only mapping to the underlying
page cache entry.
If this mapping is written to, then the Copy-on-Write triggers and the
mapping behaves as if it were anonymous, only initialised with the con-
tents of the mapped file.
However, if after this pages within the file are truncated (which can occur
if the file is deleted, overwritten or shrunk in size) the anonymous pages
are freed and it reverts back to being a Copy-on-Write page cache map-
ping (triggering SIGBUS if data does not exist in the file at the accessed
page).
See section 6.6 for more details on how this functions.
• MAP_SHARED – Indicates that more than one process might map the same
underlying physical memory. This can be used both with anonymous
and file-backed mappings, with the latter meaning that each process
which maps the same file also maps the same page cache pages.
Shared anonymous memory is useful for sharing memory between
forked processes, as it prevents the mapping from adopting Copy-on-
Write semantics. Behind the scenes, the memory is actually mapped
as an deleted copy of /dev/zero effectively residing in tmpfs (setup via
shmem_zero_setup()), however for all intents and purposes it is an anony-
mous mapping.
• MAP_SHARED_VALIDATE – The MAP_SHARED flag, for legacy compatibility rea-
sons, does not confirm that the flags parameter contains only valid
flags. If this needs to checked, use MAP_SHARED_VALIDATE instead.
• MAP_ANON/MAP_ANONYMOUS – Indicates that the underlying mapping should
be backed by RAM only and when faulted in, physical memory should
be allocated to back it.
• MAP_POPULATE – Fault in the mapped memory immediately using the
kernel’s GUP functionality (see section 8.1.2). This invokes the
mm_populate() function (and __mm_populate() in turn). Note that this fault-
ing in is best effort, if an error occurs during faulting it is ignored, there
fore it is possible that memory mapped this way may still result in page
faults.
• MAP_FIXED – Indicates that the addr parameter is not a hint but rather a
hard requirement. The specified address must be suitable for a virtual
mapping for the architecture, which typically means it must be page-
aligned, failure to do so will result in an error.
It’s important to note that this flag will cause mmap() to unmap any map-
pings which already exist at the specified address, so this is a rather dan-
gerous flag to use, and in typical usage should only be used to overwrite
an already existing mapping (perhaps a PROT_NONE mapping) to ensure
mappings are not unexpectedly overwritten.
• MAP_FIXED_NOREPLACE – This is equivalent to the MAP_FIXED flag, only avoid-
ing the dangerous unmapping (i.e. replacing) behaviour, returning an
error if the mapping would do so.
• MAP_GROWSDOWN – Indicates that this mapping is a stack and should
grow downwards (this is a user-defined stack and thus not tied to the
architecture-dependent direction of program stack growth).
Memory mapped this way has the special quality of stacks, which is that
the valid VMA range is not necessarily static. When unmapped mem-
ory below the start of the stack is accessed, rather than a segfault arising,
expand_downwards() is called which extends the start of the VMA to en-
compass the range up to and including the faulting address (see section

Stack expansion is controlled by the RLIMIT_STACK limit which is checked
on page fault, this can be set to being unlimited at which case stack ex-
pansion is limited only by overcommit settings (see section 4.1) and the
RLIMIT_AS and RLIMIT_DATA user-specified limits.
Clashes with other mappings are avoided as the kernel maintains a gap

stack_guard_gap bytes. This can be configured by the kernel command

• MAP_LOCKED – Indicates that all memory faulted in for this mapping should
be mlock()’d (see section 8.2.1 for more on this). This is equivalent to
setting the VM_LOCKED VMA flag.
The purpose of locking memory like this is to prevent it from being re-
claimed or swapped out. This is necessary for regions of memory which
the user requires to remain strictly resident in memory, though doing so
adds memory pressure.
If this flag is specified, then MAP_POPULATE is implied (as checked in
do_mmap()). Since this function ignores any errors which occur when faulting in memory this does not guarantee that further page faults will
not occur.
As the mmap() documentation indicates, if such faulting behaviour is not

Address space is managed in an rbtree of VMAs (each node = one VMA).

Each node stores rb_subtree_gap = the largest free gap in its subtree.

Algorithm (unmapped_area_topdown)
Compute:

high_limit = max_addr - length

low_limit = min_addr + length

Compute gap_start = end of previous VMA (adjusted by stack_guard_gap).

Compute gap_end = start of current VMA (adjusted by stack_guard_gap).

If gap fits length, we found a place.

Else, follow left/right children based on where gaps may exist.

If leaf node reached and no gap found → backtrack up tree, try left subtrees.

If no sufficient gap → return error (-ENOMEM).

🔹 2. VMAs (Virtual Memory Areas)
Per-process structures in mm_struct.

Define contiguous regions of virtual memory with same properties.

Backed by:

anonymous pages (heap, stack),

file mappings (mmap),

special kernel mappings (e.g., /dev/mem).

Managed in:

RB-tree (ordered by address, with subtree max-gap for fast gap search).

Interval tree (for overlap queries, used by reverse mapping).

Operations:

mmap → create/merge new VMA.

munmap → remove/split VMAs.

mprotect, mlock, madvise → may split VMAs.

Merge & split reduce fragmentation, keep trees balanced.

🔹 3. File Cache vs Page Cache
Page cache = kernel-global cache of file data, keyed by (inode, page index).

Implemented with xarray (mapping->i_pages).

Holds struct page* objects.

File cache = colloquial name for the same mechanism.

On read(fd, buf):
Lookup page in page cache.

If not present → allocate, load from disk.

Copy to user buffer.

On mmap(file) + page fault:
Lookup page in page cache via inode->address_space.

Map it into process page tables.

VMA tells kernel where to insert mapping.

👉 Key difference:

read/write don’t need VMAs.

mmap needs VMA to connect file pages to process address space.

🔹 4. mmap vs brk vs read/write
brk/sbrk: grow the heap (contiguous). Used by malloc for small allocs.

mmap: create new VMAs (file-backed or anonymous). Used for large allocs or shared mappings.

read/write: kernel I/O path via page cache, copies to/from user buffers, no new VMA.

🔹 5. userfaultd
Special syscall/fd interface.

Lets user-space handle page faults for VMAs.

Normal kernel: demand paging automatically fetches/allocates.

With userfaultd: kernel pauses faulting thread, delivers event to user-space daemon. Daemon fills page (UFFDIO_COPY / UFFDIO_ZEROPAGE).

Use cases:
Live VM/container migration (pull pages from remote lazily).

Checkpoint/restore (CRIU).

User-space paging (custom DBs, caches).

Debugging (first-touch monitoring).

Caveats:
Performance hit (fault → kernel → user → kernel).

DoS risk if daemon stalls.

Limited support (mostly anon + shmem).

Security safe: kernel enforces boundaries, but daemon bugs can hang processes.

🔹 6. mlock & resident pages
mlock()/mlockall() pins pages in RAM (sets VMA flag VM_LOCKED).

Prevents swap/reclaim.

Resident Set Size (RSS) = pages currently in RAM and mapped.

Useful for crypto, real-time apps, but adds memory pressure.

🔹 7. fd vs VMA vs file
fd (file descriptor) = per-process handle → struct file.

struct file = kernel object (per-open instance). Refcounted.

inode + address_space = underlying file, page cache state (global).

VMA = per-process mapping → describes where in virtual memory that file or anon region is mapped.

Relationships:
Closing fd doesn’t remove VMA (VMA holds ref to struct file).

Multiple processes can mmap the same file → each has its own VMAs, but share the same inode->address_space (so same physical cached pages).

🔹 8. Data structures
Page cache: xarray (mapping->i_pages).

VMAs: rb-tree (mm->mm_rb), interval trees for overlaps.

Buddy allocator: manages free physical pages (power-of-two blocks), not rb-tree.

LRU lists: track active/inactive pages for reclaim.

Writeback queues: track dirty pages to flush.

🔹 9. Gap finding for mmap
Kernel finds free virtual address gaps with augmented rb-tree:

Each VMA node stores rb_subtree_gap (largest hole in subtree).

Search is O(logN), not linear.

For top-down mmap: walk right-first to prefer high addresses.

🔹 10. Security & correctness caveats
File truncation after a MAP_PRIVATE mapping can SIGBUS when accessed.

MAP_FIXED can overwrite existing mappings (dangerous).

MAP_NORESERVE disables commit checks → process may crash later if memory really exhausted.

userfaultd safe but can stall app if daemon doesn’t reply.

Closing fd doesn’t unmap — VMA persists until munmap/exit.

Global (per-file):

inode → address_space → page cache (xarray of struct pages).

Read/write: use page cache directly, no VMA.

userfaultd: special hook where kernel outsources fault handling to user-space.
