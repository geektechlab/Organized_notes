Linux uses a 4- or 5-level page table hierarchy. ( usually 48-bit VA )
	PGD (Page Global Directory) → top level
	P4D (Page 4th Directory) → (only on 5-level paging, otherwise folded away)
	PUD (Page Upper Directory): pmd_offset(pud, addr) → get PMD pointer for an address
	PMD (Page Middle Directory): A page table page containing PTEs, or A large page (huge page mapping, e.g. 2MB on x86_64, 2MB/1GB on ARM). pte_offset_kernel(pmd, addr) → get PTE pointer for an address
	PTE (Page Table Entry) → lowest level, (type: pte_t) points directly to a physical page frame (PFN) in RAM.

Virtual Address (VA): what processes and kernel code see. Continuous ranges per process.

Physical Address (PA): actual DRAM addresses. Discontinuous, limited by hardware.

MMU + page tables = VA → PA mapping.

Kernel vs User Split
	32-bit x86: usually 3G user / 1G kernel split.
	64-bit: much larger VA, kernel + user mapped into different halves.

Why no direct PA from user? → protection, isolation, prevents buggy/malicious access to kernel/hardware.

PFN (Page Frame Number): index into physical memory, PFN = PA / PAGE_SIZE.

struct page: kernel’s descriptor for every physical page (tracks refcount, flags, mapping).

Virtual Memory Areas (VMAs):
	struct vm_area_struct: describes each contiguous VA region (heap, stack, mmap file).
	Page faults handled via MMU + fault handler.
	mmap() system call → new VMA → filled with pages on demand (faults).

DMA & IOMMU:
	dma_alloc_coherent(): returns DMA-ready buffer (pinned, contiguous).
	dma_map_page(): maps normal page for DMA.
	IOMMU/SMMU: provides devices with IOVA space, stitching scattered PFNs into contiguous virtual ranges.

Fragmentation happens when memory is not efficiently utilized due to the way pages are allocated and freed.
	Internal Fragmentation	Wasted space inside an allocated block due to allocation granularity not matching the request size.	If an app needs 6 KB but the kernel allocates a 4 KB page, it wastes 2 KB.
	External Fragmentation	Memory is available but scattered into smaller chunks that are not contiguous, preventing allocation of a larger block.	Need 2 MB contiguous for THP, but memory is scattered into many 4 KB pages across the zone.

struct page
	every physical page frame in RAM has a corresponding struct page object. This is the metadata, not the memory itself. Stored in a global array mem_map[]. Contains fields like:
		Flags (dirty, referenced, compound, etc.)
		Refcount
		Mapping pointer (which file or anon_vma owns it)
		List pointers (for LRU, free lists, etc.)
	Think of struct page as the “business card” of a physical page — describing what it’s being used for.
	Used historically for everything: anonymous pages, file-backed pages, cache pages, compound (huge) pages, etc.
	Problems with struct page: Hard to handle multi-page blocks (like THP or MTHP) because the kernel still treated each page individually. Performance issues in page cache and I/O.

struct folio:
	Introduced to represent a contiguous block of pages as one logical unit. Reduce overhead when accessing page cache (one lock for multiple pages in a folio). Every folio still has a struct page for the head and tail pages internally. THP and MTHP are just special types of compound folios. The folio abstraction simplifies managing these multi-page units without looping over individual struct pages. Every folio is made up of struct pages.
		struct folio	Logical unit for page cache (multi-page aware)	THP, MTHP are compound folios
	Used in:
		File page cache
		Anonymous pages
		Swap and reclaim

Each PTE contains:
	Physical page frame number (PFN)
	Access permissions (R/W, user/supervisor, exec)
	Flags (present, dirty, accessed, cache settings, etc.)

Types of Compound Pages in Linux:
	Basic unit of memory management is a struct page, which represents one physical page frame (usually 4 KB). Generic concept of multiple struct pages glued together to behave as one.
	Transparent Huge Pages (THP):
		Transparent Huge Pages (THP) are special case of compound pages created automatically by kernel, used to automatically back large virtual memory areas with huge pages (like 2 MB or 1 GB pages) for improving TLB efficiency and reduce page fault overhead in user processes (esp. for large memory workloads like databases, ML training).
	HugeTLB Pages:
		Reserved huge pages, allocated explicitly by user-space (mmap() with MAP_HUGETLB). Used in DBs, HPC workloads needing deterministic hugepage allocations.
	High-Order Allocations (e.g., order > 0):
		The buddy allocator can allocate multiple contiguous pages at once (e.g., for DMA, networking). These higher-order allocations are internally represented as compound pages.

Head Page vs Tail Page:
	A compound page is built from multiple struct pages. The first page in that set is the head page storing metadata (refcount, mapping, flags, etc.).and remaining pages are tail pages referencing back to the head page. This lets the kernel track one big object while still having per-4K page granularity when needed (e.g., for splitting). Used for Kernel bookkeeping for compound/THP.

	Tail pages are not independent — they exist only as part of the compound. That’s why all tail pages contain a pointer back to the head. If only the last tail page pointed back, the kernel couldn’t:
		Handle arbitrary page faults inside the hugepage,
		Split compound pages into smaller ones,
		Correctly free/reclaim pages in the middle.

		Example: A 2 MB THP = 512 × 4 KB pages. The first page struct is the head. The other 511 page structs are tails.

Anonymous Page:
	A page not backed by a file on disk. They don’t have a permanent disk "home". Comes from malloc() / brk() / mmap(MAP_ANONYMOUS), i.e., heap or stack allocations. Under memory pressure if evicted, it must be written to swap (not to a file). Tracked via an anon_vma structure so the kernel knows which VMA they belong to.
		Example: process heap, stack, BSS data, non-file mmap, All "normal" process-private memory that isn’t file-mapped.
				int *p = malloc(4096);   // allocated from anon pages
	Anonymous → swap-backed
	Swap space is a special disk (or SSD) area used as a backing store for anonymous pages. Can be:
		Dedicated swap partition: dedicated block device region (common on older Linux setups).
		Swap file (/swapfile) inside a filesystem: regular file marked as swap
	Swap is slow compared to RAM, but prevents OOM.

KSM (Kernel Samepage Merging) pages:
	A Linux feature to deduplicate identical anonymous pages across processes. Runs a background kernel thread ksmd that scans anon pages and merges identical ones into a single physical page (marked Copy-on-Write). Widely used in virtualization for multiple VMs running the same OS may have many identical libc pages. If one process writes, the page is copied (like COW fork). KSM pages are still anonymous pages, but with extra sharing/deduplication.

File-Backed Memory:
	Memory that comes from a file mapping. If evicted, the kernel can drop the page and reload from the file (no need for swap).
		Example: mmap("/usr/lib/libc.so") → file-backed mapping of a shared library. Memory-mapped files (mmap with file descriptor).
	File-backed → file/disk-backed

When RAM is full:
	File-backed pages → can be dropped and later reloaded from the file.
	Anonymous pages → must be written to swap space to free RAM.

File-Backed Pages:
	Pages that map to a file on disk. If evicted → kernel can drop them and reload later from disk (no need for swap).
		Examples: shared libraries, executables, memory-mapped files.
	Metadata: struct page->mapping = address_space (file’s cache).

Page Cache:
	A cache of file-backed pages in RAM. At read() a file, the kernel keeps its pages in memory so subsequent reads are fast. At write(), the kernel writes to the page cache first, and syncs to disk later. Found in /proc/meminfo as Cached. Optimizes file I/O by avoiding frequent disk access. These are pages cached in RAM when you read() or mmap() a file. Stored in the kernel’s page cache for faster access.
	Example:
		reading /etc/passwd → contents sit in page cache.
		int fd = open("file.txt");
		read(fd, buf, 4096);
	The file’s block is read from disk into a page cache page in RAM. If evicted → kernel can just discard it, and later reload from disk. Their struct page->mapping points to an address_space (file’s page cache metadata).

	The page cache is the actual data in RAM. There’s no “duplicate” copy of the file unless you explicitly copy it (e.g., memcpy into a buffer).
		Say process loads libm.so:
			Page fault occurs on first access.
			Kernel sees mapping → it’s file-backed.
			Kernel checks page cache:
				If not present, allocate a physical page from buddy → read file block from disk into that page.
				Insert it into the file’s page cache (address_space mapping).
				Process PTE now points to this page.
				CPU executes directly from this page in RAM.
		So:
			Disk copy = permanent storage on SSD/HDD.
			Page cache = in-RAM copy of only the parts you’ve touched (demand paging).
			No extra hidden duplicate — page cache is the working copy in RAM.

File-backed page = any page mapped from a file.
Page cache page = the actual cached physical page holding that file’s content.

If you have 10 processes mapping libc.so:
		There is 1 page cache page (per file offset).
		There are 10 file-backed pages (virtual mappings → PTEs) pointing to that single page cache page.
	File-backed page = virtual mapping (VMA+PTE)
	Page cache page = physical backing (struct page, RAM)

Pinned page
	A page that cannot be moved or reclaimed while in use.
		Example: DMA buffers handed directly to hardware, mlock’ed memory, kernel pages with direct hardware mappings.
	Pinned = non-migratable + non-swappable.

Swappable page
	A page that can be evicted to swap/zram if memory pressure rises.
	Typical: anonymous pages (heap, stack).
	Swappable pages must be migratable first, because swapping out is just a form of migration (from RAM → swap disk/zram).

Anonymous mapping
	Created by:
		mmap(MAP_ANONYMOUS | MAP_PRIVATE, …)
		brk() (via malloc, heap growth)
		Thread stacks
	No file backing → pages are “anonymous” (not tied to an inode).
	On first access (fault), they are allocated as zeroed pages.
	If swapped, they go to swap/zram, not to disk file.
	Eligible for THP/MTHP promotion.

File-backed mapping
	Created by:
		mmap(fd, …) on a real file
		ELF program text/data (mapped by loader)
		Backed by page cache of the file.
	Clean file pages can be dropped and reloaded from storage.
	Dirty pages → written back to file before eviction.
	Sharing across processes is easy: same file mapping → same page cache pages.

tmpfs
	A special filesystem: “temporary file storage in RAM”.
	Mounted usually on /dev/shm, /tmp (depending on distro).
	Backing:
		Uses shmem (shared memory) API in kernel.
		Backed by swap for overflow — so data persists until swap runs out.
	Behavior:
		Files look like real files (open, read, write).
		Contents live in RAM (page cache), but evict to swap when needed.
	Use cases:
		Fast temporary files
		IPC (via memfd_create, shm_open)
		Backing store for posix_shm and /dev/shm
	tmpfs/shmem also uses page cache pages, but instead of being tied to a disk file, they are tied to an in-RAM pseudo-file. That’s why tmpfs files can swap: the page cache entries are backed by swap when evicted.
	Created by:
		shm_open()
		memfd_create()
		/dev/shm usage
		tmpfs mounts (/tmp, /dev/shm)
	Pages are file-backed (inode exists), but since there’s no disk, they go to swap if evicted.

shmem (shared memory filesystem API)
	shmem = the internal kernel implementation that powers tmpfs.
	tmpfs is essentially a user-visible mount of shmem.
	Key details:
		Each file in tmpfs → inode → address_space → page cache pages.
		If memory pressure hits → shmem pages can go to swap/zram.
	Used for:
		IPC (shmget, shm_open)
		Anonymous memfd_create() buffers
		Backing store for System V shared memory

tmpfs vs shmem:
	tmpfs = filesystem wrapper you mount.
	shmem = kernel’s memory-backed file subsystem that tmpfs uses.

Slab Cache:
	Kernel often allocates many small objects (task_struct, inode, dentry, etc.). Slab allocator keeps caches of frequently used kernel objects to avoid repeated allocation/free overhead. Found in /proc/slabinfo. Improves performance of kernel internal allocations.

VFS (Virtual Filesystem) Cache:
	Maintains metadata caches:
		Dentry cache → directory entry objects
		Inode cache → file inode structures
	These caches live on top of the slab allocator (they are actually slab caches of dentry/inode objects). They speed up pathname lookups (open("/usr/bin/ls") doesn’t walk the disk every time, it reuses cached dentries/inodes).

Movable pages:
	A kernel concept to allow page migration/compaction. Needed because long-lived kernel allocations can cause physical memory fragmentation.

Linux splits zones into:
	ZONE_NORMAL: contains unmovable allocations (kernel data, page tables, etc.).
	ZONE_MOVABLE: contains pages that can be relocated elsewhere. It is not not a new kind of page, but a policy designation saying the page can be migrated if needed.
		Types of pages considered movable:
			User-space anonymous pages
			Page cache pages
		Kernel tries to place movable pages in ZONE_MOVABLE so compaction can free up big contiguous ranges (for hugepages, DMA, etc.).

All KSM pages are anon, but not all anon pages are KSM.
Many anon/page-cache pages are movable, but kernel-core pages are not.
"Anon", "Movable", "KSM" are orthogonal concepts: one is type, one is policy, one is optimization.

Page Migration:
It is the process of moving a page from one physical location to another while preserving its virtual mapping.
		Scenario				Why Migration Happens
		NUMA balancing			Move hot pages closer to the CPU accessing them (NUMA locality).
		Memory compaction		Rearrange pages to create contiguous free memory blocks for THP, CMA, or device DMA.
		Hot-remove memory		When offlining a memory block (like removing a DIMM).
		Tiered memory systems	Move pages between fast DRAM and slower persistent memory tiers.
	Mechanism:
		Uses migrate_pages() internally. Migrated page retains the same virtual address and page->mapping association. Page locks and reference counts ensure consistency during migration.
	Migratable pages:
		Anonymous pages
		File-backed page cache pages
		HugePages (static and THP, though THPs are first split)
		ZRAM-backed anonymous pages (indirectly when swapped in/out)

Migratable pages
	moving a physical page’s contents to a new physical page, then updating page tables and metadata.
		Anonymous pages: Heap, stack, BSS, malloc allocations.
		Page cache pages (file-backed): Mapped file contents.
		KSM pages (deduplicated anon pages): Migratable since they’re just anon pages with COW semantics.
		Some movable kernel allocations: Allocations explicitly marked movable (e.g., via GFP_MOVABLE).
	Migratable pages can move within the same NUMA node for compaction (to defragment RAM and create contiguous blocks for hugepages/DMA) or across NUMA nodes for NUMA balancing (migrate closer to the CPU accessing it). Or to swap/zram when under memory pressure (but that’s eviction, not migration within RAM).
Non-migratable pages:
	Kernel internal pages: Slab pages holding kernel-critical objects (task_struct, mm_struct, page tables, etc.).
	Allocated with GFP_KERNEL, not movable.
	Pinned pages: Pages locked in memory by DMA, RDMA, mlock(). Migration would break device access.
	Special hardware mappings:Device memory (GPU buffers, MMIO).
	ZONE_DMA or ZONE_DEVICE pages may be unmovable.

ZRAM:
	Compressed swap in RAM. Uses a RAM-backed block device that stores pages in compressed form. Instead of writing anon pages to disk, kernel swaps them into zram (compressed, e.g., LZO, ZSTD).
	Trade-off:
		Saves memory (2–3× effective RAM).
		CPU cost for compression/decompression.
	Widely used in Android phones, embedded devices, VMs where disk swap is slow or unavailable.
	Swap/ZRAM extend RAM capacity for anonymous pages.

Anonymous page = a usage type of a physical page (for private process memory).
Page cache page = a usage type of a physical page (for file-backed memory).
struct page = the data structure that tracks any physical page, regardless of use.

Pinned Pages:
	Pages that cannot be migrated or swapped because they’re locked.
		Examples: mlock(), DMA buffers, GPU buffers.

Swap Cache Pages
	Temporary state when anonymous pages are swapped out. A page in RAM but also has a copy in swap space and tracked in the swap cache until eviction completes.

Swap vs ZRAM
	Feature				Swap Space (Disk/SSD)				ZRAM (RAM Compression)
	Location			Disk or NVMe/SSD					Consumes precious RAM (compressed)
	Performance			Slower (I/O-bound)					Faster (CPU-bound compression)
	Use case			Large swap space					Faster reclaim, embedded/low-memory systems
	Page types			Anonymous pages (non-file-backed)	Same (anonymous pages)
	THP/MTHP support	THP must be split before swapping	Same: split, compress

Swapping – The Classic Mechanism
	Purpose: Free up physical RAM by moving inactive pages to swap space on storage (HDD/SSD).
	How it works:
		When RAM pressure increases, kswapd or direct reclaim moves pages to the swap area.
		When a process accesses a swapped-out page, it causes a major page fault, and the page is brought back to RAM.
	Characteristics:
		Slow (limited by storage latency, especially on HDDs).
		Can handle large datasets if enough disk space is available.
		Swapped pages are stored uncompressed unless combined with compression tools.
	Use zram first for fast compressed swap → fallback to disk swap for large workloads.
ZRAM – Compressed In-Memory Swap
	Purpose: Create a compressed swap device in RAM to reduce pressure without using disk I/O.
	How it works:
		ZRAM creates a block device in RAM.
		Pages are compressed (using algorithms like LZO, LZ4, ZSTD) and stored there.
		When accessed, they are decompressed back into RAM.
	Characteristics:
		Much faster than disk-based swap.
		Reduces pressure but still uses some physical memory for the compressed pages.
		Great for systems without a fast swap disk (like embedded devices, phones, or VMs).
	ZRAM helps compress idle pages and avoid OOM situations efficiently.

Both swap and zram interact with:
	kswapd for reclaim.
	Page fault handler for bringing back pages.
	LRU lists to decide which pages are least active.
	ZRAM can also be tuned via sysfs (e.g., /sys/block/zram0/disksize, /sys/block/zram0/max_comp_streams).

File-backed pages rarely use swap; instead, they are dropped and reloaded from the file system if needed. Anonymous pages (heap, stack, malloc'd memory) are what go to swap/zram.

ZRAM exposes itself as a /dev/zramX block device because the Linux swap subsystem only works on block devices. It is a pseudo-block device driver in RAM:
	Data written to it is compressed and stored in RAM.
	Reads from it decompress and return the data.
Being a block device also allows using zram for other purposes like:
	/tmp storage
	Fast scratch partitions
Internally, it uses genhd block layer API and hooks into the swap layer through swapon.
Compression algorithms (LZO, LZ4, ZSTD) achieve better ratios on larger contiguous memory compared to compressing multiple fragmented 4K pages separately. Metadata overhead also reduces when you compress one 64KB page vs sixteen 4KB pages.
	Example:
		Compressing 16×4KB scattered pages → ~50% saving.
		Compressing 1×64KB hugepage → ~65–70% saving due to better pattern detection.

ZRAM vs ZSWAP
	Feature			ZRAM														ZSWAP
	Location		RAM-only compressed block device							In-RAM compression front-end to disk swap
	Usage			Acts as full swap device									Cache for swap pages before writing to disk
	Persistence		Volatile (lost on reboot)									Also volatile
	Speed			Faster (no disk I/O)										Slower if fallback to disk triggers
	Best Use Case	Embedded devices, VMs, low-RAM systems without disk swap	Systems with disk swap that want compression first
	Implementation	Separate device /dev/zramX									Built into swap layer
	Memory Pressure	Eviction drops data (if no backing store)					Eviction writes compressed pages to disk swap

ZSWAP Cache vs Page Cache vs VFS Cache
	Type		What it Holds										Where Used	Key Difference
	Zswap Cache	Compressed swap pages before being written to disk	Swap subsystem	Memory-saving cache to reduce disk writes
	Page Cache	Cached file data (file-backed pages)	FS read/write operations	Speeds up I/O by keeping file data in RAM
	VFS Cache (dentry/inode cache)	Metadata (directory entries, inode structs)	Virtual File System layer	Speeds up path lookups and metadata access
		Important Distinction:
			Page cache is about actual file content.
			VFS cache is about filesystem metadata.
			Zswap cache is about compressed anonymous or file-backed pages waiting for eviction.

Under Memory Pressure:
	Page allocator decides LRU victims.
	Anonymous pages → first try zram/zswap (if configured).
	File-backed pages → dropped if clean (since they can be reloaded from storage).
	If zram fills, system either evicts (discard compressed pages) or falls back to disk swap if configured.
ZRAM is a block driver because swap requires a block device, even if it’s in RAM.

Buddy allocator is kernel-internal and the root supplier of all physical RAM.
Kernel allocators (slab/slub/slob, vmalloc, dma_alloc_*) sit on top of buddy.
Linux memory mgmt ≠ only RAM: it also integrates disk (file-backed pages, swap).

brk, mmap, and malloc Flow
	malloc() in user space doesn’t directly allocate RAM → it asks the kernel for virtual address space via:
		brk() → extend/shrink heap (small allocations).
		mmap() → anonymous mapping (large allocations).
	Userspace malloc → brk/mmap → page fault → buddy.
	Actual physical pages are only allocated on first access → via a page fault.

Page Faults
	A page fault occurs when a process accesses a virtual address that is not currently mapped in its page tables (PTE invalid or missing). The CPU traps → raises a page fault exception (#PF) → kernel’s page fault handler (do_page_fault()) is invoked.
	Handling Path
		CPU raises #PF → enters page_fault() trap handler.
		Kernel locates the VMA (find_vma).
		If invalid (address not in any VMA) → SIGSEGV to process.
		Otherwise, kernel chooses:
			Anonymous fault → handled via do_anonymous_page() or do_cow_fault().
			File-backed fault → handled via do_fault() → filesystem’s ->fault() handler.
		Depending on whether page is in RAM (minor) or must be read in (major), kernel updates PTE.
	Types:
		Minor fault → page already in RAM but not mapped in page table.
			Cause:
				Copy-on-Write (COW) → forked child touches a shared page.
				Lazy malloc() → first access to anon memory after brk/mmap().
				A page from file cache already resident in RAM but not yet mapped into this process.
			Handling:
					Kernel looks up the VMA (via find_vma()).
					Finds that the backing page is already in memory (anon_vma or file page cache).
					Just updates the PTE to point to it (sets present bit, access flags).
					Returns to user.
				No disk I/O involved. Fast (microseconds).
		Major fault → must load from disk/file/swap. Page is not mapped, and the data is not in RAM — must be fetched from disk (swap or file).
			Cause:
				First access to a file-backed page that isn’t cached yet. Anonymous page evicted to swap, now needs to be read back.
			Handling:
					Kernel looks up VMA.
					Determines if it’s file-backed or anonymous.
					Allocates a free page from buddy allocator.
					Issues disk I/O:
						File-backed → read from filesystem into page cache.
						Anon → read from swap area.
					Once page is filled, updates PTE → resume process.
				Disk I/O = slow (microseconds → milliseconds).
	Example
		// Program:
		char *buf = malloc(4096);   // reserves VA only
		buf[0] = 'a';               // MINOR fault (alloc fresh anon page)

		int fd = open("bigfile", O_RDONLY);
		char c = buf2[0];           // MAJOR fault (file page not cached yet)
		char d = buf2[0];           // Next time: no fault (already mapped)
		🔹 Observability
		You can see minor vs major faults via /proc/[pid]/stat fields.

Buddy Allocator
	Core physical memory manager. Splits RAM into power-of-two blocks (order = 0…MAX_ORDER).
		APIs: alloc_pages(), __free_pages().
	Supplies memory to everything: kernel allocators, user mappings, page cache.

Slab/SLUB/SLOB
	Layer on top of buddy for kernel object caching. Pre-caches frequently used objects (task_struct, inode, dentry).
	Variants:
		SLAB → original, heavy metadata.
		SLUB → modern default (simpler, faster).
		SLOB → tiny systems (low memory).

Buddy Allocator Recap (Base Layer)
	Unit: works in powers-of-2 blocks of pages (2^order, order = 0..MAX_ORDER).
	Goal: satisfy requests for physically contiguous pages.
	Free lists: per-order, per-zone.
	Algorithm:
		Alloc:
			Round request up to nearest power-of-2 block.
			If free list empty at that order, split higher-order block into halves (buddies).
			Return one, keep the other.
		Free:
			Check if buddy block free.
			If so, merge into higher-order block.
			Repeat until no merge possible.
	Provides page-level allocation, but inefficient for small objects (structs, kmalloc, kernel objects).
Slab Allocator Family (Built on Buddy)
	Kernel allocates lots of small objects (inodes, dentries, task_struct, sk_buff, etc).
	Buddy gives pages; slab breaks them into caches of fixed-size objects.
	Avoids internal fragmentation and speeds up object reuse (less init/teardown).
		A. Slab (Original)
			Idea: allocate a page (or multiple pages) from buddy, carve into objects.
			Data structures:
				kmem_cache: describes a cache for a specific object type.
				Each cache has slabs: contiguous pages split into equal objects.
				Each slab has 3 lists: full, partial, empty.
			Algorithm:
			Alloc:
				Find a cache for requested size.
				If a partial slab exists → use free object.
				Else, allocate new slab (from buddy), carve into objects.
			Free:
				Return object to slab’s free list.
				If slab empty → return to buddy (optional).
			Pros: object coloring, cache hotness, great for SMP.
			Cons: high metadata overhead, complexity.
		B. SLUB (Default in modern kernels)
			Simplification of SLAB (no queues of slabs).
			Each kmem_cache holds objects directly inside pages.
			Data structures:
				struct kmem_cache: describes object size, alignment, flags.
				Each CPU has per-CPU freelist for fast allocation.
				Pages contain metadata (struct page) describing used/free objects.
			Algorithm:
				Alloc:
					Check per-CPU freelist → O(1).
					If empty, fetch a new page from buddy, split into objects, refill freelist.
				Free:
					Return object to freelist.
					If whole page free → return to buddy.
			Pros: less fragmentation, lockless fast path, simpler.
			Cons: no object coloring, but mitigated with cache alignment.
		C. SLOB (Embedded/Minimal Systems)
			Simplest slab allocator, optimized for low-memory embedded.
			Works like a simple linked-list allocator (like malloc).
			Data structures:
				slob_block: header with size, next pointer.
				Free list: singly linked, first-fit allocation.
			Algorithm:
				Alloc:
					Walk free list.
					If block big enough, split and return.
					If none found, allocate a new page from buddy.
				Free:
					Insert block back into free list.
					Merge adjacent blocks if possible.
			Pros: tiny overhead, simple.
			Cons: fragmentation, poor scalability, slower.

[ Buddy Allocator ]
    └── Allocates pages (2^order)
        ├── SLAB → per-cache object slabs, full/partial/empty lists
        ├── SLUB → per-CPU freelists, object metadata in struct page
        └── SLOB → first-fit heap within pages
Buddy ensures physical contiguity and merges/freeing. Slab family ensures efficient small-object allocation.

Fragmentation:
	Internal: slab/SLUB alignments waste some bytes per object.
	External: SLOB worst, SLUB better.
SLUB: modern default, fast, simple.

2) SLUB internals (default on most modern kernels)
Data structures (simplified)
	struct kmem_cache — describes an object type/size (e.g., kmalloc-128 cache)
	Per-CPU state:
		c->freelist — single-linked list of free objects for the current CPU
		c->page — the current slab page source for this CPU
		c->partial — small per-CPU cache of partially used pages (optional)
	Per-node:
		n->partial — node-wide list of partially used pages (shared)
		Freelist encoding: SLUB stores the next-pointer inside the freed object itself (tiny header) to avoid extra metadata.
	Allocation fast path (O(1), no locks)
		kmalloc(128)  →  pick kmalloc-128 cache  →  per-CPU freelist ?
			yes → pop one pointer → return
			no  → slowpath
	Slowpath (high level)
		If c->page exists but freelist empty → refill from that page’s free objects
		Else try per-CPU partial → install as c->page
		Else try node partial list (locked)
		Else allocate new slab page(s) from buddy (order chosen by SLUB for packing)
		Carve into objects, build freelist, return one
	Free path
		If freed on the same CPU and page is c->page → push into c->freelist (lockless)
		If different CPU or page not current → put object back in page freelist with minimal locking; if page becomes empty, it may be returned to buddy
	Debug / features that change behavior
		slub_debug (redzones, poisoning, sanity checks)
		SLAB_TYPESAFE_BY_RCU (RCU rules for reuse)
		memcg slab accounting (per-cgroup caches)
		cpu_partial: batching of partial pages to avoid contention
3) SLAB internals (classic)
	Data structures
		kmem_cache: object type/size
		Per-CPU magazine (kmem_cache_cpu): a small array of free objects for fast, lockless alloc/free
		Per-node (kmem_cache_node) lists of slab pages:
			full — no free objects
			partial— some free
			free/empty — all free
	Allocation
		kmalloc(128) → find size cache
		  per-CPU magazine has free? → pop → return
		  else: refill magazine from node’s partial list (lock)
				if none: allocate new slab from buddy, carve objects,
						 move to partial, fill magazine, return
	Free
		If per-CPU magazine not full → push there (lockless)
			Else return object to its slab’s free list (lock); move slab between lists if state changes; if slab empty, may return pages to buddy
	Pros/cons: good scalability in its time; more metadata and list management than SLUB, more locks on hot paths.
4) SLOB internals (tiny systems)
	Treats each page as a mini-heap with a first-fit free list (slob_block)
			Allocate: walk list, split block if large enough; O(N)
			Free: insert back; coalesce adjacent free blocks
		Requests new page from buddy if no fit
		Smallest overhead, worst scalability/fragmentation; used mainly on very small embedded builds

5) What happens on kmalloc(128, GFP_KERNEL) — practical step-by-step
Assume SLUB, CPU 3, NUMA node 0:
	A) Warm fast path
		The request is mapped to kmalloc-128 cache (power-of-two size class, alignment guaranteed)
		SLUB checks per-CPU freelist → has entries
		Pops one pointer, returns object (no locks, no IRQ disable)
	B) Cold path (no freelist)
		No freelist; check c->page → if present, rebuild freelist from that page
		If not, try per-CPU partial; if empty, try node partial (take lock)
		If none: ask buddy for a new page (often order-0 or order-1 for 128-byte objects)
		SLUB carves the page into 128-byte objects, builds freelist
		Returns one object; keeps the rest on c->freelist
	C) Freeing
		Caller kfree(ptr)
		If its page == c->page and same CPU → push to per-CPU freelist (lockless)
		If that page becomes entirely free, depending on cache policy, it may be put on node partial or returned to buddy
	Under pressure
		A shrinker (for caches that register one) may reclaim unused slabs, moving them to empty and returning pages to buddy.
	Compaction/migration: slab pages are usually unmovable; kernel avoids placing unmovable slabs in movable pageblocks to protect CMA/THP.

	SLUB allocate (fast & slow)
	kmalloc(128)
	  ↓
	find kmalloc-128 cache
	  ↓
	per-CPU freelist ?
	  ├─ yes → pop → return
	  └─ no  → c->page ?  → rebuild freelist → return
				│
				├─ if none → per-CPU partial ? → install as c->page → return
				│
				├─ node partial ? (lock) → install as c->page → return
				│
				└─ buddy alloc new page(s) → carve → set c->page → return
	SLAB allocate
	kmalloc(128)
	  ↓
	per-CPU magazine ?
	  ├─ yes → pop → return
	  └─ no  → refill from node partial (lock)
			   ├─ success → pop → return
			   └─ else → buddy alloc slab page(s) → carve → add to partial
						 → refill magazine → return
	SLOB allocate
	kmalloc(128)
	  ↓
	walk free list (first-fit)
	  ├─ found big block → split → return
	  ├─ found exact fit → return
	  └─ none → buddy alloc new page → add to free list → retry

Example: kmem_cache_create("task_struct", sizeof(struct task_struct), …)
	Each kmalloc-size class (kmalloc-128, kmalloc-256) is itself a slab cache.
Think of slab allocator = factory, slab cache = per-object production line.

Caveats:
	IRQ/softirq context must use GFP_ATOMIC (cannot sleep). If per-CPU freelist empty and buddy cannot instantly satisfy, allocation may fail.
		Example: NAPI RX path: use small kmalloc with GFP_ATOMIC. If you accidentally use GFP_KERNEL, it may sleep → BUG.

	NUMA locality
		kmalloc_node(size, GFP_KERNEL, nid) sticks to a node.
			If node 0 low on memory, SLUB/buddy may fallback to remote node, hurting latency. Watch with perf/numa stats.

	Large kmalloc sizes
		Beyond cache sizes, SLUB calls kmalloc_large/kmalloc_order → buddy high-order pages.
		High order fails under external fragmentation. Prefer kv*alloc (e.g., kvmalloc) which falls back to vmalloc safely.

	Debug options change behavior
		slub_debug=FZP (Free-poison, Redzone, Poison) adds canaries/fills; slows fast path and increases memory footprint—great for catching overflows/use-after-free but not for production perf.

	False sharing & alignment
		Objects that multiple CPUs touch should be __cacheline_aligned/SMP_CACHE_BYTES to avoid ping-pong.
		Misaligned caches can cripple scalability (e.g., per-CPU stats structs).

	Reclaimability
		Many slab caches are unreclaimable; they don’t sit on LRUs. If you over-allocate kmalloc memory, zram/swap won’t help; you can hit OOM even with big file cache available.
		Use shrinkers (e.g., for dentries/inodes) for reclaimable kernel objects.

	CMA/THP interference
		Slab pages are generally unmovable, so if the kernel places too many slab pages in movable pageblocks, later CMA/THP allocations can fail. This is why pageblock migration types matter.

	Remote free contention (SLUB)
		Freeing objects from a CPU different than the one that owns the page induces locking. Hot cross-CPU frees (e.g., networking RX/TX recycling) can cause contention; batching helps.

	Constructors & cache init
		kmem_cache_create(..., ctor) runs a ctor per object when a slab is first created (not per allocation). Don’t put runtime state there; it’s for one-time layout/init only.

	Zeroing vs non-zeroing
		kzalloc zeroes the object (costly). Prefer kmem_cache_zalloc for a dedicated cache that expects zeroed objects, or avoid zeroing if you overwrite fully.

	How SLAB/SLUB/SLOB interact with the rest we discussed
		They serve kernel objects only. User memory (heap, stacks, file maps) is managed as anonymous/file pages, not via slab.

GFP Flag Cheatsheet
	GFP_KERNEL: default, may sleep. Use in process context.
	GFP_ATOMIC: non-sleeping (IRQ/softirq/NAPI). Smaller success window.
	GFP_NOWAIT: do not sleep; fail fast.
	GFP_HIGHUSER/GFP_HIGHUSER_MOVABLE: user pages, movable preferred.
	__GFP_ZERO: zero-fill pages (use kzalloc/vzalloc).
	__GFP_NOFAIL: avoid if possible; must handle stalls. Prefer retries/backoff.
	__GFP_COMP: create compound page for higher-order allocations.

PID and TGID
	PID = Process ID → unique identifier in kernel for every thread.
	TGID = Thread Group ID → shared by all threads in a process (in userspace terms, "process ID").
	Example:
		$ getpid() = 1234   // PID of thread
		$ gettid() = 1234   // main thread has same PID & TGID
		$ pthread_create()  // new thread
		getpid() = 1234     // TGID = 1234 (process ID)
		gettid() = 1235     // PID = 1235 (new thread’s ID)
	Each thread (task_struct) points to the same mm_struct if they share address space. mm_struct contains page tables, VMAs, etc. → so memory management is per TGID (process), not per PID (thread).
	TGID is the "owner" of the address space, while PID is per-thread execution context.

File Descriptors (fd)
	fd = integer handle representing an open file within a process. Backed by kernel object struct file. FDs are stored in the per-process file descriptor table (files_struct).
	File-backed mmap():
		int fd = open("data.bin", O_RDONLY);
		void *p = mmap(NULL, size, PROT_READ, MAP_SHARED, fd, 0);
	Here fd ties your process memory to the underlying file. The kernel uses struct file → address_space to fetch pages into the page cache when faults occur. So fd is the gateway to file-backed memory mappings.
		Anonymous memory → no fd.
		If you call mmap(MAP_ANONYMOUS), kernel doesn’t need struct file.

ioctl (Input/Output Control)
	ioctl(fd, cmd, arg) = user → kernel control channel. Not about raw read/write, but about controlling kernel objects. GPU, DMA, or /dev/mem can use ioctl to allocate or map special memory.
		E.g. DRM (GPU driver) uses ioctl to allocate buffers, then mmap() them into process VA.

Static Huge Pages / Reserved Huge Pages (hugetlb/hugetlbfs):
	Static huge pages are manually reserved and pinned huge pages in memory. They do not get allocated or freed automatically by the kernel.
		Size: Usually 2 MB (huge page) or 1 GB (gigantic page), depending on the architecture.
	Controlled via:
		/proc/sys/vm/nr_hugepages
		/sys/kernel/mm/hugepages/hugepages-*/
	Databases like Oracle, PostgreSQL, MySQL, or DPDK (for high-performance packet processing) that need deterministic performance and no risk of memory fragmentation. Memory regions that need to be locked in RAM without kernel reclaim. Cannot grow/shrink automatically. Pages are reserved at boot or manually added, preventing fragmentation issues. Low runtime overhead — pinned and fixed
		mmap() large buffers for DPDK or high-frequency trading systems.
	Example:
		int fd = open("/mnt/huge/myfile", O_CREAT | O_RDWR, 0755);
		void *addr = mmap(NULL, 2*1024*1024, PROT_READ | PROT_WRITE,
					  MAP_SHARED, fd, 0);
	Not swappable and not reclaimed by the usual LRU reclaim path. Essentially pinned/reserved from a hugetlb pool; pressure elsewhere won’t free them. When freed by the app, they return to the hugetlb pool, not the general LRU.
	Designed to avoid runtime fragmentation by reserving huge pages early (boot or runtime increase of nr_hugepages). Gigantic pages (1 GiB) often must be reserved at boot. Uses a dedicated MIGRATE_HUGETLB pool.
	Hugetlb: pages are carved out of the buddy into the hugetlb pool (per-node). The pool uses its own free lists (pageblocks tagged MIGRATE_HUGETLB).
	Typically mapped via hugetlbfs (looks “file-backed” in API), but not the normal page cache; it uses the hugetlb pool, not generic VFS page cache machinery.
	1 GiB optional for gigantic pages	Matches CPU hardware page sizes supported by the MMU (4 KiB base, 2 MiB huge, 1 GiB huge for x86).
	User must pre-allocate a fixed number of pages of a particular size via echo <num> > /proc/sys/vm/nr_hugepages or mount -t hugetlbfs.
	Not swappable, not splittable.

Transparent Huge Pages (THP):
	Transparent Huge Pages are automatically managed huge pages by the kernel. They let applications benefit from huge pages without explicit support.
		Default size: 2 MB huge pages (not 1 GB by default).
	Kernel tries to coalesce adjacent 4 KB pages into a 2 MB THP when possible. Can be enabled/disabled:
		cat /sys/kernel/mm/transparent_hugepage/enabled
	Modes: always, madvise, never.
	General-purpose workloads like JVM apps, Redis, or large in-memory analytics workloads. Allocation happens automatically at runtime. Can fail under heavy fragmentation (falls back to 4K pages). Some overhead in background collapsing/khugepaged daemon.
		Example	malloc() → normal mapping → kernel upgrades to THP
	For ease of use with memory-hungry applications that don’t handle memory allocation explicitly. Running big data applications or caching servers.
	Example:
		Just do a normal malloc() or mmap(), and the kernel transparently upgrades regions to 2 MB pages if possible.
	Can be reclaimed like normal anon/file pages. Kernel will often split the THP into 4 KiB pages first for reclaim, migration, mprotect/mremap, partial unmap, writeback quirks, etc., then reclaim/swap those base pages. If anon: can be swapped; if file THP: can be written back or dropped.
	Sensitive to fragmentation. Allocation tries an order-9 (2 MiB) page; if it can’t, khugepaged may collapse adjacent 4 KiB pages later. Memory compaction/migration helps create big contiguous ranges.
	khugepaged is a kernel daemon (kernel thread) that runs in the background when Transparent Huge Pages (THP) are enabled. Runs periodically to find small pages that can be promoted (collapsed) into a huge page.
		Path: /sys/kernel/mm/transparent_hugepage/khugepaged/
		Binary: actually implemented in mm/khugepaged.c
	khugepaged is a background kernel thread responsible for collapsing multiple base pages into Transparent Huge Pages (THPs) to improve TLB efficiency and reduce page table overhead. It scans virtual memory regions (VMAs) that are:
			Anonymous (like heap, stack, malloc() memory)
			Continuous 512 × 4KB pages (for 2MB THP)
			All clean (no dirty mismatches)
			Properly aligned in virtual and physical memory
		Not on-demand: Collapse is lazy and happens in the background, unlike fault-time THP allocation.
	Buddy allocates a high-order page (order 9 for 2 MiB). Anonymous THP typically placed as MOVABLE so they can be migrated/compacted.
	Commonly anonymous; also file THP exists (notably tmpfs/shmem, and increasingly large-folio page cache in some FS). File THP follow page-cache/writeback rules.
	2 MiB is a sweet spot between TLB coverage and manageable memory fragmentation.
	User can override with /sys/kernel/mm/transparent_hugepage/enabled or per-VMA hints using madvise(MADV_HUGEPAGE) or MADV_NOHUGEPAGE.

A shrinker in the kernel is a mechanism used by the memory reclaim subsystem (via shrink_slab() and related APIs) to reclaim memory from caches or subsystems when memory pressure occurs.
	THP shrinker is a specialized shrinker that:
		Scans memory to find idle or underused PMD-sized THPs.
		Splits them into base 4 KB pages when needed.
		Returns those base pages to the buddy allocator for other allocations.
	Location in code:
		mm/huge_memory.c → split_huge_page_to_list() and mm/huge_memory.c → deferred_split_huge_page()
	THP Shrinker Work Flow:
		Memory pressure detected by page reclaim (kswapd, direct reclaim, etc.).
		Shrinkers are called via the shrinker API registered by the THP subsystem.
		The THP shrinker walks through a list of deferred split THPs maintained by the kernel.
		For each candidate:
			Unmaps the huge page temporarily.
			Splits the page into 512 × 4 KB base pages.
			Updates the reverse mapping (rmap) for each process using that page.
			Pages are then reinserted into the LRU lists for reclaim by the usual page reclaim code.
	Why THP Shrinker is Needed
		Under memory pressure, holding memory in huge pages can lead to:
			Fragmentation.
			Wasted memory (unused portions of a 2 MB page remain reserved).
			Shrinking avoids premature OOM kills by freeing memory earlier.
	Interaction with Processes
		When a huge page is split:
			Page table entries of the process are updated to point to base pages.
			No visible effect in user space except a slight latency.
			Process continues to run without knowing its THP was downgraded.
	PMD-level THPs register with the shrinker:
		The deferred split queue keeps track of PMD THPs that can be split.
		khugepaged may also trigger collapses or deferred splits depending on activity.

Zones, LRU, and Migratability
	Zones: THPs are typically allocated from ZONE_NORMAL or ZONE_DMA32 depending on NUMA and architecture.
	LRU lists: Once split, base pages rejoin the LRU inactive or active lists.
	Migration: Split base pages can be migrated like normal pages; PMD THPs need special handling for migration.

“mmap/slab/slub/slob” are not sources of physical memory; they are APIs or allocators layered above. mmap(): establishes virtual mappings; the actual physical frames still come from buddy on fault (THP) or from the hugetlb pool (hugetlb).

SLAB/SLUB/SLOB: kernel object allocators that themselves get base pages from buddy; they don’t supply huge pages for user memory.

mTHP (multi-size THP):
	4 KiB, 64 KiB, 2 MiB, 16 MiB, 1 GiB (depending on architecture and kernel config)	Allows the kernel to pick the largest practical size based on alignment, contiguity, and workload patterns.
	Problem with only 2 MiB THP: Harder to allocate under fragmented memory conditions. For NUMA and mixed workloads, 2 MiB is sometimes too big and wastes memory.
	mTHP: Provides flexible granularity for huge pages — e.g., fallback to 64 KiB or 512 KiB instead of failing THP promotion. mTHP makes more efficient use of fragmented zones because it can choose smaller orders when big contiguous blocks are not available.
	File-backed: Supported for page cache (tmpfs/shmem, some FS)	More efficient support for large folios	Not in generic page cache; separate hugetlbfs
	mTHP integrates more tightly with the large-folio page cache, meaning fewer TLB misses for file-backed mappings without the rigidity of static hugetlb pages.

All draw from ZONE_NORMAL / ZONE_DMA32 / ZONE_MOVABLE depending on policy and NUMA placement.

malloc() → first touch	Allocates 4 KiB; khugepaged promotes to 2 MiB if possible | promotes dynamically to the largest suitable size | Needs explicit mmap with MAP_HUGETLB

For a 4-level page table (most ARM64 configs):
	Level	Name					Typical Size (4 KB base)	Typical Size (64 KB base)
	PGD		Page Global Directory	~512 GiB					~32 TiB
	PUD		Page Upper Directory	~1 GiB						~512 GiB
	PMD		Page Middle Directory	2 MiB (block mapping)		512 MiB (block mapping)
	PTE		Page Table Entry		4 KB						64 KB

	Hugepage size comes from which level of the page table you stop at when creating a "block mapping":
		At PTE level → small page = base page size.
		At PMD level → first "huge page" size (block size).
		At PUD level → even larger page (gigantic page).

	Case 1: 4 KB base page
		Base PTE: 4 KB
		PMD block: 2 MiB (512 entries × 4 KB)
		PUD block: 1 GiB (512 × 2 MiB)
			So hugepage sizes = 2 MiB, 1 GiB

	Case 2: 64 KB base page
		Base PTE: 64 KB
		PMD block: 512 MB (8192 entries × 64 KB)
		PUD block: 16 GB (32 × 512 MB)
			So hugepage sizes = 512 MB, 16 GB

	This is why, when 64 KB is the base page size, the first "huge" block mapping jumps to 512 MB, not 2 MiB. The page table walk size multiplies with the base granularity.

	mTHP tries to bridge this gap by introducing intermediate hugepage sizes using the folio mechanism and order- allocations even if the hardware block size jumps from 64 KB → 512 MB.
	Example: On 64 KB base page system:
		mTHP may use 64 KB × 8 = 512 KB or 64 KB × 32 = 2 MB folios internally.
	Hardware still maps them as 4 KB entries, but reduces kernel overhead and page cache pressure.

	On ARM: CONT bit is used when allocating contiguous physical pages to form these mid-sized transparent hugepages. Without the CONT bit, the hardware treats them as separate pages, losing the TLB optimization.

rw_semaphore:
	The rw_semaphore (read-write semaphore) is heavily used in:
		Memory management (like mmap_sem / mm->mmap_lock)
		Protecting VMAs (Virtual Memory Areas) during:
			Page faults
			THP/MTHP splitting
			Migration
			Swap-in/swap-out
	For example:
		A write lock might be taken during unmapping or remapping operations. A read lock is enough during page fault handling when the VMA is not being modified.

LRU Lists (Least Recently Used):
	Linux uses multiple LRU lists to manage pages for reclaim and swap:
		LRU List		Description
		Active file		Frequently accessed file-backed pages
		Inactive file	Cold file-backed pages (reclaim candidate)
		Active anon		Frequently accessed anonymous pages
		Inactive anon	Cold anonymous pages (can be swapped out)

	For swap:

Kernel Samepage Merging (KSM)
KSM is deduplication, not migration. It scans for anonymous pages with identical content across processes and maps them to the same physical page in a Copy-On-Write (COW) manner.
	Scenario:
		Virtual Machines (KVM/QEMU)	Many guest VMs load identical OS images → saves RAM.
		Forked processes (after fork())	Many identical anonymous regions exist until they diverge.
		Memory deduplication in containers	Reduce footprint when running many similar workloads.
	Mechanism:
		Background thread ksmd scans memory regions marked MADV_MERGEABLE.
		Identifies pages with same checksum → replaces duplicates with a shared read-only page.
		On write, a new private copy is allocated (COW fault).

eBPF (extended Berkeley Packet Filter) is a safe, in-kernel virtual machine that allows you to load and run small programs in kernel space without writing or modifying kernel modules.
	Key properties:
		Runs sandboxed programs inside the kernel.
		Verified for safety (no arbitrary pointer dereferences, bounded loops).
		Allows high-performance, low-latency access to kernel hooks like networking, tracing, and security.
	Common Uses:
		Networking: XDP (eXpress Data Path) for ultra-fast packet filtering, DDOS mitigation.
		Tracing & Profiling: Tools like bpftrace, bcc for performance debugging.
		Security: cgroup-based filtering, seccomp enhancements, LSM hooks.
		Observability: TCP latency analysis, syscall monitoring, etc.

VFIO
	VFIO (Virtual Function I/O) is a kernel framework for user-space drivers to securely and directly access hardware devices using IOMMU protection.
	It provides secure, direct device access for frameworks like DPDK, QEMU, and other virtualization stacks. VFIO ensures isolation so that even if the user-space driver crashes, it doesn't corrupt kernel space or other processes.
		Key traits:
			Provides device isolation with IOMMU mappings.
			Exposes device memory and interrupts to user space safely.
			Used for PCI passthrough in VMs (with QEMU/KVM).

DPDK
	DPDK (Data Plane Development Kit) is a userspace framework for high-performance packet processing. It bypasses the Linux kernel networking stack to achieve line-rate performance. It uses poll mode drivers (PMD) to interact directly with NIC hardware.
		Key traits:
			Runs entirely in userspace.
			Requires hugepages for DMA memory buffers.
			Optimized for low latency, high throughput, e.g., firewalls, load balancers, virtual switches.

The linear map (also called the direct map) is a 1:1 mapping of all physical RAM into a contiguous range of kernel virtual addresses. Implemented in PAGE_OFFSET region. Uses page tables but simple offset arithmetic for translation.
	Characteristics
		Covers all physical RAM.
		Allows kernel to access any physical address quickly.
		Allocations from buddy allocator (e.g., alloc_pages(), __get_free_pages()) live here.

vmalloc:
	vmalloc provides virtually contiguous memory to the kernel, but not physically contiguous.
	It creates separate page table mappings for each page, unlike the linear map where physical pages are contiguous.
	Characteristics
		Feature				Linear Map								vmalloc
		Physical Contiguity	Yes										No
		Virtual Contiguity	Yes										Yes
		TLB Pressure		Low										Higher (extra page table walks)
		Use Case			DMA buffers, page cache, slab allocs	Large allocations for kernel modules, stacks, etc.

CONFIG_UNMAP_KERNEL_AT_EL0:
	This is a kernel configuration option (CONFIG_UNMAP_KERNEL_AT_EL0) mainly for ARM64 (AArch64) architecture.
	It unmaps the kernel's virtual address space when running at EL0 (user mode) to mitigate security vulnerabilities like Meltdown or speculative execution attacks.
	How it works:
		When a process is running in user mode (EL0), the kernel's linear map and kernel VA space are not visible.
		When a syscall, exception, or interrupt occurs (switching to EL1), the kernel mapping is temporarily remapped for handling the event, then unmapped again when returning to user space.

Can a user application see kernel mappings?
	Before CONFIG_UNMAP_KERNEL_AT_EL0: Kernel virtual addresses were mapped but protected by permission bits (cannot read/write from EL0). This allowed speculative execution vulnerabilities to leak data.
	After CONFIG_UNMAP_KERNEL_AT_EL0 (and KPTI on x86): The entire kernel VA space is unmapped while in user mode.	A user process cannot see or guess kernel addresses via normal means.

vDSO (Virtual Dynamic Shared Object):
	vDSO is a small shared library mapped into every user process.
		Purpose: To let user-space execute certain system calls in user space without a full context switch.
	Examples of vDSO usage
		gettimeofday()
		clock_gettime()
		getcpu()
		Instead of switching to kernel mode for every call, the kernel maps a read-only page with relevant code/data at a fixed user VA, improving performance.
			clock_gettime(CLOCK_MONOTONIC, &ts);
				→ Executes entirely in user space via vDSO mapping for speed.
			int fd = open("/proc/kallsyms", O_RDONLY);
				→ Requires root to see real kernel symbol addresses.

Can kernel VA space be mapped into user space?
	Generally, No, for security and isolation reasons:
		Kernel memory is privileged and not directly accessible from EL0.
		The kernel enforces strict page table separation (especially with CONFIG_UNMAP_KERNEL_AT_EL0 and KASLR).
	Exceptions
		Shared memory mechanisms like:
		mmap() with /dev/mem, /proc/kcore, or character devices (if allowed — often restricted)
		DPDK or VFIO can map DMA buffers from kernel to user, but those are controlled, isolated mappings, not arbitrary kernel space.

kallsyms
	/proc/kallsyms lists kernel symbols and their addresses.
	Used for debugging, profiling, or kernel module development.
	However:
		With kptr_restrict=1 or 2, non-root users see 0x00000000... instead of actual addresses for security.
		Even if you see the symbol, you cannot dereference kernel addresses from user space because the mappings are inaccessible under EL0.

KASLR:
	KASLR (Kernel Address Space Layout Randomization) is a security feature that randomizes the location of the kernel and its key structures in virtual memory at boot time. It’s like ASLR for user-space programs but applied to the kernel.
		Randomizes:
			The kernel text/code base
			Modules
			Kernel stacks
			Some key static mappings.
	Why KASLR Exists
		Without randomization:
			Kernel addresses are predictable.
		Exploits like ROP (Return-Oriented Programming) or privilege escalation attacks can jump to known kernel addresses.
	With KASLR:
		Attackers cannot reliably guess addresses without leaking info first.
		Root users can still inspect symbol addresses for debugging or profiling.
		Crash dumps (like kdump) save physical addresses; tools like gdb vmlinux still work by correlating random offsets.
		Impact on Performance:
			Minimal overhead, since randomization happens at boot time only.
			No runtime penalty except in debugging workflows.

CMA — Contiguous Memory Allocator
[ CMA in Memory Management ]
   ├─ Purpose:
   │    • Provides large physically-contiguous regions of memory.
   │    • Needed for DMA-capable hardware (GPU, DSP, multimedia engines).
   │
   ├─ How It Works:
   │    • At boot, reserves a big physically-contiguous memory region
   │      (e.g., 256MB reserved for graphics or camera).
   │    • Pages inside this region can be used by the kernel for normal
   │      allocations **until** a DMA request needs them.
   │    • Uses page migration to free up and compact that region when needed.
   │
   ├─ Relation to Page Types:
   │    • Allocates base pages, but may coalesce into larger compound pages.
   │    • Doesn't directly create THP or static hugepages but can allocate
   │      huge contiguous areas if fragmentation is low.
   │
   ├─ Connection to Migration:
   │    • Relies on the **page migration framework** to move movable pages
   │      out of the reserved CMA region on demand.
   │
   ├─ Connection to Shrinker/OOM:
   │    • If CMA region is fragmented and migration fails → allocation fails.
   │    • Doesn't directly trigger OOM, but failed CMA allocations can
   │      propagate errors to drivers needing contiguous buffers.

	Example Use Cases:
		GPU framebuffers
		Multimedia codecs (video encode/decode)
		DMA engines for networking or ISP pipelines

CMA reduces external fragmentation by reserving a contiguous range upfront.

CMA’s magic is possible only if all pages inside its pool are reclaimable/migratable. If pinned pages or non-movable kernel slabs ever leak into CMA → compaction fails → devices requesting contiguous DMA buffers fail.

CMA pages are designed to be used as fallback for movable allocations and cannot be used for non-movable allocations. If CMA pages are utilized poorly, non-movable allocations may end up getting starved if all regular movable pages are allocated and the only pages left are CMA. Always using CMA pages first creates unacceptable performance problems. As a midway alternative, use CMA pages for certain userspace allocations.
	The userspace pages can be migrated or dropped quickly which giving decent utilization.
		From userspace processes
			(e.g., GEM buffers, Android SurfaceFlinger buffers, camera buffers)
		Easily migratable or drop-able
			(e.g., cached textures, streaming buffers)
	Non-movable allocations (like kernel stacks, page tables, pinned buffers) cannot use CMA memory. Pages allocated from CMA must be migratable, meaning they can be relocated elsewhere if needed (e.g., via page migration or compaction).
		Starvation of Non-Movable Allocations:
			If the system uses too much CMA for buffers (e.g., pinned GEM buffers, large VRAM allocations), the buddy allocator runs out of regular movable pages, starving other parts of the kernel that need non-contiguous memory.

	Linear Map & VA Space: CMA regions live in the linear mapping, ensuring physical ↔ virtual translation is straightforward for DMA

Until a driver requests contiguous memory, CMA’s region can be used temporarily for movable pages (like page cache, anon). If a driver suddenly needs N MB contiguous memory from CMA, the kernel can:
	Migrate those temporary pages (file cache → drop, anon → swap/zram).
	Compact the region, freeing physically contiguous pages.
Thus, CMA memory is flexible:
	In idle times, it’s used like normal RAM (but only for movable pages).
	When a device (GPU, ISP, V4L2 camera, etc.) asks, CMA can reclaim it for contiguous allocations.
Where can they get migrated?
	To any other free page frames outside CMA in the same NUMA node/zone, provided the target pages are available.
	If anon → might be swapped/zram’d.
	If file-backed → can be dropped and reloaded from disk.

CMA is about physical contiguity. It ensures drivers can always get physically contiguous memory regions even under fragmentation by migrating pages out of reserved regions.

DMA-BUF is about buffer sharing. It provides an efficient mechanism for zero-copy sharing between different subsystems, often using CMA-backed memory.

DMA-BUF — Shared Buffer Framework
[ DMA-BUF in Kernel Memory Sharing ]
   ├─ Purpose:
   │    • Framework to share **physically-backed buffers** across multiple
   │      drivers or subsystems (GPU, display, camera, video, etc.)
   │
   ├─ How It Works:
   │    • One driver allocates a buffer (often from CMA or ION).
   │    • Exports a "file descriptor" for that buffer to user space.
   │    • Another driver (e.g., GPU) imports the buffer using the FD.
   │    • Reference counting ensures safe sharing and cleanup.
   │
   ├─ Relationship to CMA:
   │    • Buffers for DMA-BUF often come from CMA because hardware usually
   │      needs contiguous physical memory.
   │
   ├─ Interaction with Page Management:
   │    • The underlying pages can still be migrated **if not pinned**.
   │    • When pinned (for DMA), pages are locked and exempt from reclaim,
   │      compaction, or THP collapse.
   │
   ├─ Performance:
   │    • Avoids expensive copies between subsystems.
   │    • Enables zero-copy pipelines (e.g., camera → ISP → GPU → display).

DMA-BUF buffers are fixed-size and pinned, so THP promotion/demotion is not applicable.
	Shrinker & OOM: DMA-BUF itself doesn’t reclaim memory; buffers stay until explicitly released.
	ZRAM/ZSWAP: DMA-BUF pages are not swappable because they are device-critical.
	Page Cache: DMA-BUF buffers are not part of page cache but are reference-counted like file-backed pages.
	Linear Map & VA Space: DMA-BUF buffers appear in kernel VA but protected from user-space mapping unless specifically mmap’d

Security and Mapping: User-space apps can mmap a DMA-BUF FD into their space, but only for that buffer — not arbitrary kernel VA (CONFIG_UNMAP_KERNEL_AT_EL0 still applies).

PSI (Pressure Stall Information)
	PSI = Pressure Stall Information, a kernel feature that measures how much time tasks spend stalled waiting on CPU, memory, or I/O resources.
		Exposed under /proc/pressure/.
	Why:Not just how much memory/CPU is used, but how much stalling it causes for workloads.
	Files:
		/proc/pressure/cpu
		/proc/pressure/memory
		/proc/pressure/io
	ZRAM/ZSWAP/Swap: High PSI memory values mean tasks are blocked waiting on reclaim/swap-in.
	THP/MTHP: Collapse/compaction overhead increases PSI stalls if fragmentation is high.
	CMA/GEM/DMA-BUF: If large contiguous allocations fail, drivers may stall waiting for migration/compaction → visible in PSI.

CONFIG_IDLE_PAGE_TRACKING
	A kernel config option (CONFIG_IDLE_PAGE_TRACKING) that allows the kernel to track which pages are accessed/idle.
	Useful for performance tuning, NUMA balancing, memory hotplug, and memory tiering (DRAM vs PMEM).
	How it works:
		Provides /sys/kernel/mm/page_idle/bitmap interface.
		Each physical page frame has a bit indicating idle (not accessed recently) or young (accessed).
	Use cases:
		NUMA balancing: Move hot (frequently accessed) pages closer to CPUs.
		Tiered memory systems: Place cold/idle pages on slower memory (NVDIMM/PMEM).
		Page reclamation: Evict idle pages first to minimize performance impact.
		CMA/DMA-BUF interaction: Idle page tracking helps migration by picking pages less likely to be touched during compaction.

HWPoison
	hardware memory error handling.
	When ECC detects an uncorrectable error in a RAM page → kernel marks it poisoned (PG_hwpoison).
	That page is offlined: unmapped from processes, migrated/reclaimed, never reused.
		Exposed via /sys/devices/system/memory/hwpoison/ and madvise(MADV_HWPOISON).
	Used in RAS (Reliability, Availability, Serviceability) subsystems.

KASAN (Kernel Address Sanitizer)
	A runtime memory error detector for the kernel.
	Instruments memory allocations to catch:
		Use-after-free
		Out-of-bounds
		Invalid free
	Implemented by poisoning shadow memory + redzones.
	Variants: KASAN inline, outline, hardware-assisted (HWASAN).
	Heavy overhead; mostly used in debugging builds.

ftrace
	Function Tracer framework in Linux.
	Hooks into almost any kernel function entry/exit.
	Provides APIs (trace_printk, tracepoints, perf, bpf) to trace kernel execution in real time.
	Used for:
		Latency tracking
		Syscall monitoring
		Scheduler tracing
		Lock contention debugging
	Files: /sys/kernel/debug/tracing/*

kernel_panic_notifier and Callbacks
	Kernel has a notifier chain mechanism: modules can register callbacks for events.
	panic_notifier_list = chain for panic events.
	Example: crash dump, watchdog, reboot manager may register.
	Mechanism:
		static int my_panic_cb(struct notifier_block *nb, unsigned long event, void *ptr) {
			printk("panic detected: taking action\n");
			return NOTIFY_DONE;
		}
		static struct notifier_block my_block = { .notifier_call = my_panic_cb };
		register_panic_notifier(&my_block);
	Other notifier chains exist: cpu_notifier, die_notifier, reboot_notifier, etc.
	Helps in custom error handling, logging, failover actions.

The page cache is the actual data in RAM. There’s no “duplicate” copy of the file unless you explicitly copy it (e.g., memcpy into a buffer).
	Say process loads libm.so:
		Page fault occurs on first access.
		Kernel sees mapping → it’s file-backed.
		Kernel checks page cache:
			If not present, allocate a physical page from buddy → read file block from disk into that page.
			Insert it into the file’s page cache (address_space mapping).
			Process PTE now points to this page.
			CPU executes directly from this page in RAM.
	So:
		Disk copy = permanent storage on SSD/HDD.
		Page cache = in-RAM copy of only the parts you’ve touched (demand paging).
		No extra hidden duplicate — page cache is the working copy in RAM.

how page cache works with .so (mmap/exec) vs when you do a read() into a malloc’d buffer.
		Case 1: mmap/exec a .so (shared lib)
		[ Disk: libm.so ] 
			  │
			  ▼ (on first access, page fault)
		[ Page cache page in RAM ]
			  │  (the same RAM page is linked to the file inode)
			  ▼
		[ Process PTE → points to page cache page ]
			  │
			  ▼
		[ CPU executes code directly from page cache page ]
		Only one copy in RAM.
	Page cache entry is the process’s code/data.
	Multiple processes mapping the same .so share the same physical page (page cache).
		Case 2: read() into malloc buffer
		[ Disk: libm.so ]
			  │
			  ▼
		[ Page cache page in RAM ]   (kernel always uses page cache to buffer file data)
			  │
			  ├─ stays in kernel's page cache for reuse
			  │
			  └─ copy performed by sys_read()
					│
					▼
			[ User malloc() buffer (anonymous page) ]
					│
					▼
			[ Process sees data in its heap ]
		Now there are two copies in RAM:
			One in page cache (kernel keeps it for re-reads or other processes).
			One in your malloc’d buffer (private, anonymous memory).
	Writable mappings (COW case)
	If you mmap(file, PROT_WRITE, MAP_PRIVATE) and write:
		[ Disk: libm.so ]
			  │
			  ▼
		[ Page cache page in RAM ]   (read-only in process)
			  │
			  └─ On first write → COW fault:
					   │
					   ▼
			 [ New anonymous page in RAM ]
					   │
					   ▼
			 [ Process PTE remapped to anon page ]

File-backed page stays untouched in cache.
Writes go to a new anonymous page.

Visual Summary
        mmap/exec                read()                   mmap+write (COW)
     ───────────────        ────────────────          ─────────────────────
Disk → Page Cache Page      Disk → Page Cache Page    Disk → Page Cache Page
       │                          │                           │
       ▼                          └─copy─→ malloc buffer      └─COW─→ new anon page
Process PTE → same page         Process PTE → anon buf        Process PTE → anon page

Takeaways
	mmap/exec: page cache page = process memory, no duplicate.
	read(): duplicate created (page cache + user buffer).
	COW write: duplicate created only on write, anon page replaces mapping.
	Page cache’s purpose = avoid redundant disk I/O + allow sharing across processes.

Unlike mmap(), read() / write() don’t create mappings, but they populate page cache pages, which are the same pages used by mmap() if later mapped.


Kernel-only Allocations (not exposed to userland but create mappings)
	These don’t use mmap from userspace, but they still create VMAs internally:
		vmalloc() / vmap() (kernel allocs non-contiguous memory, maps virtually contiguous).
		ioremap() (map device MMIO into kernel VA space → file-backed in a sense, but by device memory).
		remap_pfn_range() (used by drivers to mmap device memory into user space, e.g., /dev/fb0).

Exhaustive List of Linux Memory Zones
Zone			Purpose
ZONE_DMA		Low PFN memory reserved for devices with old DMA addressing limits (e.g., <16MB on x86, <32-bit addressable range on ARM).
ZONE_DMA32		(On x86-64/ARM64) memory below 4GB, usable by 32-bit PCI devices needing DMA.
ZONE_NORMAL		Main region for kernel allocations, page cache, slabs. Directly mapped in kernel linear map.
ZONE_HIGHMEM	(x86 32-bit only) Memory above 896MB, not permanently mapped into kernel VA. Rare now.
ZONE_MOVABLE	Region reserved for migratable pages only (anon, file cache). Used by compaction, CMA, THP to keep fragmentation low.
ZONE_DEVICE		For device memory managed like RAM via devm_memremap_pages() (e.g., persistent memory, HMM for GPUs). Not swappable.

ZONE_DMA / ZONE_DMA32
	Used when drivers call dma_alloc_*(). Related to CMA: CMA pools usually carved out of low memory so devices can DMA into it. Pinned pages for device buffers (DMA-BUF, camera/GPU) often must come from DMA zones.

ZONE_NORMAL
	Default zone for almost everything:
		Page cache
		Slab/SLUB/SLOB caches
		Anonymous memory (heap/stack)
		File-backed mappings
		THP/MTHP promotion: buddy compaction happens here to form contiguous 2M (or other order) chunks.
		HugeTLB pages: reserved hugepages usually carved out of ZONE_NORMAL.

ZONE_HIGHMEM (only x86 32-bit)
	Not directly mapped in kernel linear address space → must kmap temporarily.
	Mostly historical, but influences why zones exist.
	THP/HugeTLB not usually placed here.

ZONE_MOVABLE
	Special pageblock type for migratable pages only:
		Anonymous memory
		File cache pages
		Unmovable allocations (slab, kernel stacks, pinned DMA pages) cannot go here.
	Critical for:
		CMA: CMA pools often come from movable blocks.
		THP: compaction prefers migrating pages from movable zones.
		Page migration: used to free space for large allocations.

ZONE_DEVICE
	Added for persistent memory (NVDIMM/pmem) or device-managed RAM (GPUs via HMM).
	Shows up as a zone but doesn’t behave like regular DRAM:
		Not swappable
		May not be on LRU

HMM (Heterogeneous Memory Management for GPUs):
	Modern GPUs (NVIDIA, AMD, Qualcomm Adreno with SVM) want to share memory with the CPU:
		Unified Virtual Addressing (CPU+GPU see same pointers).
		GPU can directly access system RAM pages.
		Need page faulting on GPU side if a page is missing.
	HMM Solution
		HMM = Heterogeneous Memory Management, part of Linux MM.
		Allows GPU drivers to:
			Mirror CPU page tables into GPU’s MMU (via SVM = Shared Virtual Memory).
			Handle GPU page faults by calling into the Linux MM to migrate pages if necessary.
			Support memory migration between device memory (VRAM) and system DRAM.
	Flow:
		Process allocates memory (anon/file-backed).
		HMM lets GPU page tables map those same pages.
		If GPU touches a page not resident → HMM triggers CPU page fault handling → allocate/migrate page → update GPU PTE.
		This is how modern APIs (CUDA UM, ROCm SVM, OpenCL SVM) work under Linux.

devm_memremap_pages() vs ioremap()
	Both are about mapping physical addresses into the kernel virtual address space, but they’re very different in intent.
	ioremap()
		Used for device MMIO (memory-mapped registers, framebuffers).
		Creates non-cacheable, strongly ordered mappings.
		Doesn’t treat the range as normal RAM.
			Example: map PCI BAR registers or GPU command buffer space.
	devm_memremap_pages()
		Used for device memory that behaves like RAM (e.g., NVDIMM persistent memory, HMM GPU VRAM).
		Returns an array of struct pages → the memory becomes part of the page allocator.
		Can be used with normal kernel allocators (page cache, anon pages).
		Supports ZONE_DEVICE.
		Integrated with migration, compaction, and LRU if applicable.
	Key difference:
		ioremap() = just map device space for MMIO, no struct page, not on LRU, not swappable.
		devm_memremap_pages() = register memory with Linux MM as managed pages (like DRAM/ZONE_DEVICE).

HMM SVM (Heterogeneous Memory Management + Shared Virtual Memory):
1) The problem HMM SVM solves
	Traditional “userptr” GPU memory had two bad choices:
		Pin pages (get_user_pages)
			Pros: simple; GPU can DMA them.
			Cons: pins break migration/compaction/CMA, block THP collapse, hurt NUMA balance, can stall reclaim, and are unsafe across munmap/mprotect/fork/COW.
		Copy into driver-owned buffers
			Pros: safe for MM; movable.
			Cons: extra copy, latency, bandwidth waste, double-buffering.
		HMM SVM gives a third way:
			Let the GPU access the process’s normal pages (anon or file-backed) without pinning long-term.
			Keep CPU and GPU page tables coherent at the mapping level (not cache coherence).
			Handle GPU page faults and MM invalidations correctly so memory remains migratable and swappable.
	2) Key building blocks
		HMM (mm/hmm.c)
			MMU notifiers / interval notifiers: callbacks that tell the driver when CPU page tables change (unmap, mprotect, COW, munmap), so the GPU mappings can be invalidated/updated.
			migrate_vma helpers: to move pages between locations (e.g., DRAM ↔ device-private) while preserving userspace VA.
			ZONE_DEVICE pages (optional): if the device has its own memory pool (Adreno generally uses system DRAM; AMD/NVIDIA often use VRAM).
			GPU page-fault path: the GPU/SMMU raises a fault IRQ with the faulting VA; the driver resolves it (fault-in, map, resume).
	3) What “SVM” means in practice
		Shared Virtual Memory: the same user virtual addresses are valid on CPU and GPU (one pointer works on both), or at least the GPU has a per-process page table that mirrors the CPU’s VA layout.
		In Adreno/KGSL designs with the ARM SMMU, the GPU has its own per-process page tables (IOVA space). With SVM, the driver maintains a VA≡IOVA model (or 1:1-ish) and updates GPU PTEs to match CPU mappings.
		SVM doesn’t require the GPU to be cache-coherent with the CPU. It’s about addressing & mappings, not automatically about cache coherence.
	4) Control/data flow (KGSL-flavored)
		User
			App malloc()/mmap() → gets a user VA range (anon or file-backed).
			App passes pointer(s) to GPU runtime/driver via KGSL ioctls (e.g., import user memory as a GPU object, bind to a context).
		Driver (KGSL-like)
			Registers mmu_interval_notifier on the VA range.
			On first use (or prefetch), does an HMM range fault:
		Faults-in pages if needed (swap-in for anon, read from page cache for file).
		Ensures correct write permissions (handles COW if required).
		Collects the stable PFNs (no long-term pins).
		Programs the GPU page table (via SMMU) for that VA range → PTEs point to those PFNs.
		Submits GPU work.
	When GPU touches new pages
		GPU page fault IRQ fires (ARM SMMU stall/fault reported to driver) with the faulting VA + access type (R/W/X).
		Driver calls HMM helpers (e.g., hmm_range_fault()) to fault-in, do COW if write, migrate if necessary; then maps the resolved PFN(s) into the GPU page table.
		Driver un-stalls the faulting context and resumes GPU.
	When CPU changes the mapping (munmap, mprotect, COW, truncate…)
		MMU notifier fires → driver invalidates the affected GPU PTEs (TLB shootdown on GPU), may quiesce work touching that VA, and re-resolves if needed next access.
	Under memory pressure
		The pages remain migratable/swappable (because they’re not pinned).
		If a page migrates or is swapped out, next GPU access faults again; driver re-resolves and re-maps.
	5) Page types supported
		Anonymous pages: heap/stack; swap/zram eligible. SVM lets GPU fault them in and map them.
		File-backed pages: .so, data files, tmpfs/shmem; SVM maps the page cache pages.
		THP/MTHP: workable; usually split during fault/migration if the GPU/SMMU wants base-page granularity. The driver/HMM cope with that.
		HugeTLB (static): typically not used with SVM (pinned, non-migratable); drivers usually avoid long-term pinning for SVM regions.
	6) Why HMM SVM is better than long-term pinning
		Keeps CMA/THP/compaction healthy (pages can move). Allows swap to work (for anon). Plays nice with NUMA balancing and memory tiering (pages can migrate). Correctly handles COW (write faults create private pages; GPU mappings updated accordingly). Reduces the “GUP-longterm” problems (FOLL_LONGTERM pins that break MM).
	7) What you need in the hardware/SoC path
		ARM SMMU (or IOMMU) with fault reporting/stall support so the GPU can page-fault instead of crashing. Per-process GPU page tables (one address space per context). Driver path to install/uninstall PTEs and shoot down GPU TLBs. Fault ISR + bottom-half (workqueue) to resolve faults using HMM APIs. MMU notifier subscribers to handle CPU-side map changes. (PCIe PRI/ATS is the PC world equivalent for GPUs/NICs; on mobile SoCs it’s SMMU faults & stall.)
	8) Coherency, caches, and fences (important!)
		SVM ≠ data cache coherence.
		If the SoC interconnect provides I/O coherence, the GPU sees CPU writes without explicit flushes.
		If not, the driver must do cache maintenance (flush/invalidate) or use uncached mappings / coherent buffers for producer/consumer handoff.
		Correct synchronization (fences/semaphores) is still required so CPU/GPU don’t race on stale data.
		For write permissions, HMM’s range fault sets up PTEs matching PROT; GPU write to a COW’d private mapping → COW fault → new page created, GPU PTE updated.
	9) Swap, reclaim, migration (how it behaves)
		Anon pages can be swapped/zram’d. If swapped out, GPU access will fault, driver will swap-in via HMM fault path, then re-map.
		File pages can be dropped and reloaded from storage on demand; same story.
		Migration/compaction: MM can move pages at will; MMU notifiers force the driver to unmap stale PTEs; next access re-resolves.
		This preserves system health (CMA, THP, movable pageblocks) unlike long GUP pins.
	10) How this looks in a KGSL-style API surface (conceptual)
		Import user VA into a GPU object (IOCTL) with SVM semantics.
		Driver sets an interval_notifier on [va, va+len).
		Command submission references that VA directly (no staging buffer).
		On GPU fault, driver resolves with HMM and installs PTEs; on CPU invalidation, driver unmaps.
		(Exact ioctl names vary by kernel/version; the pattern is consistent.)

Character Devices (char devs)
	Character devices are stream-oriented: read/write sequentially, ioctl control, not addressable by block number.
	In our context:
		/dev/mem, /dev/kmem, /dev/kmsg — raw kernel memory access (rarely used now, security-locked).
		/dev/null, /dev/zero — pseudo devices for testing/zero-pages (anon mappings often use zero_page behind the scenes).
		/dev/random, /dev/urandom — entropy sources (not directly MM, but char devs).
		/dev/shm/ (tmpfs mountpoint) — looks like files (so normal file API), but backed by tmpfs/shmem (internally page cache + swap).
		/dev/dri/renderD or /dev/kgsl (Adreno)** — GPU drivers usually expose char dev nodes; ioctls import memory, map VA, submit jobs.
		/dev/fb0 (framebuffer), /dev/ion (on Android legacy) — memory management interfaces for GPU/display, exposed as char devs.
	Most GPU, memory control interfaces, pseudo-memory sources are char devices.

Block Devices (block devs)
	Block devices are sector-addressable: they export a block I/O queue, page cache sits on them, filesystem mounts them.
	In our context:
		Disks/SSDs (e.g., /dev/sda, /dev/nvme0n1) — file-backed mappings and page cache sit on top of these.
		Swap partitions/files — configured on block devices; anon pages are evicted here.
		zram — block device driver that provides compressed RAM-backed block storage. Used as a swap target or tmpfs backing.
		loop devices (/dev/loopN) — block dev backed by a file; can host swap or filesystems.
		pmem (NVDIMM) — appears as a block device, can be mapped with devm_memremap_pages() into ZONE_DEVICE.

Which are neither?
	Anonymous pages, file-backed pages, THP/MTHP, hugeTLB — these are VM constructs managed inside the kernel, not exposed as a device node.
		CMA pools — reserved regions, kernel-internal, not a dev.
		Page cache itself — in-kernel memory, not exposed as a /dev node.
		Slab/SLUB caches — pure kernel allocator, no /dev node.
		HMM SVM — GPU page-fault mechanism, not a /dev, but used via char devs like /dev/kgsl.

Supoose on bootup if I observe multiple smmu map and umnap issue, will using cma with pinned pages or hugepage solve it ?
	If the issue is driver mapping lots of short-lived buffers (e.g., frame allocations, scratch buffers), both CMA and Hugepages may still churn map/unmap.
	If the issue is fragmentation/compaction overhead, pinned CMA pages actually worsen long-term system flexibility.
	If the issue is TLB pressure in SMMU, hugepages are indeed the right fix.
	Practical design patterns
		For GPUs (KGSL, Adreno):
			SVM/HMM avoids per-buffer map/unmap — GPU page faults in normal process pages, driver installs PTEs lazily.
		For camera/display:
			CMA pinned buffers are common (imported as DMA-BUF), reused across frames.
		For networking/fast I/O:
			IOMMU hugepages reduce PTE churn, but require driver + hardware support.
	Answer
		If your map/unmap churn is due to small pages → hugepages (HugeTLB or THP if supported by SMMU) reduce mappings.
		If churn is due to reallocation of DMA buffers → long-lived CMA pinned buffers reused via DMA-BUF help.
		If churn is due to design (short-lived per-frame buffers) → neither alone “fixes” it; solution is to change strategy (e.g., pre-allocate pools, use SVM/HMM for GPU, or batch mappings).

VFS:
	VFS = Virtual File System: the abstraction layer in the Linux kernel that provides a uniform API for files, regardless of the underlying filesystem or storage.
	Implements:
		open, read, write, mmap, fsync, ioctl etc.
		dentry cache, inode cache, superblocks.
	Dispatches operations to actual FS drivers (ext4, tmpfs, NFS, procfs, etc.).
	Provides a consistent view so processes don’t care if a file is on disk, tmpfs, NFS, or procfs.

VFS Page Cache:
	The page cache we discussed earlier is actually managed by the VFS layer.
	Every file/inode in Linux has an address_space object:
		Holds the mapping between file offsets → cached physical pages.
	These pages live in the page cache.
	All file I/O goes through it:
		read() → copies from page cache pages.
		write() → updates page cache pages, marks dirty, later flushed.
		mmap(file) → directly maps those page cache pages into user space.
	VFS page cache = the kernel’s central cache of file contents in RAM, attached to inodes, managed by the VFS.

Virtually contiguous:
	The process/kernel sees a linear virtual address range.
	Underlying physical pages may be scattered anywhere in RAM.
	MMU page tables stitch them together.
	Example:
		Anonymous pages (heap, stack, brk/malloc)
		File-backed pages (ELF .so, mmap(file))
		Tmpfs/shmem (incl. /dev/shm, memfd)
		vmalloc()
		ioremap()

Physically contiguous:
	PFNs are adjacent in real RAM.
	Required for certain hardware (DMA without scatter-gather, CMA).
	Example:
		Slab/SLUB/SLOB caches
		Each object carved out of pages from buddy
		Buddy allocator
			Can return:
				Order-0 (one page) = scattered.
				Order-N (2^N pages) = physically contiguous.
		Pinned pages (CMA, HugeTLB, DMA) are usually physically contiguous → but hurt system flexibility (can’t migrate).

VFS/page cache doesn’t enforce contiguity.

Page cache pages
	Virtually contiguous: ❌ (each file offset → one physical page).
	Physically contiguous: ❌ (can be scattered, managed by inode’s radix tree/XArray).

Exhaustive malloc internal flows
	Case A: Small malloc (e.g., malloc(1KB))
		malloc(1KB)
		  → brk() system call
			→ expand heap VMA
			→ no physical pages yet
			→ first access triggers page fault
			   → allocate single 4K anon page
			   → map into PTE
	Case B: Large malloc (e.g., malloc(1MB))
		malloc(1MB)
		  → mmap(MAP_ANONYMOUS|MAP_PRIVATE)
			→ create new VMA covering 1MB
			→ first access triggers page faults per 4K
			   → allocate 4K pages from buddy
			   → map into PTEs
			→ khugepaged may later collapse into 2M THP
	Case C: Very large malloc (e.g., malloc(1GB))
		malloc(1GB)
		  → multiple mmap() regions or large brk() growth
		  → on access:
			 - allocate many 4K pages (scattered PFNs)
			 - if alignment/contiguity ok:
				  THP collapse at PMD level (2M)
				  MTHP if >2M supported
			 - else remains fragmented 4K
	Case D: malloc + HugeTLB (explicit)
		mmap(fd on hugetlbfs, MAP_HUGETLB, ...)
		  → reserved hugepage pool used
		  → physical hugepage allocated at mmap time (not deferred)
		  → mapped directly into PTE/PMD
		  → first access does not fault in small pages
	Case E: malloc under memory pressure
		malloc() call (brk/mmap) still reserves VA
		→ page fault tries alloc_pages()
		   - If buddy has free pages → success
		   - Else kswapd triggered
				* Reclaim file cache pages first
				* Reclaim anon pages via swap
		   - If THP candidate, may split into 4K to allow partial reclaim
		   - If still fails → OOM killer invoked

KGSL mempool:
	Static Hugepages, THP, MTHP, CMA are all physically contiguous mechanisms.
	KGSL mempool is virtually contiguous only, relies on SMMU → ideal for GPU.
		KGSL doesn’t use CMA because GPU doesn’t need physical contiguity and CMA would starve real DMA clients.
		Hugepages don’t help: they reduce CPU TLB misses, but GPU SMMU already hides physical scatter, so no benefit.
	The best fix for SMMU map/unmap churn is driver-level VA mapping reuse (don’t unmap same IOVA on every submit). Memory pools + persistent VA solve it; CMA/hugepages don’t.

	A reserve pool wrapper (e.g., mempool_create()) that guarantees an allocation even under pressure by preallocating elements. It does not change contiguity or mapping; it uses whatever underlying allocator you give it (slab/alloc_pages/etc.).
	Why vmalloc() isn’t a drop-in for KGSL pools
		DMA & coherency: vmalloc memory is not suitable for dma_map_single(). You must operate on struct page arrays and map per page; at that point you’re back to a page-list design (what shmem already gives you).
		Userspace mapping: KGSL buffers are typically exported via dma-buf and mmap’d by apps. The standard, robust exporter is shmem (tmpfs) backed GEM; exporting vmalloc regions to userspace is awkward and non-standard (you can remap_vmalloc_range() in custom drivers, but it bypasses dma-buf & page cache semantics and complicates security/zeroing/accounting).
		Cache maintenance: Many SoCs rely on I/O coherency or explicit cache ops. Shmem + dma-buf paths have this well-worn; vmalloc adds corner cases.
		TLB & map pressure: vmalloc doesn’t reduce SMMU map ops; the GPU still needs per-page IOVA mappings unless you switch to huge IOVA mappings (independent of vmalloc).
	Preferred design for KGSL (and most DRM drivers):
		Back buffers with shmem/tmpfs pages (drm_gem_shmem style) → you get a list of order-0 pages.
		Export via dma-buf for userspace.
		Map those pages into the GPU SMMU (per-process VA) → device sees contiguous IOVA, PFNs can be scattered.
		Add a driver-level pool of page-backed objects and a persistent IOVA allocator so you map once and reuse mappings → this fixes the “map/unmap churn” you saw at boot.

vmap()
	Creates a virtually contiguous mapping of a list of physical pages (scattered).
	Where used: High-level kernel allocators (vmalloc, ioremap, remap a page list).
	Properties:
		Virtually contiguous ✔️
		Physically contiguous ✖️
	Used when you need one linear VA for scattered PFNs.

fixmap
	A set of fixed virtual addresses (at compile-time) reserved by the kernel for special mappings.
		Examples: APIC registers, temporary page tables, early I/O.
	Not dynamically allocated, but used by macros like set_fixmap().
	Always virtually contiguous, usually map device MMIO or kernel internals.

Kernel modules (static vs dynamic)
	Static (built-in): Compiled into vmlinux, lives in .text, .data, .bss sections → in kernel image memory.
	Dynamic (loadable): Allocated using module_alloc(), backed by vmalloc (virtually contiguous, physically non-contiguous).

idr in Linux kernel
	idr = ID Radix tree (now mostly replaced with xarray).
	Allocates small integer IDs (like handles) → maps to kernel objects.
	Used for DRM GEM handles, device minor numbers, etc.

File descriptor (fd) uniqueness
	Yes, fd is different per process, even if the file is the same.
	Each process has its own fd table (struct files_struct → fdtable).
		fd = index into this table.
	But multiple fd entries can point to the same struct file if:
		Two processes open() the same file separately (different struct file objects, but same inode).
		Or one process does dup()/fork() (then both share the same struct file).

How fd is translated in kernel
	Userspace passes an int fd.
		In syscall (read(fd, buf, len)):
		Kernel calls fget(fd).
		Looks up current process’s task_struct → files_struct → fdtable → struct file*.
		struct file describes the open instance (file pos, flags, mapping).
		struct file points to struct inode (the actual file in VFS).
	Userspace passes int fd → syscall (read/write/mmap/ioctl)
	   current->files (struct files_struct)
		  └─ fdtable[fd] → struct file*
				 ├─ f_op (file ops), f_pos, flags
				 └─ f_inode (struct inode)  ← VFS object
	dup()/fork() can share the same struct file* across fds/processes.

Where modules and their memory live (snapshot)
	Boot:
		• vmlinux + built-ins: loaded contiguously; linear-mapped; text ROX, data RW
	Runtime:
		• LKM text/data: vmalloc area (virtually contig, phys non-contig)
	Backed by:
		• struct page metadata for each physical page, tracked by mm

Why kernel modules are not file-backed
	File-backed mapping (like a .so) = the kernel can drop the in-RAM page and later reload from disk.
	Kernel modules:
		Loaded from a .ko file initially, yes.
		But once inserted, the kernel copies the code/data into memory allocated with vmalloc/module_alloc.
		After that, the .ko file is no longer tied to those pages.
		The module’s memory is anonymous RAM, not linked to the filesystem anymore.
	This is by design:
		Kernel code must always be resident.
		It cannot be swapped out or lazily reloaded from disk (latency, reliability, device drivers must always run). So it’s “pinned” memory.
	Then what about crash/power outage?
		If the system crashes or power is lost:
			RAM contents (kernel, modules, user pages, page cache) are lost.
			On reboot, bootloader reloads the kernel image from storage (e.g., /boot/vmlinuz).
			If modules are needed, they’re reloaded from their .ko files on disk.

Physically contiguous memory
	Means the physical frames (PFNs) are consecutive in RAM.
		Example: PFNs 1000, 1001, 1002 … → contiguous in DRAM.
	Devices that do DMA without scatter-gather must have physically contiguous buffers. Kernel allocators that guarantee this:
		alloc_pages(order > 0) (buddy) → returns contiguous block of 2^order pages.
		CMA → guarantees contiguous DMA buffers.
		HugeTLB, THP → physically contiguous large pages.
	Contiguity is about physical DRAM layout.

One-to-one mapping (linear/direct map in kernel)
	On most 64-bit systems, the kernel sets up a direct mapping between physical addresses and a part of the kernel virtual address space:
		Kernel VA = PAGE_OFFSET + PA
	Example (x86-64):
		Physical 0x12345000 → Kernel VA 0xffff888012345000.
	This mapping is created at boot, covering almost all RAM.
	Used for virt_to_phys() / phys_to_virt() translations. It means the entire RAM is linearly mapped into kernel VA space.
	But note:
		It doesn’t make memory physically contiguous — it just means every PFN has a predictable kernel VA. You can have PFNs scattered all over, but they are all still accessible in the linear map.
	Example
		Say RAM has 3 pages: PFNs [100, 200, 300] (scattered).
		Physically contiguous: If you want 3 contiguous → need [100, 101, 102].
		One-to-one mapping:
			VA(100) = PAGE_OFFSET + 100*PAGE_SIZE
			VA(200) = PAGE_OFFSET + 200*PAGE_SIZE
			VA(300) = PAGE_OFFSET + 300*PAGE_SIZE
		Even though PFNs are not contiguous, each is still mapped predictably in kernel VA space.

Why kernel doesn’t need physically contiguous memory for code/data CPU executes using VA, not PA ?
	Kernel modules/code just need a contiguous VA range (so instruction addresses work).
	The direct map (1:1) ensures all PFNs are accessible.
	Only hardware/DMA cares about physical contiguity.

Devices vs Non-Devices in Linux
	A device = hardware (or a kernel abstraction pretending to be hardware) that implements the character or block device interface.
		Examples: /dev/sda (block device, HDD/SSD), /dev/tty (char device, terminal), /dev/fb0 (framebuffer).
	Devices are exposed via device nodes under /dev, backed by struct file_operations.

	A non-device subsystem = purely kernel-managed memory or state, not tied to hardware I/O.
		Examples: VFS page cache, zswap, slab caches.
	These don’t expose a /dev node, but are observable via /proc, /sys, or special FS (procfs, sysfs, debugfs).

debugfs:
	a special filesystem created for kernel developers to expose internal kernel state. It’s not tied to real hardware or storage — it’s a pseudo filesystem, like procfs or sysfs.
	Designed for debugging and testing, not ABI stability → contents may change between kernel versions.
	Kernel subsystems and drivers can create entries in debugfs.
	These create inodes and file ops under /sys/kernel/debug/....
		Example: GPU driver might expose /sys/kernel/debug/kgsl/proc/<pid> for GPU memory.
		Each file usually implements:
			read() → dumps kernel state (e.g., register values).
			write() → allows tweaking/debugging parameters.
		Example: using debugfs
			driver does:
				struct dentry *dir, *file;
				dir = debugfs_create_dir("mydriver", NULL);
				file = debugfs_create_u32("debug_level", 0644, dir, &my_debug_level);
			This creates:
				/sys/kernel/debug/mydriver/debug_level
				Backed by an internal struct dentry + struct inode with file ops pointing to kernel debugfs helpers.
				You can read/write it from userspace:
					cat /sys/kernel/debug/mydriver/debug_level
					echo 3 > /sys/kernel/debug/mydriver/debug_level
		How is debugfs different from procfs/sysfs?
			procfs (/proc): process info, memory, scheduling (user ABI).
			sysfs (/sys): device model representation (stable ABI for userspace).

			debugfs (/sys/kernel/debug): arbitrary debug hooks, not guaranteed stable, optional.

How mounting works (VFS + mount table)
	When you run:
		mount -t debugfs none /sys/kernel/debug
	Steps inside kernel:
		User → syscall
			mount("none", "/sys/kernel/debug", "debugfs", 0, NULL)
		VFS layer
			Looks up "debugfs" in registered filesystems (register_filesystem() done at boot by debugfs).
			Calls debugfs_fill_super() → sets up a struct super_block for debugfs.
			Root inode created (struct inode + struct dentry for /sys/kernel/debug).
		Mount table
			Kernel links the super_block to the mount point (/sys/kernel/debug).
			Adds an entry in the kernel’s mount namespace (per-process view of mounts).
	Now /sys/kernel/debug is a valid mount point that routes operations to debugfs file ops.

		mount -t debugfs none /sys/kernel/debug
		Flow inside kernel:

		User: mount syscall
		   │
		   └─> VFS: do_mount()
				  │
				  └─> find "debugfs" in registered filesystems
						 │
						 └─> debugfs_fill_super()
								│
								├─ Allocates struct super_block (represents whole FS instance)
								│
								├─ Creates root inode (struct inode) for "/sys/kernel/debug"
								│
								└─ Creates root dentry (struct dentry) to link inode to name
				  │
				  └─> Attach super_block to mountpoint "/sys/kernel/debug"
				  │
				  └─> Add entry into current namespace mount table

udev (device discovery & naming)
	What it is: the userspace daemon (systemd-udevd) that listens to kernel uevents (netlink) when devices appear/disappear (USB, PCI, block, net…). It labels them, sets permissions/ownership, creates /dev nodes, and can trigger services.
	Key pieces
		Kernel emits uevent with environment (SUBSYSTEM, ACTION, DEVPATH, attributes from sysfs).
		udevd matches rules (/usr/lib/udev/rules.d/*.rules, /etc/udev/rules.d/*.rules).
		Rules can set NAME/MODE/GROUP, create SYMLINKS (e.g., /dev/disk/by-uuid/*), set ENV, and even start systemd units.
			Example rule — stable name for a USB-serial adapter + start a service:
				# /etc/udev/rules.d/99-usb-serial.rules
				SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ATTRS{idProduct}=="6001", \
				  SYMLINK+="usb/ftdi-%k", MODE="0660", GROUP="dialout", \
				  TAG+="systemd", ENV{SYSTEMD_WANTS}+="ftdi-starter.service"
			Useful in PCIe hot plug endpoint detection

systemd-journald: central log collector.
	journalctl -xeu <unit> for failures, -f to follow.

How they all fit together (end-to-end)
	Boot: firmware → bootloader → kernel
	  → systemd (PID 1) mounts proc/sys/dev (devtmpfs), starts udevd
	  → udev coldplugs existing hardware (enumerates sysfs), creates /dev nodes, tags devices
	  → systemd brings up targets & services in parallel (dependencies, sockets, timers)
	  → Network manager configures links once udev announces them
	  → journald collects logs; monitoring agents scrape metrics and traces

How dma-buf works in principle:
	dma-buf = a framework for buffer sharing between kernel drivers.
		A kernel driver that allocates a buffer can export it as a file descriptor (fd) using the dma-buf API. Another driver (or even another process) can import that fd to access the same physical buffer.
		That fd is a normal UNIX file descriptor created over an anonymous inode (no filename, no /dev entry).
		So: having an fd ≠ there is a /dev/… device node. The fd refers to a kernel object (struct dma_buf) with file-like ops.
		Core objects:
			struct dma_buf — the shared buffer (global, refcounted).
			struct dma_buf_ops — exporter’s callbacks (map/unmap, begin/end CPU access, mmap).
			struct dma_buf_attachment — per-importer attachment (ties a struct device to the dma-buf).
			struct sg_table — SG list the importer’s device will DMA from/to.
			struct dma_resv (reservation object) — fencing synchronization (GPU/display/camera).
	So:
		Exporter driver = “owns” the memory (allocates and manages it).
		Importer driver = uses the memory (maps it to its device, or lets userspace mmap it).
	Export path (producer driver)
		Driver allocates memory (could be shmem/tmpfs pages, CMA pages, or ION heap). Calls dma_buf_export() with:
			size, ops (struct dma_buf_ops), and private pointer to buffer.
		Kernel creates a struct dma_buf object + associates a struct file object. Returns an fd to userspace via ioctl or API. Now, in userspace, the fd is just an integer like any other file descriptor.
	Import path (consumer driver)
		A different driver (or the same driver in another process) receives the fd from userspace (e.g., passed via ioctl, or via SCM_RIGHTS over a Unix socket). Calls dma_buf_get(fd) → returns a pointer to the same struct dma_buf.
		Then it can:
			dma_buf_attach() to attach its device.
			dma_buf_map_attachment() to get a scatter-gather table (sg_table of PFNs).
			Use this sg_table to program IOMMU or device DMA.
			importer (in kernel)
				struct dma_buf *dmabuf = dma_buf_get(fd);             // lookup by fd
				struct dma_buf_attachment *att = dma_buf_attach(dmabuf, dev);   // attach device
				struct sg_table *sgt = dma_buf_map_attachment(att, DMA_BIDIRECTIONAL);
				// sgt->sgl is now DMA-mapped; use sg_dma_address() / sg_dma_len() for device
				dma_buf_map_attachment() calls exporter’s .map_dma_buf() which typically builds the SG list, and calls dma_map_sg() for the importer’s dev.
					Result: an IOVA (or bus DMA addresses) and segment lengths ready for programming your device.
				No IOMMU? Then dma_map_sg() returns bus addresses directly; you need hardware SG support or physically contiguous backing (CMA).
	Userspace perspective: VA vs PA
		From userspace: the fd is just a handle.
		Userspace cannot directly know the PA (physical addresses are hidden by the kernel for security and abstraction). If userspace wants to access buffer contents:
			Call mmap(fd, ...).
		Kernel sets up a VA mapping in the process → PTEs pointing to the buffer’s pages. Userspace sees a linear VA region, same contents as kernel buffer.VA is provided by mmap. PA is never exposed.
	Different drivers vs different processes
		Different drivers = different kernel subsystems (e.g., GPU driver, display driver, V4L2 camera driver).
			They all can import the same dma-buf fd and attach/map it to their device.
		Different processes = completely separate userspace apps.
			One app can export fd, send it to another process (via Unix domain socket with sendmsg() + SCM_RIGHTS).
			Second app now has its own fd that references the same struct dma_buf.
		So dma-buf is cross-driver and cross-process. That’s the whole point.
	If userspace wants to see the buffer: mmap(fd, …) → exporter’s .mmap() is invoked to map pages to user VA.
	If kernel wants CPU access: dma_buf_vmap() for a linear kernel mapping (exporter must support it).
	When mixing CPU & device access, use dma_buf_begin_cpu_access()/end_cpu_access() (and the exporter performs proper cache maintenance).
	Unmap & detach
		When done:
			dma_buf_unmap_attachment(att, sgt, DMA_BIDIRECTIONAL);
			dma_buf_detach(dmabuf, att);
			dma_buf_put(dmabuf);   // drop importer’s ref
			Exporter frees the buffer when all references (all fds + all attachments) are dropped.
	Fencing / reservations (ordering across drivers)
		dma-buf includes a reservation object (struct dma_resv) that holds fences (timeline sync objects).
		Exporter/importers add fences when they start/finish GPU/ISP/Display work.
		Consumers wait on fences before accessing the buffer to avoid tearing or stale data.
	Does dma-buf fd imply a /dev/* node?
		No.
		The fd refers to an anonymous inode associated with struct dma_buf.
		There is no /dev/dmabuf123.
		You’ll see the fd under /proc/<pid>/fd/<n> pointing to anon_inode:[dmabuf].
		You can create or receive that fd via driver ioctls, EGL/GBM APIs, V4L2, DRM/KMS, etc., and pass it cross-process with SCM_RIGHTS.

DMA fundamentals (what addresses are we talking about?)
		CPU virtual address (VA): what kernel/user code sees.
		Physical address (PA): DRAM address.
		Bus/Device address (DMA address / IOVA): what the device uses on its bus.
	If there’s an IOMMU/SMMU, the device sees an IOVA that the IOMMU translates → PA. If there’s no IOMMU, the device must be able to DMA directly to physical (or a limited range) and often needs physically contiguous memory (or hardware scatter-gather support).
	Cache coherency matters:
		Some SoCs are I/O coherent (device sees latest CPU writes without explicit flushes). Others need cache maintenance.
	Linux DMA API distinguishes:
		Streaming mappings (temporary, call dma_map_* / dma_unmap_* + dma_sync_* as needed).
		Coherent mappings (dma_alloc_coherent) which give a region that’s kept coherent (or mapped uncached).
		Directions: DMA_TO_DEVICE, DMA_FROM_DEVICE, DMA_BIDIRECTIONAL drive cache ops & barriers.
	If the mapping is streaming, respect direction and call dma_sync_* if CPU will access between ops.

Scatter-Gather (SG) lists
	Why SG? A big buffer in RAM is often made of many 4K pages that are physically non-contiguous. Devices can still DMA the whole thing if either:
	The hardware supports scatter-gather (reads an SG list of segments), or an IOMMU stitches non-contiguous PFNs into one contiguous IOVA.
	Kernel structures & flow:
		struct scatterlist (per segment) + struct sg_table (the collection).
		You fill an SG list with pages (or the exporter does), then call dma_map_sg(dev, sglist, nents, dir).
		Returns the number of DMA segments after merging adjacent PFNs into larger segments (hardware-friendly).
		Populates sg_dma_address() and sg_dma_len() for each segment (the device addresses it should use).
		Later you must dma_unmap_sg() when the device is done (for streaming mappings).
	If an IOMMU is present, dma_map_sg also programs the IOMMU to map IOVA→PA for those segments.

DMA BUF map
[Exporter] (alloc pages) → [dma_buf_export] → fd to userspace
     ^                                     |
     |                                  pass fd (SCM_RIGHTS / API)
     |                                     v
[Importer] ← dma_buf_get(fd) ← attach(dev) ← map_attachment(dir)
     |                 |                        |
     |                 └→ sg_table (DMA addrs) ←┘ (via dma_map_sg/IOMMU)
     └→ program device with sg_dma_address/len
          (DMA runs; fences record completion)
… CPU access? → mmap(fd) + begin/end CPU access …
cleanup: unmap_attachment → detach → dma_buf_put → exporter frees when refs drop to 0

Fd lifetime in Linux in general
	A file descriptor (fd) is per-process, stored in that process’s struct files_struct → fdtable.
		When a process exits, the kernel automatically closes all its fds (filp_close() → fput() on the struct file).
		Closing the fd decrements the struct file refcount, which may eventually free underlying resources.

dma-buf is special but consistent
	A dma-buf fd is backed by a struct file (anon_inode:[dmabuf]).
	That struct file points to a struct dma_buf (the shared buffer object).
	struct dma_buf has its own refcount (global, across all processes).
	So:
		Each process holding the fd contributes a refcount.
		When the exporter process dies: its fd table is torn down → refcount is decremented.
		If no other process has a reference → dma-buf is freed (buffer memory released).
		If another process (or kernel driver) still has an fd or attachment → buffer stays alive until the last reference goes.

What about exporter vs importer processes?
	The exporter process (e.g., camera HAL) is not privileged compared to importers.
	Once it has exported a dma-buf fd, the buffer is owned by the kernel (not tied to the exporter’s lifetime).
	Any importer process (e.g., GPU, display) that still has the fd can keep using it even if the exporter exits.
	The kernel only frees the dma-buf when all fds and kernel attachments are gone.


Does dma-buf work only on CMA?
	No.
	dma-buf is agnostic to the actual memory backend.
	Exporter driver decides what type of memory backs the buffer. Common backends:
		shmem/tmpfs pages → swappable, pageable, flexible (most common: DRM GEM shmem, V4L2).
		CMA pages → physically contiguous, pinned, non-swappable (needed for devices w/o scatter-gather or IOMMU).
		ION heaps (older Android) → wrappers around shmem/CMA.
		Device-private memory → e.g., VRAM, GPU-specific heaps.
	If buffer must be physically contiguous → CMA.
	If it can be scattered + IOMMU does stitching → shmem.


If CMA/non-swappable, how do we stop other processes from touching that PA?
	Processes cannot directly touch physical addresses. They only ever see virtual addresses via page tables. Unless the kernel explicitly maps those pages into a process’s VA space (via mmap(fd, …)), that process cannot access them. So only processes that are given the dma-buf fd can mmap() it. The fd acts like a capability/handle.

	No fd → no mapping → no way to reach that PA. Kernel enforces access. If you don’t have the fd, you can’t mmap() or read() that buffer. Even if you guess the PA, there’s no syscall to map arbitrary PAs (unless you’re root poking /dev/mem, which is restricted on modern kernels with CONFIG_STRICT_DEVMEM).

Is the fd “everything” in Linux?
	Almost. In Linux, “everything is a file” is the guiding philosophy, and fd is the handle you use in userspace. But under the hood:
	File descriptors (fd) = userspace handle to a struct file in kernel.
	struct file may represent:
		A disk file (ext4 inode).
		A socket (network endpoint).
		A pipe or eventfd (IPC).
		A character device (/dev/tty).
		A block device (/dev/sda).
		A dma-buf (anon inode).
		Even epoll, signalfd, timerfd, inotify.
	So yes: fd is the generic abstraction for kernel objects you can read/write/ioctl/poll.

But not everything in Linux is an fd. For example:
		Memory mappings (VA) are not accessed via fd (once mapped, you just use pointer deref).
		Threads/tasks are kernel objects, not fds (though you can pidfd_open() to turn a process into an fd-like object).
		cgroups, namespaces, netlink sockets are managed differently (but often have fd interfaces too).
	Linux is increasingly moving towards fd-unification (pidfd, io_uring, etc.), but not literally 100% of kernel resources are fds.

ZRAM = a virtual block device backed by compressed RAM. Each page is compressed and scattered in RAM with zsmalloc. No physical contiguity needed. ZRAM is useful when you have no swap device (embedded, Android).

ZSWAP = a compressed cache for swap. It intercepts swap I/O, compresses to RAM pool first, and only writes to real swap (disk or zram) when needed. ZSWAP is useful when you have disk swap but want fewer I/O writes and better performance.

CPU side: MMU, page tables, TLB
	MMU (Memory Management Unit)
		Hardware that translates Virtual Address (VA) → Physical Address (PA) using multi-level page tables.
		Enforces permissions (R/W/X, user/kernel), attributes (cacheability), and records A/D (accessed/dirty) bits.
	TLB (Translation Lookaside Buffer)
		Small CPU cache of recent VA→PA translations (and perms).
		On TLB hit → fast; on miss → page table walk (hardware walker), possibly a page fault into the kernel if mapping absent/invalid.

Page sizes
	Base pages (e.g., 4 KiB / 16 KiB / 64 KiB), THP/MTHP (e.g., 2 MiB, variable), HugeTLB (2 MiB/1 GiB).
	Larger pages reduce TLB pressure (fewer entries for same coverage).

VA→PA flow (CPU)
	CPU loads VA
	 ├─ TLB hit → get PA + perms → access RAM
	 └─ TLB miss → HW page-table walk:
		  • read PGD/PUD/PMD/PTE
		  • if valid → fill TLB → access RAM
		  • if invalid/no page → page fault to kernel:
			   - anon: allocate page from buddy (or swap-in)
			   - file-backed: fetch/instantiate page cache
			   - set PTE, resume
	THP/MTHP: single huge PTE covers many base pages → fewer TLB misses.
	HugeTLB: pinned huge mappings (pre-reserved).
	Anon vs file-backed: PTEs either point to anonymous pages or to VFS page cache pages.

Device side: DMA addresses, IOMMU (SMMUv3), IOVA
	Devices don’t use CPU VAs. They issue memory requests on a bus with a device address:
		Without IOMMU: that’s usually a physical address; device may require physically contiguous buffers (→ CMA, HugeTLB).
		With IOMMU: device uses IOVA (I/O Virtual Address). The IOMMU translates IOVA→PA, analogous to the CPU MMU, with its own IOMMU page tables and IOMMU TLB.

ARM SMMUv3 (generic IOMMU on ARM64 SoCs)
	Supports per-device or per-process address spaces.
	Integrates with ARM SMMU TLB, support for ATS/PRI, and PASID (Process Address Space ID) to multiplex many address spaces per device.

DMA mapping API (kernel)
	dma_map_sg() (or friends) programs the IOMMU with an IOVA→PA mapping from your scatter-gather list; returns device-visible DMA addresses (IOVAs).
		With IOMMU, PFNs can be scattered; device still sees a contiguous IOVA (no need for CMA).
		Without IOMMU, hardware must support SG itself, or you must use physically contiguous memory.

PASID (Process Address Space ID)
	Tag carried with device memory requests so one device can access multiple address spaces, typically per user process. Lets the IOMMU select the correct page table (think “device versions of mm_struct”).
	Ties directly to SVM: device can use the same VA as the CPU process (pointer-sharing).

PRI (Page Request Interface)
	Device can fault on missing IOVA translations and ask the host/IOMMU to resolve them (device-generated page faults). The kernel resolves by faulting-in/migrating the CPU page, installing the IOMMU PTE, then the device resumes — like a device-side equivalent of a CPU page fault. Crucial for HMM/SVM so GPUs can access regular process memory without long-term pinning.

ATS (Address Translation Service)
	Device can query/cached CPU translations (or IOMMU translations) directly, reducing IOMMU walk overhead. Works with ATC (Address Translation Cache) on the device (device-side TLB).

Pitfalls & correctness
	IOTLB/ATC invalidation: whenever CPU unmaps/migrates pages, the kernel/driver must invalidate IOMMU TLB and device ATCs → otherwise devices see stale translations.
	Cache coherency: CPU↔device must agree on cache policy. Use the DMA API and dma-buf begin/end CPU access hooks.
	Long-term page pinning: GUP-pinned user pages break migration/THP/compaction/CMA. Prefer HMM/SVM or shmem + dma-buf.
	Map/unmap churn (your SMMU boot issue): fix at the driver policy layer with persistent IOVA mappings and buffer pools; hugepages/CMA don’t cure churn.

What exactly happens during execve() (ELF case, step-by-step)
	sys_execve(path, argv, envp)
	  → VFS path lookup, open executable (struct file, inode)
	  → Pick binary handler (binfmt_elf)
	  → Read ELF headers, PT_LOAD/INTERP, etc.
	  → Create new mm (mm_struct), tear down old mappings (except fds not O_CLOEXEC)
	  → Install a fresh set of VMAs:
		   - Code/text PT_LOAD → file-backed MAP_PRIVATE VMA
		   - Data PT_LOAD     → file-backed MAP_PRIVATE VMA (will COW on write)
		   - .bss             → anonymous zero-fill (VMA with anon COW)
		   - Heap (brk)       → empty anon VMA (grows on brk/sbrk/malloc)
		   - Stack            → anon VMA with guard page
		   - vdso/vvar        → special kernel-mapped VDSO pages
		   - PT_INTERP (ld.so) → map interpreter as above (file-backed)
	  → Populate user stack with argv, envp, auxv (AT_PHDR, AT_ENTRY, HWCAP, etc.)
	  → Set regs: PC = entry point (usually loader’s _start), SP = new stack
	  → Return to user mode; first instruction runs
		  • First touches cause page faults:
			  - File-backed: bring page into page cache; map PTE
			  - .bss/heap/stack: allocate anon pages; map PTE
	Key idea: before first instruction, most pages aren’t resident; they fault in lazily.

fork vs exec vs execv vs clone
	fork()
		Creates a new process by duplicating caller’s memory, fd table, etc.
		Uses COW (copy-on-write) pages: child and parent share physical pages until one writes.
		Both processes continue execution after fork.
	exec() family
		Replaces the current process image with a new program.
		Same PID, but new code/data/stack.
		execve(path, argv, envp) is the actual syscall; execv, execl, etc. are libc wrappers.
	fork + exec (classic UNIX pattern)
		fork() child → in child execve() a new program.
			Parent keeps running; child runs new program.
		clone()
			More flexible: low-level primitive.
			Used to implement both fork and pthread_create.
			Flags decide what to share: memory (CLONE_VM), files (CLONE_FILES), signals (CLONE_SIGHAND), etc.
				With CLONE_VM|CLONE_THREAD → create threads.
				With no flags → behaves like fork.

fork() = duplicate process (COW).
execve() = replace current process with new binary.
fork()+execve() = spawn new program (shell model).
clone() = flexible low-level building block (used by glibc for threads).

Why PASID is needed for SVM
	SVM (Shared Virtual Memory) = device and CPU both use the same virtual addresses to refer to memory in a process.
	That means:
		Process A’s pointer 0x7fff1234000 must refer to its private pages.
		Process B may have a different mapping at the same VA.
	The device must know which process’s VA→PA mapping to apply when it sees 0x7fff1234000.
	CPU has mm_struct per process with VA→PA page tables. With PASID, the IOMMU can mirror that mm_struct into a device PASID context.

Without PASID
	Each device has only one address space (one set of page tables) in the SMMU.
		If GPU issues DMA to 0x7fff1234000, the IOMMU doesn’t know which process’s mapping to use.
	So, the OS/driver must copy or pin buffers, and pass device an IOVA handle instead of raw VA.
	Without PASID, device only has a flat IOVA; no notion of per-process VA spaces → can’t do transparent SVM.

With PRI (Page Request Interface), the device can even fault on missing mappings and let the kernel resolve them (like CPU page faults).

CPU side: normal process VA space
	Each userspace process has:
		struct mm_struct → represents the process address space.
		Points to top-level page table (CR3/TTBR).
		Has mm->pgd, mm->mmap (list of VMAs), etc.
		Page tables → allocated in RAM (buddy allocator).
		TLB caches VA→PA mappings for CPU.
	So: mm_struct = process VA universe.

Device side: SMMU/IOMMU
	PASID table = maintained by SMMUv3 driver. Each PASID entry points to a Context Descriptor.
	Context Descriptor = contains pointer to page tables + config (permissions, formats).
	Stream Table = maps device Stream IDs to PASID tables (or single context).
		So: (StreamID, PASID) → SMMU knows which page tables to walk.

Example: GPU SVM
	Say OpenCL app does:
		int *A = malloc(1<<20);
		kernel<<<...>>>(A);   // GPU kernel accesses A directly
	Flow:
		malloc() → anon pages, mapped into process mm_struct.
		GPU driver binds device to mm with iommu_sva_bind_device().
		Allocates PASID for this process.
		Programs SMMU PASID entry to point to process page tables.
	GPU issues DMA: (PASID=X, VA=0x7fff1234000).
		SMMU looks up PASID=X → process’s PGD → walks page tables.
		If VA valid + mapped → PA found → DMA proceeds.
		If VA unmapped (e.g., swapped out) → PRI fault → kernel handles, installs mapping → retry.
	End result: GPU can dereference the same pointer as CPU code.

map
	Userspace Process A (PID 1234)
	 └─ struct mm_struct (VA space)
		 └─ pgd (page tables in RAM)
			  └─ PTEs map VA→PA
			  └─ linked to iommu_sva binding

	GPU Driver:
	 └─ iommu_sva_bind_device(dev=GPU, mm=1234.mm)
		 ├─ alloc PASID=42
		 ├─ iommu_domain → context descriptor
		 └─ PASID table[42] = pointer to process pgd

	GPU issues DMA:
	   (StreamID=GPU0, PASID=42, VA=0x7fff1234000)

	SMMU:
	 └─ Stream Table → PASID table[42]
	 └─ Page table walk using process’s pgd
	 └─ VA→PA resolved
	 └─ Device gets PA

MPAM (Memory Partitioning and Monitoring)?
	ARMv8.4+ hardware feature.
		Lets the OS/Hypervisor control memory system QoS:
		Partition cache ways (L3/LLC).
		Throttle memory bandwidth per stream.
	Monitor usage.
		Each request in the memory hierarchy can carry a PARTID (partition ID) and optionally PMG (Priority/Monitoring Group).
	Hardware enforces:
		Cache allocation/way-partitioning.
		Memory bandwidth controls.
	Counters for monitoring bandwidth/cache usage.


Process Creation Syscalls
	fork()
		Userspace call → libc fork() → syscall.
		Kernel path: sys_fork() → do_fork() → copy_process().
		What happens:
			Allocate a new task_struct for the child.
			Duplicate parent’s mm_struct → child gets same VMAs, marked COW (copy-on-write).
			Page tables are shared, marked read-only. First write → page fault → new page allocated.
			File descriptors (struct file *) are duplicated with refcounts.
			Scheduler places child on runqueue.
		Result: Two processes, same address space but diverge on write.
	vfork()
		Same as fork, but child shares parent’s address space until execve().
		Parent is suspended until child calls execve() or _exit().
		Used for performance in shell pipelines.
	clone() / clone3()
		Lower-level primitive (used by fork, pthread_create, etc).
		Flags decide what to share:
			CLONE_VM → share mm_struct (threads).
			CLONE_FILES → share file descriptor table.
			CLONE_SIGHAND → share signal handlers.
			CLONE_THREAD → create a thread in same thread group.
		Internally: also goes through copy_process().
	execve()
		Purpose: Replace process image with a new binary.
			Kernel path: sys_execve() → do_execveat_common() → search_binary_handler() → load_elf_binary().

What happens:
	Tear down old mm_struct.
	Create fresh mm_struct for new program.
		Parse ELF headers:
			.text/.rodata → file-backed private VMAs.
			.data/.bss → file-backed, then zero-fill anon.
			heap → anon VMA.
			stack → anon VMA with guard page.
			vdso → kernel-provided VDSO mapping.
			Build argv, envp, and auxv on new stack.
			Set PC=entry point, SP=new stack.
		Result: Same PID, brand new code+data.
	exit() / _exit()
		Kernel path: do_exit().
		Cleans up:
			Free mm_struct (release page tables, unmap VMAs).
			Decrement refcounts on inodes, files.
			Free task_struct after parent reaps (via wait()).

Memory Mapping Syscalls
	brk() / sbrk()
		Grow/shrink the process heap.
	Kernel: do_brk() → create/extend anon VMA.
	Actual physical pages are not allocated until first access → page fault → buddy allocator supplies page.

mmap()
	Most powerful syscall for memory:
		MAP_ANONYMOUS → anon pages (heap-like).
		MAP_SHARED|fd → file-backed shared mapping.
		MAP_PRIVATE|fd → file-backed COW mapping (used in execve).
		MAP_HUGETLB → static hugepages.
	Kernel: do_mmap() → allocates vm_area_struct, links into mm_struct.
		No pages yet → page faults fill them:
			Anon → buddy allocator page.
			File → page cache page, loaded from disk.

munmap()
	Kernel: do_munmap() → remove VMA, unmap PTEs.
		Pages become reclaimable.

mprotect()
	Change VMA protection flags.
	Kernel: do_mprotect_pkey() → update page tables (mark read-only, no-exec, etc).
	Used for JITs, sandboxing.

madvise()
	Hint kernel about memory usage:
		MADV_DONTNEED → drop pages from page cache.
		MADV_HUGEPAGE / MADV_NOHUGEPAGE → THP policy.
		MADV_PAGEOUT → proactively swap out.
	Kernel: do_madvise() → reclaim/THP policy manager.

mlock() / munlock()
	Pin pages in RAM (non-swappable).
	Kernel: mark VMA as VM_LOCKED, fault pages in, mark in LRU as unevictable.
		Used by real-time, crypto, DBs.

mremap()
	Resize/move mappings.
	Can expand heap-like areas.
		Kernel: do_mremap() → may allocate new pages, copy/migrate old.

SysV/POSIX Shared Memory
	shmat() / shmdt() (SysV) or memfd_create(), shm_open() (POSIX).
	Backed by shmem/tmpfs (inode+dentry, page cache).
	Enable IPC and dma-buf exporters.

File & Page Cache Related
	open() / close()
		VFS path walk → get inode, allocate struct file.
		Page cache not touched yet.

read() / write()
	Kernel: vfs_read()/vfs_write().
		Read path:
			Look up inode’s page cache.
			If miss: read from disk into page cache (via block I/O).
			Copy from page cache to user buffer.
		Write path:
			Copy user buffer into page cache page.
			Mark dirty → background writeback to disk.

mmap(fd)
	Creates file-backed VMA.
	Page faults pull pages into page cache.
	CPU accesses go directly via PTE → page cache → disk.

msync() / fsync()
	Flush dirty page cache pages to disk.
	fsync() → call filesystem’s ->fsync op.

Process & Resource Control
	getrusage() / prlimit() / setrlimit()
		Kernel: do_prlimit().
		Control resource caps (stack size, number of files, locked mem).
		Enforced during syscalls like brk(), mlock().

sched_setaffinity()
	Kernel updates task’s cpumask.
	Scheduler places it only on allowed CPUs.
	Links to NUMA placement.

setpriority()/getpriority()
	Change scheduler weights (nice values).

Swapping, Reclaim, Migration
	swapon() / swapoff()
		Add/remove swap devices.
	Kernel: init swap cache, mark swap slots.
	Pages can then be evicted:
		Anon → swap slot.
	File-backed → just dropped (reloaded from disk).
	Reclaim path (background, not syscall)
		kswapd and shrinkers walk LRU (anon/file), reclaim.
		Can migrate pages (NUMA, compaction, CMA).
		Swap/zram/zswap handle evicted anon.



MASTER LAYERS — single-page textual map
[ User Processes (per-process) ]
  -> syscalls: fork/clone/execve/open/read/write/mmap/brk/madvise/mlock/ioctl/munmap/munlock
  -> each process: mm_struct (VMAs) | fd table -> struct file* -> inode/dentry

  VMA types:
    - anon VMA (brk/mmap MAP_ANON, stack) -> anon pages
    - file-backed VMA (mmap(fd), code/data from execve) -> page cache pages
    - tmpfs/shmem (memfd_create, /dev/shm) -> file-backed in page cache (dummy inode)
    - hugetlbfs/MAP_HUGETLB -> HugeTLB pages (pinned)
    - THP/MTHP promoted anon/shmem -> folio-sized contiguous PFNs

[ Kernel Virtual Layer (global) ]
  - linear/direct map (VA = phys + PAGE_OFFSET) -> gives kernel VA for any PFN
  - vmalloc/vmap area -> virtually contiguous kernel mappings backed by scattered PFNs
  - fixmap area -> reserved fixed-kernel mappings
  - kernel modules -> built-in (contiguous image) or LKM (vmalloc area)

[ Kernel Memory Structures ]
  - mm_struct -> list of VMAs
  - vm_area_struct -> flags (shared/private, anon/file, PROT)
  - page tables -> PGD/PUD/PMD/PTE (in RAM, hw-walker reads)
  - struct page -> per-physical-page metadata
  - page cache (address_space) -> maps file offsets to struct page

[ Allocators & Caches ]
  - Buddy allocator -> alloc_pages() (source of physical pages)
  - Slab/SLUB/SLOB -> kmalloc / small kernel objects (backed by buddy)
  - vmalloc/vmap -> uses page lists + mapping into kernel VA
  - CMA -> reserved contiguous pool for DMA (allocatable via DMA APIs)
  - zsmalloc/zbud/z3fold -> allocators used by zram/zswap for compressed objects

[ Swap & Compression Tier ]
  - zram (block device) -> compressed page blobs stored in RAM (zsmalloc)
  - zswap -> compressed in-RAM cache in front of disk swap (zbud-like packing)
  - swap device (disk/SSD) -> swap slots (on-disk)

[ IOMMU / Device Side ]
  - Devices DMA using IOVA addresses.
  - IOMMU/SMMU -> translate IOVA -> PA (page tables in RAM; IOTLB caches entries)
  - Without PASID: one IOVA context per device/stream.
  - With PASID: multiple contexts per device -> SVM (device sees per-process VA)
  - ATS/ATC -> device can query or cache translations
  - PRI -> device-side page requests to kernel (on-demand resolution)
  - DMA mapping APIs: dma_map_sg(), dma_unmap_sg(), dma_alloc_coherent(), dma_buf_attach/map

[ Controls & Monitoring ]
  - cgroups -> memory/cpu/io limits, memory charging on page faults
  - MPAM (hardware) -> cache way partitioning, bandwidth throttling (OS maps PARTID)
  - sysfs/debugfs/procfs -> visibility and control interfaces

devm*:
	when you allocate something with a devm_* helper, the kernel records that allocation on the device’s devres list. When the driver is unbound from that device (probe fails, hot-unplug, module unload, remove), the core automatically calls the matching free/unregister in LIFO order. Not tied to userspace fds, PIDs, or threads. The lifetime is tied to the struct device ↔ bound driver relationship.
		So: devm = “free it automatically when the device/driver goes away.”
			devm_kzalloc(struct device *dev, size_t size, gfp_t gfp)
			Same as kzalloc() (zeroed memory), but registered in the device’s devres list.
		On unbind/remove, the core will kfree() it for you.
		Use when the memory is owned by the driver and does not need to outlive the driver’s binding.


PFN vs PTE
	PFN (Page Frame Number): A physical page index.
		If page size = 4 KB, then:
			PFN = PhysicalAddress / 4096
		PFN is just the numbered slot of a page frame in RAM.
		Kernel keeps a struct page[] array (the memmap) indexed by PFN.
		So PFN is the “ID” of a physical page.
	PTE (Page Table Entry)
		An entry in a process’s page table. Maps a virtual page → physical frame (PFN).
		Contains:
			PFN (frame number to use for translation).
			Flags (present, RW, user/kernel, accessed/dirty, exec, cache attrs, etc).

PTE = VA → (PFN + permission bits).
PFN = pure physical index, used inside PTE.

CONFIG_FLATMEM vs CONFIG_SPARSEMEM
	These are kernel memory model configs (see mm/Kconfig).
	CONFIG_FLATMEM
		Old/simple model. Assumes physically contiguous memmap[] array (one big struct page array).
		PFN → struct page is simple linear:
			struct page *p = mem_map + PFN;
		Works only if memory is (mostly) contiguous with few holes.
		Used by small systems, embedded.

CONFIG_SPARSEMEM
	Modern model. Allows memory with holes or NUMA nodes spread sparsely in phys addr space. Memory divided into sections (e.g., 128MB or 1GB granularity, arch-dependent). Each section has its own struct page[] array (the memmap).
		PFN → struct page requires first finding the section, then offset within section.
	Needed for:
		Hotplug memory (online/offline sections).
		Very large memory (64-bit servers, >TB RAM).
		ARM/NUMA systems with discontiguous physical RAM.

What is a "Section" in memory model?
	A chunk of physical memory in SPARSEMEM model.
		Size = architecture-defined (commonly 128 MB or 1 GB).
		Each section has its own memmap (struct page array).
	Allows memory hotplug: add/remove whole sections.
		So: section = bookkeeping unit in SPARSEMEM.

Section memmap (struct page mapping per section)
	The memmap = array of struct page structures describing every PFN.
		In FLATMEM: single big array.
		In SPARSEMEM: per-section memmap allocated only for present sections.
	Kernel stores a struct mem_section for each section, with pointer to its memmap.
	So:
		memmap = struct page[] array.
		section memmap = struct page[] for one memory section.


Every physical page frame (PFN) has a struct page describing it. Among many fields:
	struct page {
		atomic_t _refcount;      // reference count
		atomic_t _mapcount;      // number of PTEs mapping this page
		struct address_space *mapping;  // file (if file-backed)
		...
	};
		refcount (_refcount) = how many active references to this page exist (kernel-wide).
		mapcount (_mapcount) = how many PTEs (virtual mappings) point to this page.

	They track different but related lifetimes.
		Page refcount: Increments when something holds a pointer to this page:
			When it’s in page cache.
			When it’s mapped into a process.
			When get_page() is called by kernel subsystems.
			When it’s pinned via get_user_pages() (e.g., RDMA, dma-buf).
			Decremented when references are dropped.
			When refcount goes to zero → page can be freed back to buddy allocator.
				So: refcount = “is this page in use at all?”
		Page mapcount
			Increments per PTE mapping:
			Each process mapping page (via mmap) increments mapcount.
			Fork with COW increments mapcount for shared PTEs.
			Shared mappings increment mapcount across multiple VMAs.
			Zero mapcount means:
				No user-space PTE points to this page.
				But page may still be in page cache (file-backed) or pinned (refcount > 0).
			So: mapcount = “is this page currently mapped into any process’s VA space?”

	Relation to mmap()
		mmap(fd) creates a VMA.
		On page fault → kernel finds page (page cache/anon), inserts a PTE mapping → increments mapcount.
		If multiple processes mmap the same file → each inserted PTE increments mapcount.
			Anonymous pages (heap/stack, MAP_ANON):
				Mapcount goes up when mapped, down when unmapped/freed.
				If mapcount hits 0, they become candidates for swap.
		What if page is not mapped (mapcount=0)?
			Case 1: File-backed page
				Even if mapcount=0, page may still be cached in page cache (refcount > 0). Kernel can drop it anytime (clean) or writeback+drop (dirty). No mapping doesn’t mean freed — it can be reused later if remapped.
			Case 2: Anonymous page
				If mapcount=0 (unmapped, e.g., process exited), and no other refcount → page freed. If mapcount=0 but refcount > 0 (e.g., pinned for I/O), page can’t be swapped or freed until refcount drops.

	Swapping rules
		Anonymous pages:
			If mapcount=0 → candidate for reclaim (free).
			If mapcount>0 (still mapped) but inactive → can be swapped out (PTE replaced with swap entry).
			Must not be pinned (get_user_pages) or locked (mlock).
		File-backed pages:
			If mapcount=0 → can be dropped from cache (since it can be faulted back in).
			If mapped (mapcount>0) but cold → can be unmapped (PTE zapped) and later refaulted.

In SPARSEMEM model, Linux divides physical memory into sections (fixed size, e.g., 128MB or 1GB, depending on CONFIG_SPARSEMEM_EXTREME & arch).
	Each section has metadata (struct mem_section).
		Instead of one big linear array, Linux defines:
			struct mem_section *mem_section[NR_SECTION_ROOTS][SECTIONS_PER_ROOT];
		That is effectively 2D:
			Outer index = "section root" (a group of sections).
			Inner index = section within that root.
		Reason: scaling to very large PFN ranges without wasting memory.
			Old flat array would waste RAM if address space is huge but memory sparse.
			2D lets kernel allocate metadata only for sections that exist.

What does struct mem_section contain?
	Each section represents a contiguous PFN range (e.g., 128MB worth of pages).
		struct mem_section holds:
			Flags (present, online, valid, device, etc).
			Link to the section’s memmap array (struct page[]).
			Info needed for memory hotplug (state = online/offline).
	So mem_section = “section descriptor” → points to the struct page array for that section.

How section memmap relates to struct page array
	struct page[] is the array of per-page descriptors.
		In SPARSEMEM, each section has its own memmap (struct page array for all PFNs in that section).
		The mem_section struct stores a pointer to that memmap.
	So flow is:
		PFN → section number → mem_section[secno] → memmap pointer → struct page[PFN % PAGES_PER_SECTION]

vmemmap array?
	vmemmap = special linear mapping of all struct page[] descriptors themselves into kernel VA. In SPARSEMEM_VMEMMAP, kernel builds a contiguous virtual mapping of all struct page arrays.
		Think: vmemmap = virtual array of struct page, indexed directly by PFN. Behind the scenes, it’s backed by the per-section memmaps.

What is hotplug memory?
	Ability to add/remove RAM at runtime (DIMMs, memory ballooning in VMs, device memory).

What is early memory initialization?
	During boot (before buddy/slab fully up), kernel uses memblock allocator:
		Tracks reserved/free RAM in memblock.memory array.
		Used to allocate kernel image, initrd, page tables, memmap itself.
		Once buddy allocator is initialized, memblock is freed/disabled.
	Early boot uses memblock → then transitions to buddy + zones.

How node, zone, buddy, section connect
	Hierarchy:
	System
	 └─ Node (NUMA node: one CPU+memory domain)
		 └─ Zone (DMA, DMA32, Normal, Movable, Device)
			 └─ Section (sparsemem unit: e.g., 128MB)
				 └─ PFN (Page Frame Number, 4K or 64K each)
					 └─ struct page (refcount, mapcount, flags)

MiB vs MB
	MB (megabyte) = 1,000,000 bytes (10^6).
	MiB (mebibyte) = 1,048,576 bytes (2^20).
		Linux uses MiB (power-of-two) because memory alignment is binary.
	So: 128 MiB = 134,217,728 bytes, not 128,000,000.

What is “root” in section?
	Because mem_section array is 2D:
		mem_section[NR_SECTION_ROOTS][SECTIONS_PER_ROOT]
		“root” = outer dimension, grouping of sections.
	Used to scale memory metadata on large systems (avoid huge flat arrays).
	A section root covers a chunk of PFN space; inside are multiple sections.

What is a pageblock?
	Pageblock = group of pages inside a zone used as the unit for migration/compaction.
	Typically 2 MB size (aligned with THP).
		Buddy allocator + compaction operate at pageblock granularity.
		Flags per pageblock determine migration type.

What does pfn_to_page() do?
	Converts a Page Frame Number (PFN) → struct page*.
		PFN = number identifying a physical frame.
		PTE = entry in page table; contains PFN + flags.

Physical page = the actual RAM contents.
struct page = kernel metadata describing the physical page.

So:
	Virtual Address
	   ↓ PTE
	PFN (frame number)
	   ↓ pfn_to_page()
	struct page
	   ↓
	Physical RAM contents

NUMA node can be “slower/faster” for different cores (numactl --hardware)?
	NUMA = Non-Uniform Memory Access.
	Each CPU socket has local DRAM → local node.
	Accessing another node’s memory requires traversing interconnect (QPI/UPI, InfinityFabric, CCIX).
	Hence, local memory latency < remote memory latency.
	numactl --hardware shows node distances.
	Kernel prefers to allocate from local node → but may fallback to remote if local full.
	NUMA nodes are defined by hardware topology (sockets, memory controllers, interconnect), not only speed.

Why can zones and nodes overlap?
	Node = NUMA domain (hardware).
	Zone = kernel subdivision inside each node (for DMA, Normal, Movable, Device).
	Every node contains zones.
		Zones never span nodes, but zone ranges can overlap in PFN space if not carefully aligned — kernel uses zone PFN ranges within node boundaries.

pg_data_t, struct zone, section, PTE — how related?
	pg_data_t = per-NUMA node descriptor (struct pglist_data), holds all zones for that node.
	struct zone = per-zone descriptor (Normal, DMA, etc).
	Section = bookkeeping unit inside zone (128 MiB chunks).
	PFN = page frame index inside section.
	PTE = mapping VA → PFN.
	struct page = metadata for that PFN.

Hierarchy:
	pg_data_t (node)
	 └─ struct zone (DMA, Normal, Movable, Device)
		 └─ Sections (128MB blocks)
			 └─ Subsections (2MB blocks)
				 └─ PFN (4K/64K page frame)
					 └─ struct page

Direct reclaim
	Happens in the context of the allocating task.
	If you call alloc_pages() and the zone’s free pages < min watermark, kernel immediately tries to reclaim pages synchronously before satisfying your allocation.
		Blocking: your task scans LRU lists, drops page cache, writes back dirty pages.
		Risk: long latencies, can stall critical paths.

Indirect reclaim
	Handled by the background kswapd kernel thread.
	When free pages fall below low watermark, kswapd wakes up and starts reclaiming until zone reaches high.
	Async reclaim in the background, prevents most tasks from hitting direct reclaim.

Difference vs OOM:
	If reclaim fails and system still cannot satisfy allocation, Out-Of-Memory killer triggers. OOM kills processes to free memory (last resort).

pgdat_dirty, pgdat_writeback, pgdat_reclaim_locked
	These are per-node (pglist_data) state counters/flags used in writeback/reclaim:
		pgdat_dirty → counts dirty pages (to be flushed to disk).
		pgdat_writeback → counts pages currently under writeback I/O.
		pgdat_reclaim_locked → prevents multiple concurrent reclaimers on the same node (serialization).
	These are checked in reclaim functions like shrink_node() to decide when to throttle or wait.

shrink_node()
	Core function that runs page reclaim on one NUMA node.
	Walks the node’s LRU lists (active/inactive, file/anon), and tries to free or swap pages.
	Called by both kswapd (indirect) and direct reclaim paths. It uses helpers like shrink_page_list(), try_to_free_pages().

Zone watermarks & boost
	Each zone (DMA, Normal, Movable, etc.) has three watermarks:
		min → if free pages < min, allocations may fail unless caller uses emergency reserves.
		low → threshold for waking kswapd.
		high → when free pages are restored above this, kswapd goes back to sleep.
	Boost:
		When a zone is under heavy pressure, the kernel may temporarily raise the reclaim target (boost watermarks) to build extra reserves and avoid thrashing.

Per-CPU pageset / PCP cache
	Not CPU L1/L2/L3 caches! This is an allocator fastpath cache for pages.
		Problem: If every alloc/free grabbed the zone’s spinlock, contention would be massive.
		Solution: each CPU keeps a small per-CPU page list (“pcp list” or pageset) of free pages.
	When a CPU needs a page:
		First try to pop from its per-CPU list (fast, lockless).
		If empty, refill from zone (grab lock, batch).
	When freeing:
		Push to CPU’s local list. If full, bulk return to zone.
		pcp cache/pageset = kernel per-CPU allocator cache, not hardware CPU cache.

Spanned / Present / Managed / Buddy-available pages
	These are zone capacity accounting distinctions:
		Spanned pages → total PFN range the zone covers (including holes).
		Present pages → actual pages of RAM present in that zone.
		Managed pages → subset of present pages managed by buddy allocator (excludes reserved/firmware/hotplug).
	Buddy available pages → actually free and on buddy free lists.
	So:
		Spanned ≥ Present ≥ Managed ≥ Buddy-free

Why spinlock in zone structure?
	Each zone has a zone->lock protecting its free area (buddy lists, watermarks). Needed to serialize alloc/free operations across CPUs.

Why spinlock, not mutex/semaphore?
	Allocator runs in atomic contexts (e.g., IRQ handlers, GFP_ATOMIC). Sleeping is forbidden there → must use spinlocks. Spinlocks are fast under short critical sections; mutexes would sleep, which is illegal in alloc fastpath.

Lowmem reserve ratio
	Used to protect low zones (DMA, DMA32, Normal) from being depleted by higher-zone allocations. Kernel computes reserve pages in each zone, based on lowmem_reserve_ratio[]. So, an allocation from Normal zone cannot steal too much from DMA zone, which may be needed by devices.

Total reserved pages
	The kernel also reserves some pages globally:
		For emergency allocations (PFN walkers, OOM killer).
		For atomic contexts (GFP_ATOMIC).
		For device DMA (lowmem).
	These reserved pages are excluded from ManagedPages and shown in /proc/meminfo as Reserved.

	GFP_ATOMIC	Non-blocking, no reclaim, use emergency reserves.	IRQ handler, spinlock critical section.	Very limited pool → failures common.
	GFP_NOFS	Reclaim allowed, but no filesystem reclaim (avoids recursion deadlocks).	Alloc inside FS paths (writeback, journaling).	May fail sooner if memory only reclaimable via FS.
	GFP_NOIO	Reclaim allowed, but no IO (can’t trigger disk IO).	In block layer, storage drivers.	Restricts reclaim, more failures.
	GFP_DMA	Must come from ZONE_DMA (ISA legacy).	Old devices with 24-bit DMA.
	GFP_DMA32	Must come from ZONE_DMA32.	Devices needing <4GB addresses.
	GFP_HIGHUSER	From Highmem zone (x86 32-bit).	Userspace pages.
	GFP_USER	For userspace memory (anon/file).	Page cache, anon allocations.
	__GFP_THISNODE	Only allocate from local NUMA node.	Hard NUMA locality needed.
	__GFP_MOVABLE	Allocation can be migrated/compacted. Goes into ZONE_MOVABLE or MOVABLE pageblocks.	Userspace anon pages, page cache.
	__GFP_RECLAIMABLE	Kernel objects reclaimable by shrinkers (slab caches).	inode/dentry caches.
	__GFP_UNMOVABLE	Kernel memory that must not move.	Page tables, vmlinux data.
	__GFP_NORETRY	Fail quickly if not free.	Opportunistic allocations (network buffers).
	__GFP_NOFAIL	Must succeed (loop until success).	Extremely critical kernel state (swap token). Dangerous!
	__GFP_ZERO	Zero-fill page(s).	Security, predictable buffers.
	__GFP_COMP	Compound page (order>0 as one folio).	THP, hugetlb, higher-order slabs.
	__GFP_NOWARN	Suppress “allocation failure” printk.	Known failure paths where fallback exists.
	__GFP_SKIP_KASAN_POISON	Skip KASAN shadow poisoning.	Performance-sensitive fastpaths.
	__GFP_NOLOCKDEP	Suppress lockdep checks.	Special drivers where locks confuse lockdep.
	GFP_TRANSHUGE_LIGHT	Try THP, but fail softly.	MADV_HUGEPAGE.
	GFP_ACCOUNT	Charge memory to memcg cgroup.	Controlled by cgroups memory controller.

The Idea of Buddy Allocator
	Physical memory is divided into blocks of size 2^order pages (order = 0 means 1 page, order = 1 means 2 pages, etc.). Free lists are maintained for each order in each zone (Normal, DMA, etc).
	On allocation:
		If exact block size is unavailable, a higher-order block is split into “buddies”.
	On freeing:
		Allocator tries to merge (coalesce) a block with its buddy into a higher-order block.
	Key trick:
		The buddy of a block can be found by flipping a single bit in the PFN (Page Frame Number).
	Why flipping a bit works
		Every block is aligned to its own size.
		Example: order-3 block = 2^3 = 8 pages.
				→ Aligned to multiples of 8 PFNs.
				So, given PFN = 0b01011000 (PFN 88 decimal):
				It represents the base of an order-3 block (8 pages).
				Its buddies when split are:
					Block 1: PFNs 0b01011000 to 0b01011011 (88–91)
					Block 2: PFNs 0b01011100 to 0b01011111 (92–95)
				How to find buddy of a given block?
					Just flip the bit at the position = order.
					E.g. for order-2 block at PFN 0b01011000, flip bit 2:
						0b01011000 ^ (1 << 2) = 0b01011100.
					So 88 (0x58) and 92 (0x5C) are buddies at order-2.
	Coalescing on free
		When freeing:
			Look at freed block’s PFN.
			Compute buddy PFN by flipping the order bit.
			If buddy is also free (in the same order’s freelist), remove both and merge into order+1 block.
			Repeat recursively up to MAX_ORDER.
			So allocation splits downward, freeing merges upward.
	Practical Example
		Say memory zone starts with 64 free pages (order=6 block).
			Step A: Allocate 8 pages (order=3): Buddy allocator doesn’t have an order-3 block → splits:
				Order-6 (64p) → two order-5 (32p).
				Take one order-5, split → two order-4 (16p).
				Take one order-4, split → two order-3 (8p).
				Return PFN=0 (pages 0–7).
			Free lists now:
				Order-6: 0
				Order-5: 1 block (pages 32–63)
				Order-4: 1 block (pages 16–31)
				Order-3: 1 block (pages 8–15)
		Step B: Free PFN=0 (8p, order=3)
				Buddy = PFN=8 (flip bit 3).
				PFN=8–15 is free (in freelist).
				Merge → new block at PFN=0, order=4 (16 pages).
				Now order-4 freelist has two blocks (0–15 and 16–31).
				Kernel may later merge these into an order-5 (0–31).
	Metadata organization (last photo explanation)
		Each pg_data_t = one NUMA node.
		Contains node_zones[MAX_NR_ZONES].
		Each zone (Normal/DMA/Movable) has:
			zone->free_area[MAX_ORDER].
		Each free_area[order] has a list of free blocks of size 2^order.
			Protected by zone->lock (a spinlock, because allocations can happen in IRQ/atomic context → can’t sleep).

Each CPU keeps a small cache of free pages, organized by migration type (MOVABLE, RECLAIMABLE, UNMOVABLE, CMA, ISOLATE) and by order (block size).
	Why:
		To avoid global spinlock contention on the zone’s buddy allocator for every alloc/free. Most allocations are order-0 (single pages), so keeping per-CPU freelists avoids locking.
	Key fields:
		lock → spinlock to protect PCP list when bulk draining/refilling.
		IRQ-save variant (pcp_spin_lock_irqsave) is used because alloc/free can happen in IRQ context.
	We disable IRQs locally so that the same CPU cannot deadlock itself if an IRQ handler tries to allocate/frees while holding the lock.
		count → number of base pages currently cached in PCP.
		Each alloc/free updates this.
		high → high watermark.
		If PCP exceeds this many pages, extra pages are drained back to the zone buddy free lists.
		Keeps caches bounded.
		batch → how many pages to transfer between PCP and zone buddy lists at once.
	Example: If PCP empty, refill a “batch” from zone buddy.
		If PCP > high, drain a batch back.
		Tuned by zone_batchsize(), default is min(1MB, 0.1% of zone).
		free_factor → modifies how aggressively to free back larger order pages.
		Avoids PCP hoarding higher-order blocks that fragment memory.
		Implements exponential back-off: the larger the block, the more quickly it is freed back.
		expire → PCPs are per-CPU but memory can belong to other NUMA nodes.
		This field is used by refresh_cpu_vm_stats() to expire PCP pages for remote zones after a delay, to rebalance across CPUs.
		lists[] → actual linked lists of pages, separated by migrate type and order.

Second picture (alloc path diagram)
	This is the allocator call graph:
		alloc_page(), get_zeroed_page(), __get_free_pages(), kmalloc_order() all funnel into → alloc_pages().
			alloc_pages() picks correct NUMA node → _alloc_pages().
			_alloc_pages() first tries fastpath PCP → if fails, calls slowpath buddy allocator.
			If still fails, _alloc_pages_bulk() can batch allocate for efficiency.
		This is the flow from API to buddy.

Page alloc costly order
	Defined as PAGE_ALLOC_COSTLY_ORDER (currently 3, i.e. 8 contiguous pages).
		Meaning:
			For orders ≤ 3, PCP caching is used.
			For orders > 3 (like huge pages), PCP caching is bypassed → allocations go straight to buddy.
			Why?
				Large allocations are rare and need true contiguity. Caching large blocks in PCP would fragment memory and quickly drain buddy lists. So PCP is optimized only for small orders (≤ 3 pages = 32 KB on 4K base pages).

Why IRQ-save variant is used
	Per-CPU allocator lock protects PCP lists. Alloc/free can be called in hard IRQ context (e.g. networking, block I/O). If an IRQ handler ran in the middle of holding the PCP lock and also tried to take it → deadlock.
	Solution:
		Use spin_lock_irqsave() → disables local IRQs while lock held.
		Prevents re-entrancy on the same CPU.
	After unlocking, IRQ state restored.

Putting it together (Practical Scenario)
	A process calls kmalloc(128, GFP_KERNEL).
	This uses alloc_pages(order=0).
		_alloc_pages() first looks in the current CPU’s PCP freelist (order 0, MIGRATE_UNMOVABLE).
			If present → take a page, count--, return.
			Fast, no global lock.
		If PCP empty:
			Grab a batch (say 30 pages) from zone buddy → fill PCP → satisfy request.
		If PCP count > high:
			Drain extra pages back to zone buddy list in bulk.
			If request was order=4 (16 pages > costly order):
		Skip PCP → go straight to buddy allocator.


Step-by-Step Free Path
	Step A: Reference counting
		Kernel decrements page->_refcount.
		If not zero → still in use (mapped somewhere). Stop.
		If zero → page is really free. Continue.
	Step B: Identify migration type
		From page->flags and page->alloc_flags:
		Anon/file → MIGRATE_MOVABLE.
		Slab cache → MIGRATE_RECLAIMABLE.
		DMA buffer → MIGRATE_CMA.
		Suppose our page is anon → MIGRATE_MOVABLE.
	Step C: Insert into buddy free_area
		We free PFN=20 into free_area[0][MIGRATE_MOVABLE].
		The buddy of PFN=20 is PFN=21 (flip lowest bit).
		Buddy math:
			buddy_pfn = pfn ^ (1 << order)
			= 20 ^ (1 << 0)
			= 20 ^ 1
			= 21
		Check if PFN=21 is free in same order/migrate list.
	Step D: Coalesce if possible
		Suppose PFN=21 is also free (in free_area[0]).
		Remove both PFN=20 and PFN=21.
		Combine into block [20–21], order=1.
		Insert into free_area[1][MIGRATE_MOVABLE].
		Now check buddy at order=1:
			buddy_pfn = 20 ^ (1 << 1)
			= 20 ^ 2
			= 22
			So our block [20–21] buddy is [22–23].
			If [22–23] is also free → merge into order=2 block [20–23].
			Repeat upward until MAX_ORDER or no buddy free.
	Step E: Final Insertion
		Suppose [22–23] was allocated → cannot merge further.
		So block [20–21] stays in free_area[1][MIGRATE_MOVABLE].

Practical Flow (PFN Example)
	Let’s say initially free lists look like this:
		free_area[0][MOVABLE] = { pfn=5, pfn=7, pfn=21 }
		free_area[1][MOVABLE] = { }
		Now freeing PFN=20:
			Insert 20 into order=0. Now {5,7,20,21}.
			Buddy(20) = 21 → found in list. Merge.
			Remove 20+21 → add block [20–21] at order=1.
				→ free_area[1] = {[20–21]}.
		Buddy([20–21]) = [22–23] → not free. Stop.

Final state:
	free_area[0][MOVABLE] = {5,7}
	free_area[1][MOVABLE] = {[20–21]}

When freeing a page, the kernel first decrements its refcount. If it drops to zero, the page is put into the appropriate per-CPU list or zone buddy list based on its migration type. The buddy of a page is found by XOR’ing its PFN with 1 << order. If that buddy is also free, both are removed and coalesced into the next higher order block. This repeats recursively up to the largest order possible. Finally, the resulting block is inserted into the zone’s free_area[order]. This ensures fast merging and reduces fragmentation. Special pages like THPs, slabs, or CMA have their own free paths but ultimately large allocators still rely on buddy coalescing."

Each VA is split into fields:
	VA[56:48] → PGD index  
	VA[47:39] → P4D index  
	VA[38:30] → PUD index  
	VA[29:21] → PMD index

Walk:
	CPU starts from mm_struct->pgd.
	Extract top bits (PGD index), find entry.
		Follow down through P4D → PUD → PMD.
		At PTE, you get PFN + flags.
		Add VA offset → physical address.
	This is the slow path. Fast path uses TLB cache.

If PMD entry has a "hugepage" bit set. Instead of pointing to a PTE table, PMD maps directly a 2MB contiguous range. VA split:
		VA[56:48] → PGD
		VA[47:39] → P4D
		VA[38:30] → PUD
		VA[29:21] → PMD
		VA[20:0]  → Offset within 2MB page
	Result:
	Skips the PTE level entirely.
	Saves one indirection, fewer TLB entries.

1GB Huge Page)

	Let’s walk through malloc + access example:

Each process has an mm_struct, which points to the root of its page tables (pgd) and describes its VMAs. On x86-64, virtual addresses are translated by a 4 or 5-level page table walk: PGD → P4D → PUD → PMD → PTE → PFN. Normally PTEs point to 4KB pages. But if the hugepage bit is set in PMD or PUD, the walk stops early, mapping a 2MB or 1GB hugepage. Transparent Huge Pages (THP) optimize anonymous memory to use PMD-level hugepages, while hugetlbfs allows explicit user control. This whole structure is managed per-process in mm_struct, but backed by the global buddy allocator that provides the physical frames.”

On x86, every page table entry has address bits and attribute bits packed together. Linux abstracts the attributes as pgprot_t. These include present, writable, user/supervisor, cache policy (PWT/PCD/PAT), Accessed/Dirty for page reclaim, PSE/PAT for hugepages, Global for kernel mappings, NX for security, and software bits for swap/protnone. For example, an anonymous heap page is present, RW, user, accessed, NX; a kernel linear mapping adds Global; and device memory disables caching. These flags tie directly to VMAs in mm_struct via vm_page_prot and are installed by the page fault handler when building PTEs.

Linux uses both hardware-defined and software-defined PTE bits. Hardware ones include Present, RW, User, Global, Cache Disable, PAT, NX, PSE for hugepages, and PKEY for memory protection keys. Software ones include soft-dirty for CRIU, uffd-wp for live migration, prot-none for NUMA balancing, devmap for device memory, and no-struct-page for DAX memory. Together, they let Linux distinguish normal RAM, device memory, swappable vs pinned, and track dirtying/migration. For example, a GPU buffer may be marked _PAGE_DEVMAP and unswappable, while a migrating anonymous page is temporarily _PAGE_PROTNONE to fault back in.

Each page table entry has hardware-defined flags like Present, RW, User, NX, Dirty, Accessed, PSE for hugepages, and caching controls (PWT, PCD, PAT). Present controls residency, RW/User control permissions, Accessed/Dirty track usage, NX enforces W^X, and PSE/PAT configure large pages and caching. Linux adds software-only bits like soft-dirty, uffd-wp, or prot-none for migration and checkpointing. Together, these make page tables not just address maps but also metadata for replacement, security, and performance.

Each process has an mm_struct describing its virtual address space. VMAs define ranges like heap, stack, or mmap regions. When a fault happens, the kernel resolves it by installing a PTE mapping VA → PFN. That PFN indexes into struct page, the kernel’s metadata for physical frames. For normal RAM, struct page always exists; for device memory, either no struct page (MMIO via ioremap) or fake ones in ZONE_DEVICE. malloc() uses brk/mmap to extend VMAs; actual pages appear only on access. ioremap() bypasses page cache, directly installs uncached PFN mappings for devices.Linux has multiple layers of flags. Hardware page table flags (PTE bits like RW, NX, PCD) directly control CPU access. The kernel abstracts these into PAGE_* combinations, which are derived from VMA flags like VM_READ/WRITE/EXEC. When a page fault occurs, the kernel walks the VMA, decides which PAGE_* flags to apply, and installs a PTE. This is done via functions like follow_pte, under spinlock, because page tables are shared structures modified in atomic contexts. Updates happen during page faults, fork, exec, mmap, reclaim, and are always synchronized with TLB shootdowns. Mutexes are avoided; spinlocks ensure fast, atomic access.

canonical x86-64 5-level kernel virtual address space layout (Linux ≥ 4.14 can use 5-level paging: 57-bit VA). Let’s carefully decode it and relate it to your questions:
	1. First Principles: Kernel vs User Split
		On x86-64, virtual address space is split into user and kernel parts.
		By convention:
			Lower addresses → User space (0x0 up to TASK_SIZE, usually 0x00007fffffffffff for 48-bit VA).
			Higher addresses → Kernel space (ffff800000000000 upwards).
		This split is fixed per architecture (but kernel can choose base of its mappings within that high half).
		Kernel never maps into low addresses, because that would risk userspace/kernel confusion (except legacy vsyscall page at 0xffffffffff600000).
		So: Kernel is always top half, user always bottom half — contiguous in VA terms, but with holes.

Kernel Virtual Address Layout
	(a) 0xffffffffff600000 – vsyscall page (8 MiB)
		A single legacy virtual syscall page, mapped into userspace but actually kernel-controlled. Exposed for very fast syscalls (gettimeofday, getcpu). Nowadays mostly disabled, replaced by vDSO.
	(b) 0xffffffffc0000000 – Module mapping space (~1 GiB):
		Dynamically loaded kernel modules are placed here. Backed by vmalloc area (non-contiguous physical memory, contiguous virtual mapping). Allocated via module_alloc() → internally uses vmalloc. Non-direct mapping, i.e., CPU must walk page tables.
	(c) 0xffffffff80000000 – Kernel text mapping (~1 GiB)
		The core kernel image (text + rodata + data + bss). This is direct mapped to the kernel’s physical pages, but relocated at boot (KASLR). Mapped read-only + executable for text, read-only for rodata, etc. This is where the kernel instructions run from.
	(d) 0xfffffe0000000000 – EFI region mapping space (~64 GiB)
		Used to access firmware tables/memory maps in EFI machines. Backed by ioremap.
	(e) 0xfffffe8000000000 – espfix stacks (~0.5 TiB)
		Espfix is an x86 quirk: when returning from syscall/sysenter with 16-bit segments, we need per-CPU stacks to avoid privilege leaks. Rarely used, but space is reserved.
	(f) 0xfffffe8000000000 – CPU entry area (~0.5 TiB)
		Special per-CPU trampoline mappings for IDT, GDT, TSS, exception stacks. Mapped identically for all CPUs, but per-CPU content. Needed for fast entry/exit from kernel.
	(g) 0xffd0000000000000 – KASAN shadow memory (~8 PiB!)
		Kernel Address Sanitizer reserves a shadow mapping. Each real byte of memory has a shadow byte to track poisoning. Huge virtual address space, but mostly holes — only a small fraction backed. Not present unless KASAN is enabled.
	(h) 0xffd4400000000000 – Virtual memory map (~0.5 PiB)
		The vmemmap area. This is a virtual linear array of struct page objects for each PFN. Maps metadata (struct page) not actual memory. Allows pfn_to_page() and page_to_pfn() to work efficiently.
	(i) 0xffd2000000000000 – vmalloc/ioremap space (~12 PiB)
		For allocations via vmalloc(), ioremap(), vmap(). These are virtually contiguous but physically discontiguous. Example: device MMIO regions via ioremap get mapped here.
	(j) 0xffc0000000000000 – Direct mapping (~32 PiB)
		The "physmap". Every physical page in the system has a linear kernel VA mapping here:
			virt = phys + PAGE_OFFSET
		Used for normal page access: the kernel can access physical RAM directly. This is 1:1 mapping with an offset.
			For example: PFN 0x12345 → 0xffff888001234500.
		But: device memory/MMIO is not included here (only RAM).
	(k) 0xffb0000000000000 – LDT remap for PTI (~0.25 PiB)
		Page Table Isolation (Meltdown fix) remaps LDTs here. Technical detail for user↔kernel isolation.
	(l) 0xffa0000000000000 – Hypervisor reserved (~4 PiB)
		Reserved for Xen/KVM hypervisors. May map hypervisor structures or paravirtualization data.

Kernel space is physically non contiguous directly mapped, virtually contiguous, always pinned but user space is demand paged, virtually and physically non contiguous indirect mapped, swappable, zramable, mmaped and lazily mapped .

Kernel direct map is virtually contiguous and gives illusion of physical contiguity, but underlying RAM is not physically contiguous. Kernel is not swappable.

User space = VMA illusion, physically scattered, demand-paged, swappable.

Process switch / thread switch / PASID
	User space portion (per-process mm_struct)
		Each process has its own page table root (pgd → cr3 on x86, ttbr0 on ARM).
		On context switch (switch_mm()), the kernel switches the user page table root to the new process.
		That means all user-space mappings of the old process vanish (from MMU point of view) and the new process’s mappings appear.
	Kernel space portion
		Kernel mappings (direct map, vmalloc, ioremap, modules, etc.) are identical across all processes.
		On x86: the upper half of the virtual address space is shared. On ARM64: TTBR1 holds kernel mappings.
		So kernel space is not flushed / replaced during process switch.

Threads
	Threads share the same mm_struct (and hence the same page tables) → no new CR3 switch needed, just a different kernel stack pointer.
	PASID (Process Address Space ID for devices / SVM)
	For devices with SMMUv3/IOMMU+PASID: similar concept.
	Each PASID corresponds to a process page table for device DMA.
	When a device issues memory requests with PASID, the IOMMU translates using per-process page tables.
	Kernel space mappings are not per-PASID — devices generally don’t touch kernel direct map (except via dma_alloc_coherent).

On KPTI (Kernel Page Table Isolation) systems, kernel mappings are minimized when running in user mode, but still exist in parallel.

Early Initialization of Memory (bootstrapping page tables)
	Problem: At reset, the CPU starts in a mode with no MMU enabled (real mode on x86, EL3/EL2 identity mappings on ARM). But the kernel wants to run with virtual addresses → it must bootstrap its own page tables.
	Step 1. Bootloader stage
		Bootloader (GRUB, U-Boot, firmware) may identity-map some early physical memory so kernel code can run. Kernel entry code runs in physical addressing mode or minimal 1:1 mapping.
	Step 2. Kernel builds early page tables
		Before the full buddy allocator/slab are online, the kernel uses statically reserved arrays in .bss for page tables. These early page tables:
			Identity-map low memory needed for boot.
			Also create the direct map region (all RAM virtually linear).
			Map kernel text/data (link-time addresses).
	Step 3. Key structures
		swapper_pg_dir
		The first top-level page table for the kernel (statically allocated in arch/x86/kernel/head_64.S).
		Populated at boot with identity mappings + kernel virtual base.
		This becomes the initial cr3/ttbr1 value for all CPUs.
		early_pgt_alloc()
			Allocator used before buddy/slab are ready.
			Just carves memory out of a bump allocator (memblock) to create page tables.
			Only used for boot page tables.
		init_mm
			The kernel’s own mm_struct.
			Unlike process mm_structs, this doesn’t represent a user process — it’s used for global kernel mappings.
			init_mm.pgd = swapper_pg_dir.
			When no process is running (idle task), CPU uses init_mm.
	Step 4. Running without page tables?
		When MMU is disabled, CPU interprets addresses as physical → kernel entry code is linked at a low physical address to run identity-mapped.
		Kernel enables paging only after setting up swapper_pg_dir.
		At that moment, execution continues seamlessly because code/data are mapped both physically and virtually to the same place (identity map overlap).
	Step 5. Transition to normal
		Once buddy allocator is online, kernel can alloc_pages() for page tables normally.
		Old boot-time mappings are replaced/expanded into the full virtual memory map.
		But swapper_pg_dir remains the base for kernel space.

init_mm is kernel’s mm_struct, not tied to any process.

How is vmalloc different than kmalloc ? Does vmalloc have slab, slub, slob etc. and does it work using buddy allocator ? Does vmalloc do lazy allocation like mmap and populated PTE only after that memory is touched and gradually allocates physical pages in sequence/granularity of 4kb ?
	kmalloc()
		Purpose: Allocate small to medium memory chunks inside the kernel (bytes to a few MB).
	How:
		Backed by slab allocators (slab, slub, slob) on top of the buddy allocator.
		kmalloc tries to allocate physically contiguous memory for each object (because devices often want contiguous DMA buffers).
	Properties:
		Memory is physically contiguous + virtually contiguous (one-to-one linear mapping via direct map). Allocations are typically ≤ 2 MB, otherwise fail (because large contiguous chunks are rare). High-perf, low overhead.

vmalloc()
	Purpose: Allocate large regions in kernel that don’t require physical contiguity.
	How:
		Creates a virtually contiguous mapping in a special vmalloc region of kernel VA.
		Underneath, backs the mapping with non-contiguous physical pages from the buddy allocator.
		Each physical page is mapped into a contiguous virtual address range by filling in PTEs.
	Does vmalloc use slab/slub/slob?
		❌ No. Slab/SLUB/SLOB are object caches used for kmalloc. vmalloc works directly with pages from the buddy allocator and sets up page table entries in the vmalloc region.
		So it bypasses slab caches.
	Lazy allocation like mmap?
		❌ No, not really. vmalloc does eager allocation:
			When you call vmalloc(size), the kernel immediately allocates pages from buddy (non-contiguous physical pages). Then it creates PTEs mapping them contiguously in the vmalloc VA space. Unlike mmap, which installs only a VMA and faults in physical pages on first access, vmalloc allocates backing pages right away.
	Exception: vmalloc_user() + remap_vmalloc_range() can behave closer to mmap for user-mappable memory, but still not demand-paged.
	Granularity:
		Always page-sized (4 KB). It chops your request into page units and maps each individually. No hugepage backing unless explicitly managed.
	Cost:
		Slower than kmalloc because:
		Needs to allocate non-contiguous physical pages.
		Sets up page tables for the new kernel VA range.
		Invalidates/rebuilds TLB mappings (expensive).
	So vmalloc = virtually contiguous, physically scattered allocation built directly from buddy pages.

Comparing with mmap
	mmap (userspace): lazy, no physical pages allocated until page fault → demand-paged.
	vmalloc (kernel): not lazy; it allocates physical pages and sets up page tables immediately.

Why vmalloc can't be used DMA and DMA alloc coherent is needed ? Can SMMU provide translation using scatter gather ?
	Physical contiguity requirement (most devices): A DMA device does not understand virtual addresses. It issues transactions with IOVAs or physical addresses on the bus. With vmalloc, the kernel VA range is contiguous, but the underlying PFNs are scattered. Unless there’s an IOMMU to remap each page, the device would see nonsense jumps in PA.
	Cache & coherence
		vmalloc does not guarantee cacheability attributes (write-back, uncached, coherent). Devices need strongly defined caching behavior, especially coherent DMA (CPU + device see same memory).
	dma_alloc_coherent() sets up pages with proper cache attributes and flush/invalidate if needed.
	Addressability & constraints
		Many devices have addressing limits (e.g., only 32-bit IOVA, must be below 4GB).
		vmalloc does not respect device DMA masks or CMA zones.
		dma_alloc_coherent() ensures allocations come from suitable zone (ZONE_DMA, ZONE_DMA32, CMA).
	How dma_alloc_coherent() solves it
		Allocates physically contiguous pages from the buddy allocator or CMA.
		Sets the correct memory attributes (uncached or write-combined if required).
	Returns:
		CPU VA (kernel linear map of the pages).
		DMA address (PA or IOVA) suitable for the device.
		Guaranteed safe for DMA.
	Can SMMU (or IOMMU) fix this?
		Yes — but with scatter-gather tables.
	With an IOMMU/SMMU:
		The kernel can map a set of discontiguous physical pages (like those from 	vmalloc) into a contiguous IOVA range for the device.
	Achieved via APIs:
		dma_map_page() / dma_map_sg() → setup scatter-gather translation. The IOMMU then translates each device DMA access into the right physical page.
	Even with IOMMU, vmalloc is rarely used for DMA because: It lacks coherent attributes. Scatter-gather mappings add overhead. Not every device can handle large SG lists. Instead, use dma_map_sg() on pages you explicitly control.

Scatter-Gather in practice
	Many high-end NICs, NVMe, and GPUs can DMA into scatter-gather buffers. Driver provides SG list (physical addresses of each page). With IOMMU, kernel programs SG list into IOMMU → device sees it as one contiguous buffer. Without IOMMU, driver must pass SG list directly to device if it supports scatter-gather.

Bottom-up vs Top-down memory mapping
	When Linux sets up the direct physical memory map (linear map PAGE_OFFSET → RAM), it must lay down page tables.
	Bottom-up mapping
		Start mapping from lowest physical address (e.g., 0x0) upward.
		Typically used at very early boot, because we want to map the memory we are executing from and keep it simple.
		Ensures low memory (DMA zones, kernel image) are mapped first.
	Top-down mapping
		Start mapping from the highest available address downwards.
		Useful for high memory systems with sparse memory regions.
		Reduces fragmentation of large pages (1GB, 2MB), since mapping from high aligned ranges downward packs large pages more efficiently.

At init, kernel builds a full hierarchy.
	Why? Because hardware requires it:
		CR3 always points to a PGD (root).
		Even if you only use 1GiB huge pages, you still need valid entries at PGD → P4D → PUD to point to them.
	What happens is:
		For aligned regions, the kernel maps them at the largest possible level (1GiB if CPU supports, else 2MiB).
		So the hierarchy exists, but some intermediate tables are skipped (hugepage entries replace them).
	Example:
		If RAM = 0x0–0x40000000 (1GiB aligned), direct map entry may go:
		PGD → P4D → PUD (huge) → directly points to 1GiB block, skipping PMD/PTE.
		So you never have “flat 1-level tables” — but large mappings collapse the lower levels.

What is pgt_buf?
	Early boot problem: you don’t yet have buddy allocator or kmalloc().
	But you need memory to allocate new page tables (PGD/P4D/PUD/PMD pages).
		Solution = static early boot buffer: pgt_buf.
	Defined in arch/x86/mm/init.c.
	A reserved chunk of memory used only for boot-time page tables.
	Once the normal memory allocators come online, pgt_buf is no longer needed.
	Think of it as scratch space to allocate temporary page table pages before the full VM system is alive.

What is phys_p4d_init()?
	This is the helper that sets up physical address → virtual direct mapping at the P4D level.
		Called inside __kernel_physical_mapping_init().
	It checks whether a given range can be covered by a 1GiB hugepage mapping at P4D level.
		If yes → install a huge mapping entry directly.
		If no → go one level deeper (phys_pud_init()), eventually down to 4KiB if needed.
	So it’s recursive builder:
		phys_p4d_init() → phys_pud_init() → phys_pmd_init() → phys_pte_init().

Relationship of all this with init_mm
	init_mm.pgd points to swapper_pg_dir (kernel’s master page table).
	During __kernel_physical_mapping_init():
		Helpers like phys_p4d_init populate this hierarchy with direct map entries.
		pgt_buf provides early pages for PGD/P4D/etc.
		save_mr() records what mappings got installed.
	When boot finishes:
		init_mm = fully populated kernel page tables (direct map, vmalloc, fixmap, etc.)
		Every process inherits kernel space entries from init_mm into its own pgd.

init_mm: kernel’s permanent mm_struct.

struct vm_struct
	Used internally by the kernel’s vmalloc allocator.
	Lives in include/linux/vmalloc.h.
		Each vmalloc’ed region is tracked in a global linked list (and later also an rbtree) of vm_structs.
	Fields:
		addr: starting virtual address (contiguous in kernel virtual space).
		size: total size of block.
		flags: vmalloc flags (like VM_ALLOC, VM_IOREMAP, VM_USERMAP, etc. from your screenshot).
		pages: array of pointers to struct page * backing the block. This is how non-contiguous physical pages get stitched together.
		nr_pages: how many base pages span the allocation.
		caller: debugging (which function called vmalloc).
		page_order: nonzero if hugepages used.
	It does not describe user processes; it only tracks kernel vmalloc space.

struct vm_area_struct (VMA)
	Completely different: used by the memory manager for user processes.
		Each mm_struct (a process’s address space) has a red-black tree or linked list of vm_area_structs.
		Describes userland mappings (text, heap, stack, mmap() regions).
			Fields: vm_start, vm_end, vm_flags, vm_file, etc.
		VMAs are inserted into an rbtree per-process, keyed by virtual address range.

vm_struct = kernel bookkeeping for vmalloc areas.
vm_area_struct = per-process mapping descriptors.
	They are unrelated data structures.

Kernel Boot & Early Memory Init
	BIOS/UEFI / Bootloader (GRUB, UEFI stub):
	Loads kernel binary into RAM at some physical address (e.g., 0x100000).
	Provides memory map (usable vs reserved regions) via e820 / EFI memory map.
	Kernel Early Init:
		Uses memblock to track available vs reserved RAM.

Does vmalloc use first-fit?
	Yes — vmalloc uses a first-fit strategy for virtual address space allocation.
	Why?
		vmalloc allocates virtual contiguous space, not physical.
		The virtual VMALLOC range is finite (e.g. ~32TB on x86_64).
			Since fragmentation can build up, a first-fit scan is simple and guarantees O(log n) search using the underlying tree.
	More complex policies (best-fit, worst-fit) are not worth the CPU overhead, since the critical cost is mapping scattered physical pages, not finding virtual space.

task_struct
	Thread = task_struct + new kernel stack, shares mm_struct + files_struct.
	Process = task_struct + new mm_struct + new files_struct.
Both are task_structs → same scheduler, same syscalls.
Threads are lighter because they avoid duplicating mm_struct & files_struct.

Caveat: Bugs in one thread (segfault, corruption) crash the whole process, since memory is shared.

A thread is just a new task_struct sharing mm_struct and files_struct with its parent; a process has its own mm_struct and files_struct.
	Lifecycle is clone() → new task_struct → scheduler runs it, with shared or private resources depending on flags.

Action        | Threads                  | Processes
──────────────┼──────────────────────────┼─────────────────────────
malloc()      | Shared mm_struct         | New mm_struct (COW copy)
              | Both threads see same VA | Child has its own VA space
──────────────┼──────────────────────────┼─────────────────────────
open()        | Shared files_struct      | Copy of files_struct
              | fd visible to all        | fd numbers same but independent refcount
──────────────┼──────────────────────────┼─────────────────────────
mmap(fd)      | Shared VMA               | Private VMA in child only
              | All threads see mapping  | Parent unaware
──────────────┼──────────────────────────┼─────────────────────────
free()        | Affects all threads      | Affects only that process
──────────────┼──────────────────────────┼─────────────────────────
exit()        | pthread_exit kills one   | exit() kills process only
              | exit() kills all threads | Children independent

Threads:
	Share heap, stack mappings (different stacks but in same mm_struct).
	Race conditions: one thread free()ing memory while another uses it crashes whole process.
	File descriptors are live-shared (close/read/write seen by all).
Processes:
	Memory is isolated: cannot touch each other’s mallocs or mmaps.
	Fds are copied but independent (close doesn’t kill parent’s fd).
	IPC required to share data (pipes, sockets, shm).
PID vs TGID:
	Each thread has its own pid.
	All threads share one tgid (the “process ID” visible to ps/top).

Final Mental Model
	THREADS
	  task_struct[tid1] ─┐
	  task_struct[tid2] ─┤ → mm_struct (shared)
	  task_struct[tid3] ─┤ → files_struct (shared)
						 └→ all share heap, fds, VMAs
	PROCESSES
	  task_struct[pid1] → mm_struct (private)
	  task_struct[pid2] → mm_struct (private)
	  task_struct[pid3] → mm_struct (private)
	  each has own heap, VMAs
	  fd tables copied, not live-shared

Threads = multiple schedulable entities (task_structs) inside one process, sharing mm_struct and files_struct.
Processes = independent task_structs with their own mm_struct and (copied) files_struct.


Memory Split on ARMv8/9
	TTBR0_EL1 → page tables for user space (per-process).
	TTBR1_EL1 → page tables for kernel space (shared across all processes).
	So:
		Process A has its own TTBR0_EL1.
		Process B has its own TTBR0_EL1.
	Kernel space (TTBR1_EL1) is the same for all.
Context switch: Process vs Thread
	Switching between Processes
		Scheduler switches from task_struct[P1] → task_struct[P2].
		Updates TTBR0_EL1 to point to P2’s page tables.
		TLB flushed (or ASID-based invalidation used).
		Device PASIDs may need re-binding (if SVM enabled).
	Heavyweight: entire user VA mapping replaced.
		Switching between Threads (same process)
		Scheduler switches from task_struct[T1] → task_struct[T2].
	Both share same mm_struct → same page tables → same TTBR0_EL1.
	No MMU page table switch needed.
	Only CPU registers (thread_struct) and kernel stack pointer swapped.
	Lightweight: no page table/TLB shootdown.

SMMU v3 + PASID
	PASID (Process Address Space ID): lets devices identify which process’s page tables to use. With PASID + SVM (Shared Virtual Memory):
		Device submits DMA with {IOVA=VA, PASID=N}.
		SMMU looks up PASID→mm_struct→process’s TTBR0_EL1.
		Device gets same VA→PA translations as CPU.
	Processes:
		Process A (PASID=10) → SMMU maps TTBR0_EL1(A).
		Process B (PASID=11) → SMMU maps TTBR0_EL1(B).
		Device can access buffers in A or B, depending on PASID.
	Threads:
		Thread T1 and T2 in same process share mm_struct → same TTBR0_EL1 → same PASID.
		Device sees them as one address space.
		Threads are invisible to SMMU/PASID — device only cares about the mm_struct (process address space).

ATS, PRI, ATC Interaction
	ATS (Address Translation Service): device asks SMMU for VA→PA translation.
	ATC (Address Translation Cache): device caches VA→PA like a TLB.
	PRI (Page Request Interface): if device faults (page not present), it notifies CPU.
	For Processes:
		ATS/PRI requests tied to PASID (process-specific).
		If Process A page-faults → CPU loads PFN into its page table (TTBR0_EL1(A)).
	For Threads:
		Since threads share TTBR0_EL1, device sees no distinction.
		If T1 mallocs memory, T2 can access it, and device (via PASID) can too.

Caveats:
	Threads don’t trigger MMU switches → only task_struct switch.
	Processes always switch TTBR0_EL1 → expensive (TLB flushes, ASID use).
	Kernel space (TTBR1_EL1) never changes → stable across all. It is always shared and pinned.
	SMMU PASID is per-process (mm_struct), not per-thread.
	Thread-local storage (TLS) is tracked in thread_struct, not mm_struct → threads still have private registers/stacks.
	Device faults (PRI) are per-process → device can’t tell which thread caused it.

MAP_ANONYMOUS
	Means: no file backing.
	Pages have no inode, no struct file.
		Kernel sets vma->vm_file = NULL.
	The memory is anonymous → not linked to any file in the filesystem.
	Backing store is swap/zram if evicted.
	Used for:
		Heap (malloc → mmap with MAP_ANON for large allocations).
		Stacks (pthread_create stacks are MAP_ANON).
		Scratch buffers.
	Caveat:
		You must also pass MAP_PRIVATE, because MAP_ANON doesn’t imply sharing semantics.

MAP_PRIVATE
	Means: copy-on-write mapping.
	If backed by a file:
		Reads come from the file/page cache. Writes do not go back to the file → they trigger a private COW copy (anonymous page).
	If backed by anonymous memory (MAP_ANON):
		Just means the mapping is private to the process.
	Used for:
		Normal malloc memory (MAP_PRIVATE | MAP_ANON).
			File mappings where you want read-only file data but private modifications (mmap(fd, …, MAP_PRIVATE)).
	Caveat:
		MAP_PRIVATE mappings are never written back to the underlying file.

MAP_SHARED
	Opposite of MAP_PRIVATE.
	Writes are visible to all processes mapping the file.
	Writes go back to the file/page cache → can persist to disk.

Practical Examples
	Example A: Anonymous malloc
			p = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
					MAP_ANON|MAP_PRIVATE, -1, 0);
		MAP_ANON: no file.
		MAP_PRIVATE: memory private to process.
		Backed by swap if needed.
	Example B: File-backed, private
			fd = open("config.txt", O_RDONLY);
		p = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
				MAP_PRIVATE, fd, 0);
		MAP_PRIVATE: file contents mapped read-only.
		On write: private COW copy, not reflected in file.
	Example C: File-backed, shared
		fd = open("shared.dat", O_RDWR);
		p = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
				MAP_SHARED, fd, 0);
			MAP_SHARED: modifications propagate to file and to other processes mapping it.

MAP_ANON always implies no file. You must pass fd = -1.

MAP_PRIVATE does not mean anonymous → it can still map files (COW).

malloc() large allocations → mmap(MAP_ANON|MAP_PRIVATE) under the hood.

Heap via brk() vs mmap() are both anonymous+private, just managed differently.

Are user space and kernel space “different processes”?
	No. A process is always one entity: task_struct in the kernel.
	It has:
		User space execution context: code, heap, stack, mm_struct.
		Kernel space execution context: kernel stack, saved registers, file tables, signals, etc.
		When a process does a syscall or page fault:
			It switches mode from user → kernel (via exception/EL transition).
			It does not become a different process.
		The same task_struct runs, just in a different privilege level.

Are they orthogonal?
	User space = memory and instructions at EL0 (ARMv8/9).
	Kernel space = memory and instructions at EL1 (Linux kernel).
	Both belong to the same process, but:
		User space mappings → in TTBR0_EL1 page tables (per-process, swappable).
		Kernel space mappings → in TTBR1_EL1 (shared across all, pinned).
	Orthogonal in address space and privilege level, but linked via task_struct.

Is the scheduler the same?
	Yes. Linux has a single scheduler that schedules task_structs. Each task_struct can execute either:
		in user mode (EL0), or
		in kernel mode (EL1) when inside a syscall/interrupt handler.
	Scheduler does not care if the thread is “in user” or “in kernel” — it sees only runnable tasks.

Kernel threads vs user processes
	User processes:
		Have both user+kernel contexts.
		Run in user mode most of the time.
		Switch to kernel mode for syscalls, faults, page faults, etc.
	Kernel threads (kthreads):
		Only exist in kernel space.
		mm_struct = NULL (no user mappings).
		Examples: kswapd, khugepaged, ksoftirqd.
		Always run in EL1.

Who gets prioritized?
	By default: same scheduler policies.
		CFS (Completely Fair Scheduler) → for normal tasks.
		RT scheduler (SCHED_FIFO, SCHED_RR) → for real-time.
		Deadline scheduler → for real-time deadline tasks.
		Kernel threads usually run at normal priority, but some (like watchdog, rcu) can run at higher priority.
		User tasks can adjust priority with nice values or real-time policies.
	No intrinsic “kernel > user” priority — they’re all just tasks.
	But:
		An interrupt handler (hardirq) always preempts everything.
		A softirq or kernel thread handling critical events can delay user processes.

Nice value
	Nice value = user-visible priority hint (−20 to +19).
	Works only for normal CFS tasks (user processes or kernel threads scheduled under CFS).
	Not only for kernel — applies to both user tasks and kernel threads if they use CFS.
	Doesn’t affect RT or deadline tasks.

task_struct ties together:
	mm_struct (user mappings: brk, mmap, swap/zram).
	files_struct (fd table).
	signal_struct (signals).
	thread_struct (registers).

Scheduler decides which task_struct runs.
	When in user mode:
		Runs user instructions.
	Page faults may occur → kernel switches in, allocates PFNs, updates PTEs.
	When in kernel mode:
		The same task_struct is running, but using kernel stack.
		Example: malloc → brk → page fault → kernel allocates PFN → returns to user.

For kernel threads (like kswapd):
	No user mm_struct.
	Still task_struct, scheduled like everyone else.
	Handles things like reclaiming swap/zram pages for user processes.

Watermarks & reclaim interaction
	User processes allocate memory (malloc, mmap).
		If under pressure → kswapd (kernel thread) runs, tries to reclaim pages.
		If still low → direct reclaim happens in context of the user task itself.
		If still failing → OOM killer may kill some user tasks.
	Scheduler ensures both user tasks and kswapd (kernel) get CPU time.
		But user memory allocations can be throttled by kernel reclaim threads.

Big Caveats (Interview traps)
	User vs kernel is not two processes → just two modes of execution of one task_struct.
	Kernel threads are true kernel-only processes (mm=NULL).
	Scheduler is unified: it doesn’t care if a task is in EL0 or EL1.
	Nice value is not kernel-only: it applies to any CFS task (user or kernel).
	Interrupts preempt tasks: kernel code from IRQs runs immediately, outside scheduler.
	Priority inversions can occur → solved via RT scheduler, priority inheritance.

	[User process] (PID=1000, task_struct)

	   ├─ files_struct (fd table)

	   └─ thread_struct (registers)

	Modes of execution:
	   EL0 (user space)
		  - code, heap, stack

	   EL1 (kernel space, same task_struct)

	   ├─ mm_struct = NULL
	   ├─ kernel stack only

	Scheduler (unified)
	   - Picks runnable task_structs (user or kernel)
	   - Uses CFS/RT/Deadline policies
	   - Nice values for CFS tasks
	   - Kernel threads usually normal priority
	   - Interrupts always preempt

	Outcome:
	   - No "user vs kernel scheduler"
	   - Both share CPU time fairly
	   - Kernel threads may help user tasks (kswapd freeing pages)
	   - Reclaim, swap, zram, THP collapse all run in kernel context but triggered by user actions

Kernel boot sequence:
	1. Reset and CPU bootstrap (ARMv8/ARMv9)
		After reset, ARM core starts in EL3 (Secure Monitor) or EL2 (Hypervisor) depending on config.
		Boot ROM (firmware) runs → loads bootloader into RAM.
		Bootloader (U-Boot, TF-A, etc.):
		Initializes DRAM controller.
		Sets up minimal MMU mappings (identity maps).
		Loads Linux kernel image (zImage or Image) into RAM.
		Passes DTB (Device Tree Blob) or ACPI tables to kernel.
		Jumps to kernel entry at EL2 or EL1.
			Caveat: At this stage, only a flat physical map is used. No full virtual memory yet.
	2. Early kernel entry
		Kernel starts at _start in head.S.
		Switches CPU to EL1 (kernel mode) if not already.
		Initializes:
			Exception vectors (to handle faults).
			init_pg_dir (bootstrap page tables).
			Maps kernel image (text, rodata, data, bss) using large block mappings (1GB/2MB).
			Creates a minimal direct map (linear map): VA→PA identity for RAM.
		This is early identity mapping: kernel can now execute in VA space.
			Caveat: At this point, only kernel mappings (TTBR1_EL1) exist. TTBR0_EL1 (user) is empty.
	3. Early memory initialization
		memblock allocator:
			Tracks usable physical memory (from DTB).
			Used for early allocations (before buddy/slab ready).
			Sections, subsections:
				Memory carved into sections (e.g., 128MB each).
				mem_section[] built.
			Zones (DMA, Normal, HighMem, Movable):
				Pages categorized into zones.
			Buddy allocator initialized:
				Every PFN wrapped in struct page.
				Free lists created by order (powers of 2).
			Now buddy can serve allocations (4KB–2MB).
				Caveat: Hugepages are not active yet, only normal pages.
	4. Kernel subsystems setup
		Slab/SLUB/SLOB allocators built on top of buddy.
		VM structures (mm_struct, vm_area_struct) initialized.
		Page cache subsystem ready (for file-backed pages).
		Swap/zram not active yet (needs block drivers).
		Interrupts and scheduler enabled:
			Scheduler now manages task_structs.
				First kernel threads created (init, kthreadd, kswapd, etc).
		Caveat: Before scheduler, kernel runs single-threaded. After scheduler, multiple kernel threads exist.
	5. Kernel threading begins
		First process (swapper/PID 0) = idle task, runs scheduler when no one else runs.
		Kernel threads created (via kernel_thread()):
			kthreadd → parent of all kernel threads.
			kswapd → handles page reclaim.
			khugepaged → collapses THPs.
			rcu, workqueue threads, etc.
			These are pure kernel-space tasks (mm=NULL).
	6. Init process start (PID 1)
		Kernel mounts root filesystem (from initrd or rootfs).
			Loads /sbin/init, /bin/init, or /bin/sh.
			do_execve() is called:
				Creates a new mm_struct for user process.
			Maps ELF segments:
				text → file-backed, MAP_PRIVATE.
				data → file-backed.
				bss → zero anon pages.
				stack → anon-private.
				heap → fresh brk region.
				Populates page tables (TTBR0_EL1 for user).
			PID=1 is born (systemd or init).
				Caveat: If init fails, kernel panics (“No init found”).
	7. Userspace starts
		PID 1 runs → spawns other processes:
			getty, login, system daemons.
			Shell (e.g., /bin/bash) eventually started.
			When you see a shell prompt:
			Your terminal is a user process.
			Has its mm_struct (with heap, stack, brk, mmap).
		Uses syscalls (read/write/open/mmap/brk) to talk to kernel.
		Kernel provides:
			Page faults → PFNs via buddy.
			fd → struct file → page cache.
			Swap/zram if pressure.
			Scheduler fairness.
			SMMU if devices need access.

Forever Caveats (high-value interview points)
	At boot, kernel runs with identity mapping → only later builds full multi-level page tables.
		memblock vs buddy: memblock is early allocator; buddy is runtime.
	User processes always need execve to start; fork only clones.
		execve destroys old mm_struct (so malloc memory before execve disappears).
	Kernel threads mm=NULL; user processes mm!=NULL.
		Scheduler is unified — kernel vs user are not separate.
	Anonymous pages can be swapped/zram’d; file-backed dropped.
		THP/khugepaged optimize anon mappings; hugetlbfs needs reservation.
	SMMU + PASID let devices share user address space.
		OOM killer only comes into play after everything else fails.

-------------------------------------------------------------
Overcommit Modes
-------------------------------------------------------------
	Mode 0 (Guess, default)
	   - Allow unless request > RAM+swap
	   - MAP_NORESERVE respected
	   - Risk: OOM later if PFNs exhausted

	Mode 1 (Always)
	   - Always allow
	   - Best for sparse allocations (DBs, scientific apps)
	   - Very risky, OOM more likely

	Mode 2 (Never)
	   - Strict: Committed_AS <= CommitLimit
	   - MAP_NORESERVE ignored
	   - Hugetlb mappings excluded (pre-reserved)

-------------------------------------------------------------
Lifecycle Example
-------------------------------------------------------------
	malloc(1GB)
	   → VIRT +1GB
	   → Committed_AS +1GB
	   → RSS unchanged

	first write (4KB)
	   → page fault
	   → buddy alloc PFN
	   → RSS +4KB

	fork()
	   → Child inherits VMAs
	   → Committed_AS += writable VMAs
	   → RSS unchanged (COW)

	touch child page
	   → COW fault
	   → new PFN allocated
	   → RSS grows

	pressure
	   → anon pages (heap, THP, anon mmap) → swap/zram
	   → file-backed pages dropped (reload later)
	   → hugetlb pages cannot swap (pinned)

Forever-Fit Caveats (Interview gold)
	Committed_AS ≠ RSS. Commit = promise, RSS = actual PFNs.
	Anon-private mappings (heap, stack, mmap) count towards commit.
	File-backed private mappings (MAP_PRIVATE libs) also count (COW potential).
	MAP_NORESERVE: skip commit in Guess/Always, not in Never.
	THP → anon, swappable, part of commit.
	hugetlbfs → outside commit, not swappable, must be reserved.
	Overcommit_Never = strictest, avoids OOM but can block malloc upfront.
	Swap/ZRAM only help anon pages, not file-backed.

VIRT = address space size,
RSS = actual PFNs,
Committed_AS = promises (demand-paged),
CommitLimit = cap (swap+ratio*RAM),
THP = anon, swappable, commit-accounted,
hugetlbfs = reserved, pinned, outside commit.

So why mmap sharing is dangerous and dma-buf is good ? If fd sharing itself can keep fd available even if original process dies, what is point of having dmabuf
	mmap-based sharing (file, shmem, memfd)
		How it works
			Create file or shmem (open, memfd_create, shm_open).
			Share fd with another process (via fork, dup, SCM_RIGHTS).
			Both processes mmap(fd) into their VA.
		Kernel struct file → inode/address_space → page cache is shared.
		Problems / Limitations
			CPU-centric: mmap sharing is perfect if only CPU processes need to share data. But devices (GPU, ISP, NIC, etc.) don’t speak “page cache” — they need scatter-gather lists and IOMMU mappings.
			Cache coherency: If you hand-shake pages to a device driver via get_user_pages(), you pin them. If the process dies without cleanup, those pages may remain pinned (resource leak).
			No unified fencing: Two processes may write/read same mmap region without a proper synchronization primitive (like futex). For devices, there’s no standard fencing mechanism to coordinate when a buffer is ready.
			Drivers reimplement wheel: Every driver would have to take a struct file, pin pages, set up IOMMU, handle cache sync. This leads to duplication, bugs, leaks.
			Security: With plain mmap + fd sharing, nothing prevents accidental/uncontrolled access. Devices would need to trust user pages they’re given.
	dma-buf-based sharing
		How it works
			A producer (exporter) allocates a buffer (often shmem, GEM, CMA, etc.).
			Exports it as a dma-buf fd → kernel struct file with f_op = dma_buf_ops.
			Other processes or drivers import that fd via dma_buf_attach().
			Kernel tracks all attachments (who has this buffer).
			Provides synchronization (dma_fence) so producer/consumer coordinate.
			Provides cache maintenance hooks for devices with different cache models.
		Advantages
			Device-agnostic sharing: Standard API across GPU, camera, display, V4L2, audio, etc. Any driver that understands dma-buf can attach to the same buffer without reinventing mapping/pinning.
			Unified lifetime: Buffer lives until the last fd or mapping goes away. Clean release path via dma-buf ->release().
			Avoids long-term pin leaks: dma-buf core manages page pinning/unpinning properly. Regular mmap+GUP is prone to “forever pinned pages.”
		Synchronization: dma-fence system coordinates producer/consumer (e.g., GPU rendering done → display engine can scanout). mmap gives you none of that.
		IOMMU/I/O ready: dma-buf easily integrates with SMMU/IOVA. Normal mmap regions are just VA↔page cache; drivers have to build scatterlists manually.
		Security/isolation: Devices only see dma-buf pages; kernel validates attachments. With raw mmap, device drivers might accept arbitrary user pointers (dangerous).

dma-buf sharing:
	Explicit device-to-device and device-to-user buffer sharing framework.
	Tracks buffer lifetime, pinning, IOMMU mappings, cache sync, fencing.
	Solves the "scatterlist/IOMMU/cache-coherency" nightmare once, in one place.

Why mmap sharing is “dangerous”
	Pinning with get_user_pages() can starve the system (pages become unswappable).
	No standard cleanup — if a process dies, kernel may not know whether pinned pages can safely be freed.
	Different devices have different DMA requirements (contiguous, aligned, uncached) → plain mmap can’t express these.
	Multiple drivers duplicating logic → more bugs.

Why dma-buf is “good”
	Standard cross-driver interface.
	Safe lifetime & cleanup.
	Built-in fencing/synchronization.
	Designed to work with IOMMUs (SMMU v3, PASID, etc.).
	Supports CPU access via mmap of the dma-buf fd, but with controlled lifetime.

mmap+fd: good for CPU-to-CPU shared memory; dangerous for device buffers (leaks, no sync, no cache mgmt).
dma-buf: purpose-built for cross-device zero-copy sharing; tracks lifetime, pinning, IOMMU mappings, sync.

VFIO is not “just dma-buf with ioctls” — it’s a framework for entire device passthrough: kernel hands over BARs + DMA mappings + resets, so userspace can run its own driver safely. With PASID/SVM, VFIO uses process page tables (TTBR0) instead of kernel-managed IOVAs (TTBR1 analogy), enabling true demand-paged DMA.
	1. BAR (Base Address Register) Mapping
		Kernel-driver model
		Kernel driver parses PCI config space, discovers BARs.
			Calls pci_iomap() → kernel maps BAR PA into kernel VA.
			User never sees BARs directly. Instead:
				Driver exposes ioctls → mmap() only if explicitly allowed.
				Usually device registers are abstracted (opaque to user).
	VFIO
		VFIO exposes BARs as mmap-able regions through ioctls.
		ioctl(VFIO_DEVICE_GET_REGION_INFO) returns offset + size for each BAR.
		Userspace calls mmap(fd, offset, size, …).
		Result:
			BAR physical memory (MMIO) is mapped directly into userspace VA.
			Userspace can read/write device registers without kernel mediation.
		Fast path: No ioctl/syscall overhead for register access.
		Caveat: Security relies on IOMMU + VFIO reset — otherwise malicious user could brick device/host.
	2. Device Reset
		Kernel-driver model
			Driver reset device at probe/remove using vendor-specific sequence or PCIe FLR (Function Level Reset).
			Userspace can’t reset device directly.
		VFIO
			VFIO requires reset capability before binding device.
		Two options:
			PCIe FLR (standard): VFIO triggers hardware reset.
			Vendor driver hook (e.g., mediated devices).
		When user process closes fd or crashes:
			VFIO core executes reset automatically.
			Ensures device returns to clean state for reuse.
		Why special? VFIO must guarantee host integrity even if userspace driver crashes.
	3. DMA Mapping
		Kernel-driver model
			User allocates buffer → driver gets VA.
			Driver calls get_user_pages() to pin pages, builds sglist.
			Driver calls dma_map_sg() to program IOMMU.
			Device sees IOVA, driver programs DMA queue.
			DMA lifetime tied to kernel driver.
		VFIO
			User allocates buffer (malloc/mmap).
			Issues ioctl(VFIO_IOMMU_MAP_DMA) with VA/size.
		VFIO:
			Pins user pages (pin_user_pages() → struct page).
			Programs IOMMU domain: iommu_map(iova, pa).
			Device bound to VFIO domain via iommu_attach_device().
		Result:
			Device can DMA directly to user memory.
		With PASID + PRI:
			No explicit pinning → device faults to kernel like CPU page fault.
			IOMMU uses process TTBR0 page tables.
		Difference: VFIO lets user dictate what memory is DMA-capable. In kernel model, driver owns this.

User bugs can wedge device; VFIO must reset on fd close.
Not all devices support FLR → unsafe for passthrough.
Not a replacement for dma-buf
VFIO is for whole device passthrough (VM, DPDK).
dma-buf still needed for fine-grained buffer sharing between multiple drivers (GPU ↔ display ↔ camera).

VFIO is special because it moves BAR access, reset, and DMA mapping control from kernel drivers into userspace, using the IOMMU (SMMU) as the safety net. Unlike normal drivers where the kernel owns SID+CB mappings, VFIO creates isolated IOMMU domains (or PASID per-process) so devices can DMA safely into user memory without kernel fast-path intervention.

What is an IOMMU group?
	Definition: The smallest set of devices that cannot be isolated from each other by the IOMMU.
		Some devices share the same SID.
		Some platforms tie multiple devices to the same reset line or MSI interrupt.
		Some bridges don’t support per-device isolation.
	Thus:
		If devices share SID/CB → they share one translation context → they are inseparable.
		The kernel enforces grouping them into one IOMMU group.

Why VFIO requires groups
	VFIO hands devices to untrusted userspace.
	If two devices share SID/CB but only one is assigned, user could DMA into the other device’s memory.
	If two devices share reset line, one user could affect the other’s device state.
	If MSI/MSI-X routing is shared, interrupts can be stolen.
	So VFIO says: “all devices in a group must be assigned together.”
		You open /dev/vfio/$GROUP.
		You can only pass the entire group to your VM/userspace driver.
		If group contains extra devices → you can’t use VFIO passthrough safely.

VFIO + SMMU sequence
	VFIO allocates an IOMMU domain (new page tables).
	VFIO calls iommu_attach_group() (instead of iommu_attach_device()).
	Group ensures all SIDs in that group are attached to the domain.
	Device SID(s) now translate via that domain’s CB(s).
	User maps memory via VFIO_IOMMU_MAP_DMA or PASID-SVM.
	SMMU translates DMA → PA, isolated from kernel & other userspace.

Caveats
	Coarse granularity
	Grouping can make some devices unpassthroughable.
		Example: GPU and display controller share one SID → you can’t give GPU alone to VM.
	Reset limitations
		Grouping is also about reset granularity: if two devices share a reset line, you must pass both.

PCIe ACS (Access Control Services)
	On PCIe systems, IOMMU groups reflect ACS isolation. Without ACS, devices behind same bridge are grouped.

SMMU quirks
	Some SoCs multiplex multiple peripherals onto one SID (cheaper hardware). VFIO can’t split them.

Security
	Assigning less than a full group breaks isolation guarantees → kernel forbids it.

	PCIe / SoC bus
	   |
	   +-- Device A (SID=0x10) ---\
	   +-- Device B (SID=0x10) ----> [ IOMMU Group G0 ]
	   +-- Device C (SID=0x20) ----> [ IOMMU Group G1 ]

	Kernel: creates groups based on SID/reset isolation
	   |
	   +-- VFIO user asks for G0 --> gets both A + B
	   +-- VFIO user asks for G1 --> gets C

Why can’t kernel just use physical addresses and need ioremap() ?
	On modern CPUs (ARMv8, ARMv9, x86, RISC-V), the CPU never fetches instructions/data using a “naked” PA.
	All loads/stores go through the MMU (Memory Management Unit), which expects a virtual address (VA).
	VA → PA translation is done using page tables (kernel VA space).
	If you try to dereference a raw PA in C code → the MMU won’t know how to translate it → you get a fault.
	So kernel must create a VA mapping for that PA before CPU can access the register.
		ioremap(phys_addr, size) does:
			Allocates a kernel VA region (in the vmalloc/ioremap space).
			Sets up page table entries mapping that VA → the requested PA.
			Marks it with correct memory attributes:
			Non-cacheable (Device-nGnRnE for ARMv8).
			Strongly ordered or write-combining depending on flags.
			Return = VA pointer you can safely dereference in C code.

            v

	CPU Memory Access Pipeline (ARMv8/ARMv9 as baseline)
	When CPU executes a load/store or fetch:

	Instruction VA (virtual address)
		   |
		   v
	 [MMU: VA → PA translation]
		   |
		   v
	 [Cache lookup using PA index/tag]
		   |
		   v
	 [If miss → fetch from memory controller / interconnect / device]
		So the order is: MMU first, then cache.
	Why?
		Cache must be tagged/indexed by physical address to maintain global coherence.
		If cache was tagged by VA, two processes with same VA but different PA would alias incorrectly.
		(Some CPUs have VIPT caches = Virtually Indexed, Physically Tagged — still require MMU for tag check).

What is DVM (Distributed Virtual Memory)?
	DVM is an ARM AMBA/CCI/CMN/CHI interconnect feature, not a Linux concept per se.
	Purpose: allow devices + CPUs to participate in the same coherence and translation ecosystem.
	In cache terms:
		Normally, CPU caches are kept coherent via snooping/interconnect protocols.
		Devices (DMA masters) either:
		Access memory uncached (device memory), or
		Use IOMMU (SMMU) + CPU-managed cache maintenance.
	With DVM messages:
		Devices can issue coherency/translation messages into the interconnect (like CPUs do).
		CPUs see DMA memory as coherent without explicit flushes.
		SMMU can snoop the same DVM stream to keep translations aligned.
	So DVM lets CPUs and devices share TLB/cache-like structures at the interconnect level.

	CPU Access Path:                Device Access Path:
	VA (user)                       IOVA or VA (with PASID)
	 |                               |
	 v                               v
	MMU (TTBR0/1)                   SMMU (SID/PASID → CB)
	 |                               |
	PA → Cache → DRAM               PA → DRAM
			^                           ^
			|--- DVM sync (TLB/cache ops)---|

DVM is a hardware mechanism for keeping MMU (CPU) and SMMU (device) TLBs coherent. It does not unify page tables (that’s SVM), but ensures consistency when mappings change. In SMMU terms, the master is the DMA-capable device (GPU, NIC, etc.), and the slave is system memory.

How eventfd is async and scales better than poll mechanism in iouring ?
	Eventfd is async because kernel increments a counter on events, and user consumes it later; unlike poll which just signals readiness once. It scales better because multiple completions coalesce into one signal (batching), which io_uring exploits to avoid syscall thrashing and achieve high IOPS.

Still I don't get how is it async ? Without polling how user gets notified ? Is there something like interrupt from kernel to user
	Eventfd is async because the kernel actively signals and wakes the task only when events occur, so the process doesn’t poll in a loop. It’s not a “hardware interrupt into user,” but a scheduler wakeup (via wait queues), just like IRQs wake CPUs. That’s why it scales better than raw poll, especially when batching (e.g., io_uring, VFIO IRQ delivery).

Why does KGSL uses mempool ? Can't it directly use vmalloc ?
	Short answer: KGSL (a GPU driver) uses a mempool because GPU workloads need predictable, fast, and (often) physically-appropriate allocations for DMA and real-time command submission. vmalloc() is flexible but not guaranteed under pressure, produces physically non-contiguous pages (bad for some HW), and can be too slow or unsuitable for kernel paths that must not block. A mempool gives a preallocated, reserved resource pool (or fast fallback) so the driver can allocate without deadlocks or falling into expensive slow paths.

Linux uses demand paging: malloc/brk/mmap just create VMAs in mm_struct and maybe commit accounting, but physical memory is allocated only on page fault. Overcommit policy (vm.overcommit_memory) decides how optimistic to be. VmSize is total VA space, VmRSS is resident physical pages, VmPeak is the max VmSize. PROT_NONE/readonly mappings don’t trigger demand paging because they can’t generate writable pages.

why fd vs mm_struct are orthogonal:

mm_struct is per-process memory space. Kernel threads don’t have one, so Linux uses lazy TLB: they borrow the last process’s mm_struct into active_mm to avoid TLB flushes. mmgrab/mmdrop keep page tables alive while borrowed. Kernel itself always runs in TTBR1_EL1 (kernel VA), so it doesn’t depend on user mm_struct.

So mmstruct is used only for user space vma ? What about mm ? What is active mm ? Explain all fields of task structure exhaustively with caveats 
	mm_struct is the kernel object that describes a user process’s virtual address space: it contains the VMA list/tree, a pointer to the page-table root (PGD), accounting (rss, vm_committed_as, etc.), locks, and other VM-related state. It is only about user-space address mappings and their metadata (VMAs). Kernel mappings live separately (the kernel is mapped into every address space via the kernel side of the page tables or via a different top-level mapping depending on architecture).
	mm in task_struct (i.e. task->mm) is simply a pointer to that process’s struct mm_struct. Kernel threads typically set task->mm = NULL (they don't have user-space mappings).
	active_mm is the struct mm_struct * that the kernel currently considers “active” for the CPU (used for lazy TLB handling). For a kernel thread (which has mm == NULL), active_mm points to the mm_struct of the last user process that ran on that CPU (so kernel code executing on that CPU still has valid page-table mappings in hardware and we avoid heavy TLB flushes). The kernel ensures the mm_struct referenced by active_mm has a reference count held (via mmgrab()/mmdrop()) while it’s being used this way.

High-level picture (how these fit together)
		task_struct (per thread)
		 ├─ mm (-> struct mm_struct)         : user vma + pgd root
		 └─ active_mm (-> struct mm_struct)  : last active mm (for lazy TLB)
		struct mm_struct
		 ├─ pgd (page-table root used by MMU TTBR registers)
		 ├─ mmap (vm_area_struct RB-tree/list)
		 ├─ mmap_sem / mmap_lock
		 ├─ mm_count / mm_users
		 ├─ rss_stat, total_vm, swap-related counters
		 └─ other vm accounting / flags
	On context switch:
		If next task has mm != prev->mm, kernel runs switch_mm() to change page-table base / ASID etc.
		If next task is a kernel thread (mm==NULL) kernel uses active_mm to keep previous mappings loaded (lazy TLB), while holding the mm reference.

			Used for getrusage / top / ps.
			cred->capabilities & task->seccomp etc. (affects resource access)
			Caveat: resource limits interplay with allocation calls (e.g., RLIMIT_AS) and can be used to limit overcommit.
	10) Control groups, scheduling groups, namespaces
		cgroups / cgroup_subsys_state pointers
			Which cgroup the task belongs to; used by controllers (memory, cpu, blkio). Memory cgroup integrates deeply with memory reclaim/oom.
		sched_task_group / cfs_rq pointers for scheduler groups.
			Caveat: cgroup v1 vs v2 differences: memory controller behavior differs (and interacts with OOM handling).
	11) Misc & kernel bookkeeping
		audit_context, perf_event lists, work_struct proxies, notifier lists, io_context for AIO, signal_on_exit hints.
		real_parent, group_leader, ptrace fields, child_reaper flags.
			Caveat: Many of these are optional or config-dependent (CONFIG_* options). Not all kernels have the same fields.
	How some of these fields are used in the common VM flows (connect to earlier discussion)
		Fork (copy-on-write):
			Kernel clones task_struct and creates a new mm_struct for the child (or reuses anon_vma chain semantics). It increments struct page refcounts for shared pages. mm_struct data (VMAs and PGD) are set up so both parent & child share page frames until a write fault triggers CoW.
		Execve (replace mm):
			Kernel tears down old mm_struct (decreasing mm refcounts), creates a fresh mm_struct with new VMAs built by ELF loader, installs new pgd and VM ranges, and then resumes (old mappings are freed).
		Context switch:
			switch_mm() consults task->mm. If mm != prev->mm, hardware page-table base (TTBR/CR3) is swapped and TLB actions performed. For kernel threads (mm==NULL), active_mm is used as the currently loaded mm; kernel holds a ref to ensure it remains valid.
		Page fault:
			do_page_fault() looks up current->mm->mmap (VMA RB tree) to locate the VMA that covers the fault address; checks permissions, then uses VMA’s vm_ops and the mapping (address_space or anon_vma) to populate a struct page / folio and install PTE.
		Filesystem / mmap:
			If a VMA is file-backed, vma->vm_file points to struct file and its back inode->i_mapping / address_space. Page-fault handler consults address_space to find or read a folio into pagecache and maps it.
		DMA-buf & userspace fd passing:
			Kernel uses files_struct and struct file to export/import struct dma_buf. Multiple processes each hold an fd that maps to the same struct file (shared struct dma_buf). Memory pinned and IOMMU mappings created are orthogonal to task->mm but interact when mapping to a process VA (mmap of the dma-buf).

Final caveats & interview tips
	mm_struct is about user-space mappings only. Kernel mappings are part of kernel memory and are present across tasks (TTBR1 or kernel region); mm_struct does not include kernel-only mappings.
	active_mm exists to avoid expensive TLB flushes when scheduling kernel threads; always remember mm reference counting (mm_count) must be held when using active_mm.
	Most task_struct fields are protected by locks / RCU; reading them unsafely (from other contexts) can race. Use kernel helpers (rcu_read_lock, get_task_struct, etc.) when inspecting externally.
	task_struct is huge; learn the logical groups, not every field. Understand which fields are per-thread and which represent per-process shared state (signals struct, files, mm in threads).

mm_struct describes only the user-space part of the address space. But the kernel mappings (VMAs for kernel regions) are not stored in every process’s mm_struct — they live in separate kernel-global structures.

mm_struct tracks only user-space VMAs. Kernel-space mappings (vmalloc, modules, ioremap, fixmap, linear map) are managed by separate global kernel structures like vmap_area trees, not per-process mm_struct. TTBR1_EL1 keeps kernel mappings always active, so kernel threads can run without an mm_struct.

In SMMU — does stall mean dead end?
	SMMU (Arm System MMU) translates IOVA → PA for devices. If a device issues DMA to an IOVA not present in SMMU’s page tables, it raises a translation fault.
	Two handling modes:
		Stall mode
			The SMMU halts the device’s transaction. It signals the fault up to the OS/IOMMU driver. The OS can then:
				Map the missing page (like demand paging for devices if PRI/SVM supported).
				Or kill the offending context.
			If the OS doesn’t resolve it, the device is effectively stuck. Recovery depends on hardware + driver. Some devices retry after mapping, others wedge.
		Abort mode (non-stall)
			The SMMU just drops the transaction and signals error to the device (e.g., PCIe UR response).
		Device keeps running, but that access failed.
	So stall ≠ permanent dead end, but it does block forward progress until the kernel/IOMMU resolves it. Without PRI/ATS support, stall can feel like a dead end because the device cannot resume safely.

So without pri or svm, device can never access unmapped region ? How svm helps apart from pri ?  If I want to make device access for unmapped region without pri svm, then I have to reboot kernel and change SMMU mapping programming from cpu, is it only way ?
	Without PRI/SVM
			Device does DMA using IOVA. SMMU (stage-2 page tables) translates IOVA → PA. If translation missing:
				With Stall enabled → device halts until OS resolves.
				Without Stall → transaction aborted, error sent to device.
		Key point:
			Device cannot generate a page fault on its own.
			Only CPU can update SMMU page tables.
		That means:
			Device cannot access unmapped memory regions.
			If you later want it to access, CPU must explicitly program the SMMU (via kernel driver).
			Yes — if your driver never maps, device will forever be stuck on that IOVA.
	With PRI (Page Request Interface)
		Device raises a page request when it touches an unmapped IOVA. This request goes up the PCIe PRI queue → OS IOMMU driver. Kernel handles it like a page fault:
			Allocates memory or installs mapping in SMMU tables.
			Device retries → now succeeds.
		PRI = allows on-demand paging for devices, like demand paging for CPU.

With SVM (Shared Virtual Memory)
	Extends PRI by sharing process address space between CPU and device:
		Device gets a PASID (Process Address Space ID).
		PASID maps to the same page tables as that process’s CPU mm_struct.
	Now device and CPU see same virtual addresses.
		Page faults raised by device (via PRI) are resolved using CPU’s page tables.
	SVM = unifies VA space.
		CPU and device both use same mm_struct / pgd / PTE.
		Eliminates need for driver to maintain separate IOVA mappings.

What if no PRI/SVM and device needs unmapped memory?
	Only option: CPU pre-programs SMMU mappings in advance.
	Typically done by kernel driver when allocating DMA buffer (dma_map_*).
	If device ever goes outside → it will fail (stall or abort).
	You cannot “auto-recover” like CPU demand paging.
	If mappings are missing at runtime, only kernel (CPU) can update them.
	You don’t need to reboot kernel.
	But you must go back into driver code and call iommu_map() again.
	Reboot only needed if driver doesn’t support dynamic updates.

Without PRI/SVM, a device cannot ever touch unmapped memory — only CPU can pre-program mappings in the SMMU. PRI lets devices raise page faults so kernel can map on demand. SVM extends this by giving the device a PASID and sharing the same mm_struct as CPU, so device VA = CPU VA. Without them, you must pre-map buffers; dynamic paging isn’t possible.


If driver supports dynamic update, then what is point of having pri ? Also can pri induce access violation because it can demand any page ?
	Dynamic updates require the driver to pre-map memory; PRI lets devices fault in pages on demand, just like CPU demand paging. It saves memory and enables true shared VA (SVM). PRI requests are validated against process VMAs, so they can’t escape protection; invalid requests return access violation instead of mapping.


mm_users counts live userland threads in an mm_struct, torn down at 0 via __mmput(). mm_count counts all kernel refs (including userland), torn down at 0 via __mmdrop(). Thus user mappings die at mm_users=0, but the mm_struct survives until all kernel references drop too.


Kernel threads have mm=NULL since they never run user code, but CPU’s TTBR0_EL1 still needs a valid pgd for TLB/speculation. So kernel uses active_mm to borrow the last user mm_struct, increments mm_count to pin it, and avoids flushing TTBR0_EL1 on every context switch.

Each processor has an idle task which represents the task that the scheduler switches in when there is no other processor work to perform*. It is, ostensibly, the process from which all other processes are derived. The progenitor of each CPU’s idle task is created very early on in kernel initialisation and is declared statically as init_task. Its active_mm field is assigned to init_mm which represents the shared mm_struct of each idle task. The mm field is set to NULL because this is a kernel process and thus defined by not possessing its own individual mm_struct

Idle Task and init_task
	Each CPU has a special task_struct called the idle task.
	Declared statically in kernel (init_task).
	Scheduler switches to this when the CPU has nothing else to run.
	It is not a real process (no user space, no binary, no mm).
	So:
		idle_task->mm      = NULL   // no user mm
		idle_task->active_mm = &init_mm

init_mm
	init_mm is a global mm_struct object, defined in mm/init-mm.c.
	It represents the kernel’s own page tables, built during early boot.
	Its .pgd = swapper_pg_dir → the kernel’s master PGD.
	All kernel threads and idle tasks reuse init_mm as their active_mm.
	mm_users = 2 → ensures init_mm never gets freed.
	Used as the “backing mm” for kernel-only contexts.

Why idle tasks use init_mm
	Hardware requires some PGD in TTBR0_EL1, even if we don’t run user code.
	Flushing the TLB on every idle entry would be expensive.
	So kernel sets active_mm = &init_mm.
	This way, TLB entries remain valid, and CPU speculation doesn’t fault.

Without PTI, both kernel and user mappings coexist in the same PGD, with kernel made inaccessible via flags. PTI splits them into dual PGDs, flipping CR3 on syscall/interrupt entry/exit. On ARM, this separation is built-in with TTBR0/TTBR1, so meltdown didn’t bite.

what mmap_lock does and the two lock flavors
	mmap_lock (a struct rw_semaphore) is the global address-space/VMA lock inside struct mm_struct.
		Readers (down_read): many concurrent readers allowed — used for operations that only examine VMAs or access page tables but do not change the VMA tree.
		Writers (down_write): only one writer — used for operations that change the address space layout (create/destroy/resize VMAs, set protections, pin pages, mlock, etc.).
	Why it’s hot: almost every process memory syscall and many kernel operations need to read or modify VMAs → enormous contention.

page_table_lock (spinlock) is separate: used to protect page-table updates (PTE/PMD allocations/updates). Many code paths take both locks (read mmap_lock and then page_table_lock) or use them in a carefully defined ordering.

Rule of thumb:
	Read lock for “lookups / pinning / common faults / GUP fast path / procfs read / smaps / pagemap reads”
	Write lock for “mmap/munmap/mremap/mprotect/brk/fork-copy-mm/exec/mlock/populate/locking that changes VMA or pins pages long-term”

High-level practical caveats (you want these remembered for interviews)
	Page-faults usually start with an mmap_lock read to find the VMA, but the handler may release mmap_lock while doing I/O, swap-in, or long operations and then return VM_FAULT_RETRY. The faulting instruction is retried after the lock is reacquired. This is central to correctness & deadlock avoidance.
	Fault lock-releasing path allows blocking work (reading from disk, swap, file I/O) without holding mmap_lock. This is why page fault code can return VM_FAULT_RETRY and the top-level handler loops.
	Write operations (mmap/munmap/mprotect/mlock/etc.) take down_write — these exclude readers and are heavier. Long writes can starve readers or cause contention.
	GUP (get_user_pages) / pin_user_pages: common operation used for pinning user pages for DMA; it uses the mmap_lock read path (fast), but the longterm/pin variants may require more guarantees (and may fall into slower paths that re-acquire or upgrade locks). Pinning long-term or doing mlock needs care.
	Do not hold mmap_lock while doing heavy blocking work (drivers must avoid taking it if they will sleep a long time); otherwise you can deadlock user code doing memory ops.
	Ordering: there’s a canonical ordering: acquire mmap_lock first (for VMA ops), and then page_table_lock when needed for PTE updates. Reversing can lead to deadlocks.
	mmap_lock is not per-thread — it protects the process address space. Kernel threads that reuse other process mm may increment mm_count / active_mm and hold references.
	Procfs readers (/proc/$pid/maps, smaps, pagemap) mostly take mmap_lock read — must be consistent and avoid races.
VMA (Virtual Memory Area) Basics
	Each process’s memory space is split into VMAs (code, heap, stack, mmap’d regions). Stored in struct mm_struct:
		mmap → head of a doubly-linked list of VMAs (vm_prev, vm_next).
		mm_rb → red/black tree of VMAs, ordered by vm_end.
	Why two structures?
		Linked list: Easy to traverse sequentially (prev/next).
		RB tree: Efficient to search by address (log n complexity).
	Keyed by vm_end (ensures non-overlap).
		Search: Find node where vm_end > addr and check vm_start ≤ addr.
	VMA Linking & Unlinking
		When inserting/removing VMAs, we update both:
		Linked list (__vma_link_list / __vma_unlink_list).
		RB tree (__vma_link_rb / vma_rb_erase).
	Functions:
		__insert_vm_struct() → inserts new VMA.
		vma_link() → links VMA into list/tree (+ file-backed handling).
		__vma_unlink() → removes VMA, invalidates cache.
	VMA Cache
		Each thread has a small VMA cache (task_struct->vmacache).
		It’s just a tiny hash (4 entries) of recently accessed VMAs, indexed by address.
		Keeps a sequence number (mm_struct->vmacache_seqnum):
		Incremented whenever mappings change.
		If sequence mismatches → cache invalidated.
	Functions:
		vmacache_find() → lookup.
		vmacache_valid() → checks cache validity.
		vmacache_update() → updates cache after a successful lookup.
	Benefit: Speeds up repeated address lookups (avoids tree walk).
	Page Cache (for file-backed VMAs)
		Acts as a bridge between VMAs and actual file data on disk.
		Each file has an address_space object (per inode):
		Contains list/tree of cached pages (i_pages).
		Maintains locks (invalidate_lock, i_mmap_rwsem).
		Tracks writeback state, error state, etc.
		File-backed VMA points to its struct file, which links to inode → address_space.
	On page fault:
		Calls VMA’s vm_ops->fault handler (often filemap_fault()).
		Brings data from disk into page cache and maps it.
	Optimizations:
		Readahead: Load more data than requested (anticipates sequential access).
		Keep entries hot: Even after use, retain pages to avoid slow disk access.

Per-Process Memory Counters
	Kernel tracks usage stats in per-process counters:
		MM_FILEPAGES → resident file-backed pages.
		MM_ANONPAGES → resident anonymous pages (heap/stack).
		MM_SWAPENTS → number of anonymous swap entries.
		MM_SHMEMPAGES → resident pages backed by shmem (tmpfs, etc).
	Stored in:
		task_struct->rss_stat (per-thread cache).
		mm_struct->mm_rss_stat (per-mm global state).
	To reduce contention:
		Per-thread counters accumulate changes.
		Flushed to global mm counters after a threshold (TASK_RSS_EVENTS_THRESH).
	Functions:
		add_mm_counter_fast() → updates per-thread, flushes later.
		check_sync_rss_stat() → checks threshold, flushes if needed.
		sync_mm_rss() → performs full sync to mm_struct.

kmem_cache_alloc_node()

	Avoids cacheline bouncing across nodes.
	Provides NUMA-awareness for kernel object allocation.

What is difference between worker thread, threaded irq, kthread worker, work struct, softirq, hardirq, tasklet and use cases and caveats? In terms of process, deadlock, spinlock, mutex, semaphore, barrier, scheduling, kernel userspace etc also tell 
	Hardirq (Top-Half Interrupt Handler)
		Where: Runs in interrupt context (not schedulable, no process).
		Locking: Only spinlocks (cannot sleep).
		Latency: Must be very short (acknowledge device, queue work).
		Use case: Time-critical tasks (ack device IRQ, schedule softirq/thread).
		Caveats:
			No blocking (mutex, semaphore, schedule() forbidden).
			Nested interrupts disabled.
			High risk of deadlocks if spinlocks misused.
	Softirq
		Where: Runs in softirq context (still not schedulable, but bottom-half).
		Locking: Spinlocks only (no sleep).
		Latency: Longer than hardirq, but still limited.
		Use case: High-throughput async processing (network stack, block layer).
		Caveats:
			Can starve other tasks if flood of softirqs.
			Not bound to processes.
			Preemption disabled during softirq.
	Tasklet
		Where: Built on softirq (serialized per-tasklet).
		Locking: Same as softirq (spinlocks only).
		Use case: Simple, deferred execution without concurrency on same object.
		Caveats:
			Runs in softirq context (no sleep).
			Single-tasklet instance is serialized → avoids race but hurts scalability.
	Threaded IRQ
		Where: Interrupt runs in a kernel thread context instead of hardirq.
		Locking: Can use mutex, semaphores, sleep.
		Latency: Higher than hardirq (needs scheduler).
		Use case: Devices needing longer or blocking handlers (e.g. I2C/SPI, GPU interrupts).
		Caveats:
			Higher latency than hardirq.
			Must ensure top-half still ack device quickly, then wake thread.
	Workqueue + Work struct
		What: struct work_struct is a deferred work item executed by a kernel thread from a workqueue.
		Where: Runs in process context (schedulable).
		Locking: Can sleep, use mutex, semaphores.
		Latency: Not real-time; scheduled on general-purpose kernel threads.
		Use case: Medium/long background work (disk flush, fs cleanup).
		Caveats:
			Throughput limited by available worker threads.
			If queue blocked (e.g. by slow work), system-wide stalls possible.
	Worker thread (generic term)
		What: Any kernel-created thread (not necessarily tied to workqueue API).
		Examples: kswapd (reclaim), ksoftirqd, etc.
		Locking: Process context (can sleep).
		Use case: Background daemons that manage resources.
			Caveats: Higher overhead vs work_struct if only small jobs needed.
	kthread worker
		What: A dedicated worker thread where you queue jobs (kthread_queue_work()).
		Difference: Unlike global workqueues, this is private per-subsystem.
		Locking: Process context, can sleep.
		Use case: Subsystem-specific serialized execution (e.g. DRM GPU jobs, USB device tasks).
		Caveats:
			Tied to single CPU/thread (less scalable).
			Useful when strict ordering per-device needed.

Linux provides a tiered model: hardirq for immediate response, softirq/tasklet for deferred atomic work, and threaded IRQ/workqueues/kthreads for schedulable, blocking-capable jobs. The main axis of difference is context (atomic vs process), locking allowed (spinlock vs mutex/semaphore), and latency vs flexibility tradeoff. You pick based on whether the code must be atomic and fast or can afford to sleep.

Kernel Concurrency Decision Tree
	1. Do you need to respond immediately to hardware?
	   |
	   +-- YES → Hardirq (top-half)
	   |        - Run in interrupt context
	   |        - Must be very short: ack device, queue work
	   |        - Spinlocks only, no sleep
	   |
	   +-- NO  → 2
	2. Do you need deferred but atomic, non-sleeping work?
	   |
	   +-- YES →
	   |        2a. Is work per-object and serialized enough?
	   |            → Tasklet (built on softirq, single instance serializes execution)
	   |
	   |        2b. Is work high-throughput and parallel (e.g. network packets)?
	   |            → Softirq (per-CPU execution, scales better)
	   |
	   +-- NO  → 3
	3. Do you need deferred work that *can sleep* or block?
	   |
	   +-- YES →
	   |        3a. Is it tied to an interrupt?
	   |            → Threaded IRQ (runs as kernel thread, can sleep)
	   |
	   |        3b. Is it generic background work, possibly parallel?
	   |            → Workqueue + Work struct
	   |
	   |        3c. Do you need subsystem/device-specific serialized worker?
	   |            → kthread worker (dedicated per-subsystem thread)
	   |
	   +-- NO  → 4
	4. Is it a long-lived kernel daemon task?
	   |
	   +-- YES → Worker thread (full kernel kthread, like kswapd, khugepaged)
	   |
	   +-- NO  → Rethink design (maybe wrong layer).

Caveats (Interview Traps)
	Hardirq/Softirq/Tasklet
		Atomic context → no schedule(), no mutex/semaphore.
		Must finish very fast, or system stalls.
		Spinlocks only.
		Threaded IRQ
		Higher latency than hardirq.
		Must still keep top-half minimal (just wake thread).
	Workqueues
		Can block.
		Can starve if queue stuck (global workqueue).
		Use dedicated queues for high-priority tasks.
	kthread worker
		Good for serialized per-device jobs.
		But not scalable across many CPUs unless you manage it.
	Deadlocks
		Don’t take sleeping locks in atomic context.
		Don’t mix spinlocks + mutex incorrectly across contexts.
	Scheduling
		Hardirq/Softirq unschedulable.
	Workqueues/kthreads are schedulable → subject to nice, cgroups.

Linux concurrency primitives form a latency-to-flexibility spectrum. At one end, hardirq/softirq/tasklet give atomic, non-blocking, low-latency work. At the other, threaded IRQ, workqueues, kthread workers, and daemons allow sleeping, blocking, and scheduling. You choose based on whether your code must run in atomic context or process context, and how much latency is acceptable.

Mechanism	Runs In	Context Type	Why?
	Hardirq (top-half)	Directly in IRQ handler	Interrupt context	Triggered by hardware IRQ. No process associated. Must be atomic, no sleep.
	Softirq	In softirq handler (e.g., ksoftirqd, or return-from-IRQ)	Interrupt context (softirq)	Still atomic, runs either immediately after hardirq or in ksoftirqd kernel thread, but always treated as non-schedulable.
	Tasklet	Scheduled in softirq	Interrupt context	Runs bottom-half work. Serialized per-tasklet, cannot sleep.
	Threaded IRQ	Kernel thread (irq/XXX)	Process context (kernel mode)	IRQ top-half wakes this thread, which runs as a normal schedulable kernel thread. Can sleep.
	Workqueue	Kernel thread (kworker/N:M)	Process context (kernel mode)	Deferred work handled by a schedulable kernel thread. Can block and sleep.
	kthread worker	Dedicated kernel thread	Process context (kernel mode)	Driver/subsystem creates its own thread for serialized jobs. Fully schedulable.
	Worker thread	General kernel thread (e.g., kswapd, khugepaged)	Process context (kernel mode)	Background daemons in kernel space.
	User process/thread	Userland	Process context (user mode)	Runs in ring3 (ARMv8 EL0). Can make syscalls to trap into kernel.

Why These Contexts Differ
	Interrupt context (hardirq/softirq/tasklet):
		No struct task_struct actively scheduled.
		CPU preempted → jumps directly into handler.
		Cannot sleep (no scheduler context).
		Only spinlocks valid.
	Process context (threaded IRQ, workqueue, kernel threads, user threads):
		Scheduler is aware.
		Associated with task_struct.
		Can sleep/block/wait on mutexes.
		Can enter kernel mode on syscall or run inside kernel threads.

Hierarchy Example (NIC RX Path)
	Packet arrives → Hardirq fires (interrupt context)
		|
		v
	IRQ top-half: Ack device, raise softirq
		|
		v
	Softirq (NET_RX_SOFTIRQ) runs in softirq context
		|
		v
	May run in ksoftirqd (process context, kernel mode) if load high
		|
		v
	Packet queued to socket buffer → woken up process (user thread)
	So: IRQ → Softirq → ksoftirqd → Userspace process crosses all four contexts.

FAANG Interview Memory Hack
	Hardirq/Softirq/Tasklet → Always interrupt context (atomic, no sleep).
	Threaded IRQ / Workqueue / kthreads → Process context (kernel mode, schedulable).
	User process → Process context (user mode).

Caveat traps they love asking:
	“Can workqueue sleep?” → Yes, because it’s a kernel thread.
	“Can softirq sleep?” → No, because it’s interrupt context.
	“What happens if you block in hardirq?” → Deadlock, system hang.
	“Why threaded IRQs exist?” → To allow IRQ handlers that may need to sleep (I²C, SPI, GPIO).

Why to have threaded irq, workqueue, kthread worker and worker thread. All looks smae to me
	Threaded IRQ
		Created by: The IRQ subsystem (not you directly).
		Purpose: Handle interrupts that need to sleep or run long.
		Lifecycle:
			Hardirq (top-half) fires → does minimal ack.
			Wakes up the irq/XX-thread (a kernel thread dedicated to that IRQ).
			Key property: Bound to an interrupt line. Runs only when IRQ fires.
			Use case: Device interrupt handlers that need to sleep (I²C, SPI, GPIO).
			Not generic work, only IRQ-related.
	Workqueue + Work struct
		Created by: Generic deferred work framework (kworker/* threads).
		Purpose: Run arbitrary deferred jobs that can block.
		Lifecycle:
			You allocate a struct work_struct.
		Queue it via schedule_work() or queue_work().
		Kernel picks a free kworker/N:M thread and executes it.
		Key property: Shared pool of worker threads → scales automatically.
		Use case: Deferred cleanup, filesystem operations, delayed processing.
		General-purpose async execution.
	kthread worker
		Created by: Drivers/subsystems explicitly (kthread_create_worker()).
		Purpose: Like workqueue, but dedicated to one subsystem/device.
		Lifecycle:
			You create a dedicated kernel thread.
			You enqueue struct kthread_work jobs to it.
			It runs only your jobs, in order.
			Key property: Per-subsystem serialization, no interference with global kworkers.
		Use case: DRM GPU jobs, USB device tasks, block layer flush.
		When you want guaranteed ordering & isolation.
	Worker thread (kernel daemon)
		Created by: Kernel itself (kthread_run() etc.).
		Purpose: Long-lived background daemons.
		Lifecycle: Loops forever, performing system service.
		Key property: Not bound to IRQs or job submission — it is the job.
		Examples:
			kswapd (memory reclaim).
			khugepaged (THP collapsing).
			kcompactd (memory compaction).
		Permanent kernel service, not transient work.

Caveats (interview traps)
	You can’t replace threaded IRQ with workqueue — IRQ subsystem requires a guaranteed binding to hardware IRQ.
	Workqueues share threads → one misbehaving job can delay others. Use kthread worker if you need isolation.
	Worker threads (kswapd) aren’t queued at all — they are kernel daemons.
	All four run in process context (kernel mode), but only threaded IRQ is tied to IRQ subsystem.

Threaded IRQs exist for interrupt handlers that need to sleep. Workqueues are for general deferred work across subsystems. kthread workers give drivers a dedicated serialized worker. Worker threads are permanent kernel daemons. They all run in process context, but their triggers and lifetimes differ.


Locking Rules per Context
	Context / Mechanism	Sleep Allowed?	Safe Locks	Unsafe Locks	Notes / Caveats
	Hardirq (top-half)	❌ No	Spinlock (irqsave/irqrestore), atomic ops	Mutex, Semaphore, rwsem	Must be short & atomic. Never block.
	Softirq	❌ No	Spinlock (BH-safe), atomic ops	Mutex, Semaphore	Runs in interrupt context, same as hardirq but bottom-half.
	Tasklet	❌ No	Spinlock, atomic ops	Mutex, Semaphore	Single tasklet per object serializes itself, but still atomic context.
	Threaded IRQ	✅ Yes	Spinlock, Mutex, Semaphore, Completions, rwsem	N/A (all OK)	Runs as a kernel thread. Use if IRQ handler must sleep.
	Workqueue (kworker)	✅ Yes	Spinlock, Mutex, Semaphore, Completions, rwsem	N/A	Deferred work in process context. Beware global workqueue starvation.
	kthread worker	✅ Yes	Spinlock, Mutex, Semaphore, Completions, rwsem	N/A	Per-driver serialized jobs, safe for blocking.
	Kernel worker threads (kswapd, khugepaged, etc.)	✅ Yes	Spinlock, Mutex, Semaphore, Completions, rwsem	N/A	Daemon loops. Can use all locks.
	User space	✅ Yes (via syscalls)	pthread_mutex, futex, semaphores, condvars	N/A	User-space locking maps down to kernel futex/waitqueue.

Special Synchronization Mechanisms
	Spinlock: Atomic only. Use in hardirq/softirq/tasklet.
	Spinlock_irqsave/irqrestore: Prevent local IRQ deadlocks when locking inside IRQ context.
	Mutex / rwsem: Sleeping locks → only valid in process context (threaded IRQ, workqueues, kthreads, user space).
	Semaphore: Legacy sleeping lock, still used in some drivers.
	Completions: Sleep until an event is signaled (safe in process context).
	Barriers (smp_mb, wmb, rmb): Ordering only, not mutual exclusion. Safe anywhere.

Caveats That Interviewers Love
	Why not spinlock in process context?
		You can, but spinlocks waste CPU if held long. Use mutex/semaphore in schedulable context.
	Why not mutex in IRQ context?
		Because mutex may sleep → IRQ context cannot schedule.
	What if you need to sleep in IRQ?
		That’s why threaded IRQ exists.
	What if your workqueue blocks too long?
		You can use dedicated workqueue (instead of global) or kthread worker for isolation.
	Deadlock trap:
		Never grab a sleeping lock in hardirq/softirq/tasklet.
	Never nest spinlocks incorrectly — interrupts must be disabled if lock acquired in IRQ.

Textual Diagram
	Hardware IRQ → Hardirq (spinlock only)
		  |
		  v
	   Softirq/Tasklet (spinlock only, non-blocking)
		  |
		  v
	   Threaded IRQ (can block, mutex/semaphore OK)
		  |

FAANG-ready takeaway:
	If it runs in interrupt context → spinlocks only.
	If it runs in process context → all locks allowed.
	Threaded IRQs exist specifically so drivers can use sleeping locks in interrupt paths.
	Workqueues/kthread workers are the general-purpose async execution layer.

eventfd:
	A system call (eventfd(unsigned int initval, int flags)) that creates a file descriptor (fd). This fd acts like a counter in the kernel. Kernel and userspace can increment/decrement this counter to signal events. It integrates with poll/epoll/select, so user processes can wait asynchronously. eventfd() creates a struct file entry (like any fd). It is not backed by storage (like inode) but by a kernel object (eventfd_ctx). It fits into the fd table of the process (so inherited on fork, sharable with dup, transferable via Unix sockets). It lives entirely in kernel memory, not user memory (unlike anonymous VMA). So eventfd is “fd-backed”, not “VMA-backed”. That’s why you can’t directly mmap() it for shared memory; it’s for event signaling, not storage.

	In drivers (like VFIO, KVM, KGSL GPU, DMA-buf fences), the kernel wants to notify user space when an event happens (e.g., GPU completed work, PCIe device signaled MSI, DMA buffer ready).
	Normally:
		poll on a file → wakes up when event happens.
		But poll is expensive → requires scanning.
		eventfd solves this by letting the kernel directly bump a counter → wakes up the process asynchronously.
		With irqfd, eventfd is hooked into interrupt handling: when device IRQ fires, kernel calls eventfd_signal() instead of poll.
		This makes eventfd async, non-polling, and scalable compared to iouring poll.

	Unlike mmap, eventfd does not touch struct mm_struct, VMA, or page tables. It’s purely about signaling, not memory mapping. But, eventfd fds can be embedded into DMA-buf fences → userspace can poll() an eventfd to know when a DMA buffer is safe to read/write (GPU ↔ display). This ties memory (DMA-buf, vm_area_struct) and events (eventfd) together.

							   v
					   fd -> struct file -> eventfd_ctx
							   |
						 poll/epoll wakes user
